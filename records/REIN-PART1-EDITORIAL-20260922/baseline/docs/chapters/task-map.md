# 00 从一次文档维护任务认识 Rein

**状态：新版初稿，待教学验收｜永久免费**

假设一个项目更新了启动命令，README还在教读者运行旧命令。我们希望助手找出差异，说明依据，提出修订，经过批准再修改，并检查修改后的说明是否能使用。这是本书持续演进的任务。此处是任务示意，不是已经完成的实机演示。

## 先分清谁在做事

模型根据输入产生回答或工具请求；工具提供读取、搜索、验证等具体能力；环境保存文件、进程和命令的真实状态；Harness决定请求能否执行、如何记录结果、何时继续或停止。模型说“已更新”不会改变磁盘；工具退出成功也不意味着文档内容正确。

第一步只把一段文档发给模型。到03，程序才实际读取文件；到09，工具在TypeScript宿主中执行，而Rust core掌握预算和结果采纳。到16，候选补丁才有经过批准的写入路径。17处理失败后的有限修复。较长任务需要的恢复、外部扩展与委派放在后续分支。

## 为什么选择文档维护

文档容易阅读，输入变化可以直观看见，失败也能构造出来：命令过期、参数变化、相对链接失效，以及其实无须修改。它同时要求模型理解文字和程序核对事实，适合观察二者的分工。代价是文档里的命令可能产生副作用，所以前期只读取，后期在受控夹具中验证。

每个任务保留用户目标、工作区边界、依据来源、候选差异、批准记录、实际文件状态与验证结论。当前没有能力产生的记录保持缺失，不能用示意数据冒充运行事实。

## 怎样沿着这本书学习

基础路线是00–17，再进入24。03、09、13、17和24之后各有一次阶段汇总。18–19面向长任务与恢复；20之后分别学习MCP和Hooks；23需要已有的任务拆分、权限、预算和验收。附录与阅读材料用于补充知识，必需推导留在正文。

本章的产物是一张任务说明：从四类失败中选一个，写下输入文件、期待变化和判定办法，并给每一步标注模型、工具、环境或Harness。能够解释“工具成功但任务失败”的例子，才算掌握四个角色。本章不设独立提示词栏目，避免用提示词代替自己的分析。

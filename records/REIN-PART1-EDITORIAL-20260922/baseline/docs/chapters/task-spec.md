# 02 把任务说清楚：提示词与成功标准

**状态：新版初稿，待教学验收｜永久免费**

上一章完成了一次模型调用。现在把“hello”换成“帮我更新README”，模型仍能回答，但我们很难判断回答是否有用：更新哪个部分，依据是什么，允许改哪些文件？先把这些问题说清楚，后面的工具才知道为谁工作。

## 从一句请求确定任务

本章沿用文档维护场景。假设README写着 `npm run start`，项目清单声明的启动命令是 `npm run dev`。这两个字符串只是教学案例，不能据此修改真实项目。把两份材料直接放进输入，要求助手解释冲突；本章尚不让它自行读取或修改磁盘。

```text
请比较我提供的README片段与项目清单，判断启动说明是否过期。
仅根据这两份材料回答；缺少证据时写明无法判定。
输出结论、引用片段、建议改动和验证办法，暂不修改任何文件。
README：启动项目请运行 npm run start。
项目清单：scripts 中只有 dev，值为 vitepress dev docs。
```

“仅根据这两份材料”限制判断依据；“缺少证据时写明无法判定”避免把猜测填成事实；“暂不修改任何文件”区分提出建议与执行修改。完整输出格式有助于检查，但格式正确不能证明结论正确。

如果要让下一段程序读取结果，可以约定JSON字段。例如 `decision` 只能为 `change`、`no_change` 或 `insufficient_evidence`，另外保存 `sources`、`proposal` 和 `checks`。收到JSON后仍要检查字段、引用及依据；模型给出的字段名不构成证据。

## 建立固定任务集

从现在开始固定四类问题，后续章节只扩充它们，不反复换领域。

| 案例 | 输入变化 | 可检查要求 |
| --- | --- | --- |
| 命令过期 | 文档命令与项目清单不同 | 引用双方，给出准确替换；不能宣称已运行 |
| 参数变化 | 指南使用旧参数，帮助文本声明新参数 | 指明来源版本，缺帮助文本时不猜 |
| 相对链接失效 | 文档目标不存在 | 根据文档目录解析相对路径；不只匹配字符串 |
| 无须修改 | 文档与依据一致 | 返回no_change，实际文件保持不变 |

为每例再造一个反例：删掉依据、提供相互矛盾的版本、让无关文字包含同名命令、把目标文件移到另一个目录。反例可以暴露“只找关键词”的判断。

## 把三个判断分开

需求判断回答“做什么”；格式判断回答“能否解析”；正确性判断回答“是否符合事实”。一次回答可能格式正确但引用不存在，也可能结论正确却遗漏用户要求保留的内容。不要把这些问题汇成一个模糊的“效果不错”。

本章产物是四条任务说明及各自的验收问题。先人工对照，再把稳定规则逐步转成13的验证器。24会扩充为四类各三例的12个案例。离线、回放和真实模型结果分开记录。

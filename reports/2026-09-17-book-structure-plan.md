# Rein 全书结构与章末提示词栏目修订方案

- 日期：2026-09-17
- 状态：待实施的结构方案
- 适用对象：《Rein：从零手写一个 Agent Harness》的正文、配套代码、阅读路径与阶段交付。

本方案汇总本轮关于全书结构、拆章与过渡、提示词示例的讨论。以下“新章”均指本方案编号；“原章”指当前 `docs/toc.md` 的 00–16 章。内容来源表示素材迁移关系，不表示新章已经写成或通过验收。

## 一、定位与修订目标

本书面向具备基本编程经验、希望学习 Agent 工程或准备相关岗位的读者。按“不要求读者预先熟悉 Rust”的路线设计，在进入 Rust core 时就地提供必要的迁移知识。

保留 Rust core + TypeScript 宿主与扩展的架构。TypeScript 用于早期快速建立直觉；Rust 接管运行状态、循环、预算和执行边界；TypeScript 后续承担工具宿主、SDK 与领域集成。模型服务商适配接口与 core/宿主扩展协议分别推导。

全书围绕同一个工作区文档维护助手演进：

> 回答文档问题 → 查找相关资料 → 判断内容是否过期 → 提出修订 → 批准与应用 → 执行验证 → 根据失败有限修复 → 按需增加长任务、恢复、扩展与协作能力。

第 00 章先交代任务地图、输入与期望产物。完整实机演示随能力交付补充，尚未实现的终点用明确标注的任务示意表达。第 24 章回到同一场景做评测和设计复盘。

修订遵循以下原则：

1. 一个章节围绕一个主要问题，提供可观察的学习成果；多个紧密相连的步骤可以构成一个完整闭环。
2. 内容密度过高时拆章；语言、架构或任务对象发生变化时安排有实际产物的过渡。
3. 从当前实现遇到的真实困难推导抽象，每章把新能力接回同一个 Rein。
4. 读者尽早接触成功标准；复杂验证器、权限策略和恢复机制在具体需求出现后展开。
5. 主线自足。阅读材料和附录按需补充，章末提示词也是可选辅助。
6. 区分程序测试、单次任务验收、证据关联与系统评测，分别说明结论的适用范围。
7. 必要边界随能力出现：读取时解释路径约束，运行验证命令时明确执行范围，写入时解释批准和基线，接外部能力时解释对应信任边界。
8. 基础项目以单 Agent 完成；进阶能力由任务需求和比较结果决定是否引入。

## 三、阅读依赖与阶段交付

### 1. 基础交付路线

`00–17 → 24`：先获得可用的单 Agent 修改助手，再完成领域评测与复盘。读者可以按本路线完成一个完整项目。

### 2. 进阶路线

- 复杂任务与恢复：`17 → 18 → 19`。需要跨运行恢复时加入持久化能力。
- 外部集成：以第 09 章宿主及基础交付中的验证、权限机制为起点进入 20；21、22 在明确的共享接口上分别展开，无需依赖 23。
- 协作：以单 Agent 能力、任务拆分、权限、预算和验收为起点进入 23。串行委派可以在单次运行内学习；需要恢复承诺时再接入 19。
- 第 24 章接收基础路线以及读者选用的进阶分支，比较应针对实际使用的能力。

目录编号表示阅读排版顺序，不代表所有进阶内容都是强制前置。标注“可独立阅读”的章节同时说明概念先修、动手起始代码和本章新增内容。

### 3. 五次阶段汇总的交付约定

| 汇总 | 位置 | 核心检查 |
| --- | --- | --- |
| 1：真实资料问答原型 | 第 04 章后 | 实际文件变化影响答案；错误被保留；适配器复用既有工具 |
| 2：可控混合 Harness | 第 09 章后 | 连续行动、预算、取消、宿主生命周期与未知结果均可观察 |

## 四、正文的组织与学习压力控制

每章先明确起点、问题和最终产物，再围绕具体问题展开设计与实现。推荐的叙事路径为：

> 观察任务或失败 → 尝试直接解法 → 解释暴露的限制 → 推导结构 → 分步实现 → 接回 Rein → 验证并讨论取舍。

这是写作检查方式，不要求所有章节复制相同小标题。概念章通过分析或设计成果结束，实现章通过可运行增量结束。

每章写作前确定四项：进入时已经会什么、遇到了什么新问题、本章增加什么、离开时能独立完成什么。过渡章也使用这一标准。

命令和预期输出用于验证教学结论。较长的机器校验脚本放入配套代码，正文解释输入、执行方式、关键结果及失败含义。必要语言知识就地说明，更深入的语言机制链接补充材料。

练习至少包含能促使读者作决定的内容，如选择边界、构造反例、补充验收规则或解释另一种设计的代价。逐步减少对照答案式操作，仍为每项练习给出可检查的要求。

固定任务与成功标准从第 02 章起累积；上下文策略章节使用它们作比较，第 13 章系统解释验证，第 24 章再扩大案例与评测。离线夹具、回放和真实模型运行分别标注，不将一种证据替代另一种。

## 五、每章最后的“提示词示例”栏目

### 1. 位置与用途

每个正文主题章（含 00）均设置末尾栏目“提示词示例”。顺序建议为：正文推导与实现 → 练习 → 验收要点 → 提示词示例及简短解析。阶段汇总可以提供综合提示词；阅读材料和附录按需设置。

栏目主要提供读者发送给 AI 编程或学习助手的参考提示词。正文中 Rein 自身的 system prompt、任务消息和工具描述按运行时用途讲解，并与本栏目明确区分。

提示词应引导读者完成本章已经定义的任务，使用到本章为止具备的能力。概念章要求解释、比较或设计；实现章要求检查已有工程、分步修改并验证。必需任务说明和验收条件仍在正文中完整提供。

### 2. 固定组成

每章提供一份可复制的主示例，必要时再给一个有明确用途的变体。示例包括：

1. 当前基础：已有功能、相关文件或章节起始版本。
2. 本章目标：具体任务、输入与期望产物。
3. 实现范围：需保留的行为和当前授权的操作边界。
4. 协助方式：先理解已有实现，再分步推导、修改并解释。
5. 验收要求：正常场景、失败场景、检查命令和需要记录的结果。

通用写作骨架如下，实际章节必须填入具体内容：

```text
我正在学习实现 Rein，目前已经完成：[已有能力与代码起点]。

本章要完成：[任务、输入和期望产物]。

请先检查现有实现，说明本次变化应该进入哪些位置，
再分步骤协助完成，并解释关键设计。

本次范围：[允许的修改与需要保留的行为]。
请使用到本章为止已经建立的接口和能力。

完成后按以下条件检查：
- 正常场景：[具体条件]。
- 失败场景：[具体条件]。
- 原有行为：[本章相关回归条件]。

请报告实际修改、实际执行的检查及结果，
并单独列出尚未执行或无法判断的部分。
```

每份示例之后解释两到三个关键句：它限制了什么歧义、如何影响执行、验收能够说明什么。提示词的重点随章节产物改变，不逐章重复同一段泛化要求。

### 3. 贯穿各篇的提示词教学重点

| 篇 | 示例重点 |
| --- | --- |
| 第一篇 | 清楚描述任务，区分请求与执行，给出可检查的成功标准 |
| 第二篇 | 保持迁移行为、限定新增能力、表达预算和停止条件 |
| 第三篇 | 指定依据、处理信息缺失、检查来源与验收规则 |
| 第四篇 | 限定修改、展示差异、遵守批准、验证新状态和控制修复 |
| 第五篇 | 明确子任务交付、约束扩展、比较方案并报告证据局限 |

早期示例更完整；后期可以给出有标记的待填项，要求读者选择预算、失败条件和验收规则，并在解析中说明选择依据。

### 4. 统一声明

各章示例附近使用以下声明，阅读指南另作集中说明：

> 以下提示词仅供参考。大模型输出具有不确定性，可能因模型及版本、采样设置、上下文和工具环境而变化，相同提示词也可能得到不同结果。请结合自己的项目调整，并以本章的验收条件检查生成内容；模型声称完成不代表任务已经通过验证。

提示词示例验证时记录使用的起始代码、模型与工具环境、实际修改和验收结果。单次成功只说明该次试用结果，不作跨模型、跨环境的成功保证。尚未试用的示例明确标注，不伪造生成记录。

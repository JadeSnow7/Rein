# 从第一章手工改写中提炼的写作风格

依据：2026-09-14 工作区中 `docs/chapters/01.md` 的手工改写，以及它相对 Git HEAD 的差异。只把新增、改写和删减体现的倾向作为主要证据；沿用旧稿的文字不单独当作作者偏好。当前稿件只完成部分内容，以下是本书教程写作的初步约定。

## 1. 从熟悉的使用场景提出一个具体问题

原文：“今天我们几乎每天都在使用 Agent 应用，但你有没有想过，在你向 ChatGPT 发送一句简单的‘你好’时，背后经过了哪些流程呢？”

先让读者回到自己经历过的操作，再指出尚不了解的过程。紧接着用“本章，我们将会……”说明学习动作与目标。开头承担场景、问题、目标三个作用，无需叠加悬念或情绪。

## 2. 用完整段落推进，减少刻意的口语停顿

旧稿中的“现在，我们把输入框换成终端……”和独立成段的“就说一句 hello。”被换成连贯的目标说明；“我觉得”“怎么说呢”等口语引导也没有保留。

保留与读者交谈的语气，但让每段说明一件完整的事。不机械地把每句话单独成段，也不靠口头禅营造亲近感。此前写作计划中的公众号式口语转场，应以这次手工改写体现的偏好为准。

## 3. 按实际操作拆步骤，标题直接说要做什么

原文依次使用“1、环境准备”“2、拉取代码”“3、准备 API key”“4、配置环境变量”“5、发出第一句问候”。相比旧稿，把环境与拉取代码、凭据与配置分别拆开。

一次讲清一个动作。先交代操作位置或目的，再给命令，随后解释结果。例如版本检查后接“看到三个版本号即代表已经安装完成”，克隆后接“现在我们就已经成功拉取源码并进入仓库根目录了”。让读者知道自己走到了哪一步。

## 4. 概念在需要使用时出现，并连接到熟悉的事物

原文：“就像你访问 ChatGPT App 需要登录一样，在终端调用模型同样需要对应的凭据来判断请求来自哪个账户，这就是 API key。”

先说它解决什么问题，再给名称。解释 `baseURL` 时，使用“向哪个站点发送信息”这样的具体描述；讲 SDK 时，落到刚运行过的文件及参数。术语与代码标识可以保留，解释应紧贴当前操作。

## 5. 用“我们”带着做，用因果和顺序连接段落

新增转场包括“接下来切换到本章代码”“仅仅有 API key 还不够，我们还需要 baseURL”“正如我们学习编程时从 helloworld 开始一样”。

“我们”用于共同操作，“你”用于读者的环境与选择。转场说明下一步为什么出现；同一问题将在后文展开时，可以用“稍后会讨论”保持阅读顺序，但后文必须兑现。

## 6. 给出明确建议，并照顾不同起点

手工稿进一步强调了建立练习分支，并加入另建项目、备份已有 `.env` 和使用 WSL 的建议，表明作者愿意作出具体判断，也会考虑读者已有文件或不同开发环境。

建议放在会影响操作的位置。主路线保持清楚，替代路线需要给足可执行条件。强调用于会影响操作成功或凭据安全的提醒，不扩展成每段都加粗。

## 后续写作可直接采用的约定

从读者熟悉的操作引出问题，明确本节要做什么。按真实执行顺序组织步骤，使用直接的动作标题；命令前交代目录和目的，命令后解释结果与关键参数。用完整、自然的中文段落串联概念、动作和结果，以“我们”带着读者实践。少用刻意的口语停顿、情绪渲染和密集验收术语；必要的成功条件与错误解释放到对应步骤。建议要具体，涉及服务、价格和模型的判断须单独核实。

## 不作为风格继承的草稿状态

尚未写完的“异常处理”、图示占位、单独的 `git` 命令，以及误放在 TypeScript 代码块里的解释文字，属于待补写或排版问题。标签与分支的区别、`model` 能否留空、base URL 与 API key 的技术表述，也需要依据实现另行校对。它们不应成为后续仿写的规则。本次风格提炼不等于这些内容已经通过技术验证。
## 本轮方向适用说明（2026-09-14）

本轮只调整导航、章节衔接与路线状态，不修改作者保留的 `docs/chapters/01.md` 正文。后续章节继续采用当前中文教程的完整段落、实际命令、失败结果和边界说明；01–03 保持 TypeScript 入门，05 章以后以 Rust core 为权威运行时，TS 作为宿主和领域插件。历史 TS 页面保留为可恢复的对照材料，不能在导航中伪装成 05–07 的语言变体。插件正文应明确当前命令和未验收限制，不能用测试草稿替代运行时证明。

本轮插件正文进一步沿用作者手稿中的完整连贯段落：先说明读者为什么要执行下一步，再给出可复制的命令，随后解释真实输出、身份字段和失败边界。段落可以短，但不把每个判断拆成孤立的口号或测试日志；操作顺序、概念解释和结果说明应在同一条阅读路径中自然衔接。

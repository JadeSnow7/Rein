# 阅读 0 基础知识 · 公共导读

知识补充与可选示例均已提供 · 永久免费

知识索引：终端与目录、HTTP、配置、Git，以及类型、异步和错误处理。下面的可选示例以 `你好，Rein` 和一份坏输入展示这些知识如何落地。

这是一份按需知识补充。还不需要模型密钥，也不用搭建 Agent 循环，只在内存中接收状态码和 JSON 正文，取出文本，再处理失败。类型、异步和错误传播都有了具体落点。

你可以选 TypeScript，也可以选 Rust。两版围绕同一组输入展开，先把一版读顺，再切到相同小节比较写法。这里假定你接触过一种编程语言，知道变量、条件判断与函数的基本用途。

| 入口 | 适合谁 | 读完后的目标 |
| --- | --- | --- |
| [TypeScript 版](./00-ts.md) | 有编程经验，准备使用 Node.js 与 TypeScript 实现 Rein | 能读懂对象类型、异步调用和异常处理，检查外部 JSON，并运行测试 |
| [Rust 版](./00-rust.md) | 有编程经验，准备使用 Rust 实现 Rein | 能读懂所有权与借用、结构体、枚举和异步函数，用 `Result` 处理失败，并运行测试 |

两版都有可运行的本地练习。第 01 章已提供 TypeScript 与 Rust 两版 SDK 调用；这里的阅读练习仍是独立教学程序。两版的完成状态与章节实现进度见[全书目录](../toc.md)。

## 先判断自己需要补什么 {#self-check}

先试着回答下面的问题，遇到不确定的地方，再进入对应小节。

1. 终端中的当前目录会怎样影响 `src/main.ts` 这样的相对路径？见本页的[终端与目录](#terminal)。
2. 运行程序、检查类型和运行测试，分别能发现什么问题？见 [TS 版〈先把程序跑起来〉](./00-ts.md#setup) 或 [Rust 版〈准备工程并运行〉](./00-rust.md#setup)。
3. 拿到一段 JSON 文本，怎样判断其中确实有程序需要的字符串？见 [TS 版〈对象与 JSON 文本不是同一个值〉](./00-ts.md#json) 或 [Rust 版〈JSON，解析语法，再检查形状〉](./00-rust.md#json)。
4. 异步调用失败后，错误会怎样传到入口？见 [TS 失败传递](./00-ts.md#errors)与[异步调用](./00-ts.md#async)，或 [Rust 错误枚举](./00-rust.md#errors)与[异步调用](./00-rust.md#async)。
5. 测试通过、HTTP 请求成功、模型回答正确，这三者是一回事吗？见本页的[HTTP](#http)和[示例输入与结果](#acceptance)。

不确定的问题可以进入对应补充小节；示例和练习也可作为自测。无需为了进入正文完成这些内容，也无需为了「预备」把两门语言的全部语法先学完。

## 可选示例的输入与结果 {#acceptance}

两种语言的可选示例使用同一组输入，从内存中取得模拟响应，检查状态与 JSON，再打印 `text`。正常结果为，

```text
你好，Rein
```

两版练习对同一组输入约定相同的结果与错误类别。这里的 `http`、`json`、`shape` 是练习中的错误类别，不是提前冻结的 Rein 运行时合同。

| 状态与正文 | 预期结果 | 检查目的 |
| --- | --- | --- |
| 200，`{"text":"你好，Rein"}` | 返回文本 | 正常路径 |
| 500，任意正文 | `http` | 先判断状态，避免用解析错误覆盖 HTTP 错误 |
| 200，`{` | `json` | 文本不是合法 JSON |
| 200，`{}`、`{"text":null}` 或 `{"text":42}` | `shape` | 合法 JSON 不等于字段符合要求 |
| 200，`{"text":"   "}` | `shape` | 本练习要求文本不能全为空白 |
| 200，含额外字段且 `text` 合格 | 返回原文本 | 允许无关字段，不擅自改写有效文本 |

安装工具链和下载依赖需要网络；依赖齐全后，练习与测试不访问外部服务。测试通过，表示这些已列出的本地行为符合预期，不能证明真实端点可连接或模型回答正确。Rust 编译通过、TS 类型检查通过，也各自只说明其检查范围内的代码约束成立。

## 终端与目录，先确认命令在哪里运行 {#terminal}

终端接收命令，shell 解释命令，再启动相应程序。文中的代码框通常只写要输入的内容；不用输入提示符 `$`。命令结束、出现下一行提示符，只说明控制权回到了 shell，并不说明命令执行成功。

本书中的「仓库根目录」，指同时包含 `README.md`、`docs/`、`ts/` 和 `rust/` 的目录。你的本地文件夹不必叫 Rein，但它的内部结构应当一致。

如果还没有取得代码，在准备存放项目的目录执行以下命令；已有本仓库的读者直接打开现有目录，

```bash
git clone https://github.com/JadeSnow7/Rein.git
cd Rein
```

Git 尚未安装时，可从 [Git 安装页面](https://git-scm.com/downloads)进入对应操作系统的说明。安装完成后，重新打开终端，运行 `git --version` 检查命令是否可用。

在 macOS / Linux shell 或 Windows PowerShell 中，可以用下面的命令确认位置，

```bash
pwd
ls
```

`pwd` 显示当前目录，`ls` 列出目录内容。PowerShell 中它们分别是相应命令的别名。如果使用 Windows CMD，对应操作是无参数的 `cd` 和 `dir`。后文使用 `cd` 切换目录；包含空格的路径应放在双引号中。

例如，从仓库根目录执行，

```bash
cd ts
ls
cd ..
```

第一步进入 `ts/`，第二步查看该目录中的文件，最后一步回到上一级。在 `ts/` 中，`src/main.ts` 指向它内部的文件；回到根目录引用同一个文件，需要写成 `ts/src/main.ts`。遇到「找不到文件」，先检查当前位置和路径，再检查代码。

**小练习**，在编辑器中分别打开根目录与 `ts/` 中的 `package.json`，再打开 Rust 预备练习的 `rust/examples/reading-00/Cargo.toml`。它们描述各自工程的依赖和运行方式。具体命令在语言版中展开；使用 Rust 练习并不需要安装 Node.js，使用 TS 练习也不需要先安装 Rust。

## HTTP，把请求和回答分开看 {#http}

后续章节会通过 HTTP 与模型服务通信。先把它看成一次有结构的交换，客户端发送请求，服务器返回响应。请求说明要访问哪个资源、执行什么操作以及携带什么数据；响应说明处理状态，并带回数据。协议的基本组成可参阅 [MDN 的 HTTP 概述](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview)。

下面是**教学用的 HTTP/1.1 形式示意，不是终端命令，也不是真实请求记录**，

```http
POST /v1/example HTTP/1.1
Host: api.example.com
Content-Type: application/json

{"prompt":"你好"}
```

`POST` 是方法，`/v1/example` 是路径，`Host` 和 `Content-Type` 是请求头，空行之后是正文。完整 URL 还包含 `https://` 这样的协议部分。方法和路径由所调用的接口约定；把 JSON 放进正文，也不会让任意地址自动成为模型接口。

响应示意如下，

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"text":"你好，Rein"}
```

我们会先查看状态，再解析正文。本练习用 `status` 数字和 `body` 字符串在内存里表示这两部分，不建立网络连接。真实接口中的回答字段可能位于多层对象中；第 01 章会讲具体形状。

一次调用至少有三层判断，HTTP 状态是否成功，正文是否符合程序需要的结构，以及得到的内容是否解决了任务。例如，200 响应中仍可能缺少 `text`；即使 `text` 是字符串，它也可能答非所问。状态码的分类见 [MDN HTTP 状态码参考](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status)。

练习只处理前两层。对回答质量建立验收条件，是后续章节的工作。

## 配置与环境变量，知道数据从哪里来 {#environment}

程序除了接收命令行参数，也可以读取启动进程时获得的环境变量。模型服务地址、模型名与密钥属于运行配置，不应固定写进源码。

`.env` 是保存配置文本的一种文件约定。例如，第 01 章使用下面的变量名；这里全部是占位值，

```dotenv
REIN_BASE_URL=https://api.example.com/v1
REIN_API_KEY=replace-with-your-key
REIN_MODEL=your-model
```

文件放在目录中，不等于配置已经进入进程。需要由启动命令或程序明确加载。第 01 章的 TS 命令使用 `--env-file=.env`；Node.js 对这一参数的规则见[命令行文档](https://nodejs.org/api/cli.html#--env-filefile)。Rust 的具体配置加载方式会在正式调用实现中说明。两份预备练习都不读取 `.env`，也不需要密钥。

遇到配置缺失时，检查变量名、启动目录与加载方式。分享错误日志或提交文件之前，检查其中是否含有真实密钥；本仓库已忽略 `.env`，但忽略规则不会清除已经被 Git 跟踪的敏感内容。

## Git，先能看清代码和自己的修改 {#git}

Git 保存项目的版本历史。此时先掌握三个观察命令，在仓库根目录执行，

```bash
git status --short
git diff
git diff --cached
```

`git status --short` 概括工作区和暂存区状态；`git diff` 查看已跟踪文件尚未暂存的差异；`git diff --cached` 查看准备进入下一次提交的差异。新建的未跟踪文件会显示在 `git status --short` 中，其内容不会出现在 `git diff` 里。看不到 `git diff` 输出，并不说明没有新文件。完整比较规则见 [Git diff 文档](https://git-scm.com/docs/git-diff)。

**小练习**，完成任一语言版后，在它的已有源码文件中添加一行说明性注释，再运行这三个命令。找到文件名和新增的那一行。这个练习只需要查看差异，提交、恢复和可靠基线将在[阅读材料 2](./02.md)中展开。

本书还使用 tag 标记章节快照。可以先运行 `git tag --list` 查看本地有哪些快照。第 01 章初版的 tag 是 `ch01`，其中不包含本阅读材料，也不包含该章后续修订。跟随本页时，请使用包含这份材料与第 01 章修订版代码的当前 `main`，或基于该版本建立的学习分支。

书中出现的 `git checkout ch01` 会把代码切到该历史快照，并进入 detached HEAD 状态，当前位置指向一个提交，而不是普通工作分支。它会改变你看到的文件，不是「启动第一章」的命令。这里只需理解含义，无需切换。以后要在快照基础上长期修改时，应建立自己的分支；切换前先查看并保存现有工作。有关切换和分支的行为见 [Git switch 文档](https://git-scm.com/docs/git-switch)。

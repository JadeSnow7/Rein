# 阅读 0 基础知识 · TypeScript 版

知识补充与可选示例已提供 · 永久免费

把示例里的 `text` 从一句话改成数字，程序会发生什么？

它仍然是一份合法 JSON，可我们准备打印的是文本。这一点小改动，就把语法正确和数据可用分开了。这份按需补充用 TypeScript 写一个本地解析程序，沿着这条区别，把类型、检查和错误处理串起来。

先跑出结果，再回头读写法。第一次遇到 `Promise<string>` 或 `unknown`，不必同时补完整门语言。遇到哪个问题，就在这个小程序里把它弄清楚。

可选示例代码在 `ts/examples/reading-00/`，不读取密钥，也不发送请求。终端、HTTP、配置和 Git 见[公共导读](./00.md)。[Rust 版](./00-rust.md)使用相同输入和自测要求，两版按相同知识点组织，可以按需切过去比对。

## 先把程序跑起来 {#setup}

### 准备工具

本仓库沿用第 01 章的环境要求，Node.js 22 或更高版本。尚未安装时，从 [Node.js 官方下载页](https://nodejs.org/en/download)选择适合操作系统的受支持版本。安装完成后重新打开终端，在仓库根目录执行，

```bash
node --version
npm --version
npm ci
```

前两条命令应打印版本号。若提示找不到命令，先检查安装和终端环境。`npm ci` 根据根目录的锁文件安装依赖；它会重建已有的 `node_modules`，不是更新依赖版本的命令。首次安装需要访问包源，依赖已按当前锁文件安装好的读者可以跳过。安装规则见 [npm ci 文档](https://docs.npmjs.com/cli/v11/commands/npm-ci/)。

根目录使用 npm workspace 管理 `ts/`，因此只需在根目录安装一次。Node.js 负责运行程序，TypeScript 提供类型检查，`tsx` 让我们在开发时直接执行 `.ts` 文件，Vitest 负责运行测试。它们各有职责。

### 运行与检查

从仓库根目录进入 `ts/`，执行，

```bash
cd ts
node --import tsx examples/reading-00/main.ts
npx vitest run --config examples/reading-00/vitest.config.ts
npm run typecheck
```

第一条运行命令应输出，

```text
你好，Rein
```

第二条应报告本练习的测试全部通过，第三条应完成类型检查并以退出码 0 结束。这里通过 `node --import tsx` 加载 TS 执行支持，无需额外生成 JavaScript 文件。

这三个结果分别意味着，正常示例可以运行；列出的成功与失败行为符合预期；源码符合当前类型约束。运行成功并不能替代测试，类型检查也不能判断远程数据今天会返回什么。

本练习使用独立的 Vitest 配置，因为主线配置只搜索 `ts/tests/`。在根目录直接运行 `npm test` 不会执行本练习，专项检查应使用上面给出的命令。下面未特别说明的命令都在 `ts/` 中执行。

## 用类型描述一份响应 {#types}

打开 `examples/reading-00/reading-00.ts`。最先遇到的是 `LocalResponse`，

```ts
export type LocalResponse = Readonly<{
  status: number
  body: string
}>
```

花括号中的定义描述一个对象，冒号右侧是字段类型。`status` 是数字，`body` 是字符串；`type` 给这一结构取名。`Readonly<...>` 使用一个现成的泛型类型，把其中字段标为只读。此时先把尖括号理解成「把这个对象类型交给 Readonly 处理」，无需开始设计泛型工具。

入口文件的正常场景使用这份类型构造数据，简化后的节选如下，

```ts
const response: LocalResponse = {
  status: 200,
  body: '{"text":"你好，Rein"}',
}
```

这是简化节选，依赖文件顶部的类型导入；实际入口用一个 `Record<string, LocalResponse>` 保存多个场景。`Record` 描述字符串键到响应对象的映射，命令行参数选择其中一项，缺省选择 `success`。`const` 表示变量不能重新赋值；它本身不冻结对象。这里字段不能通过 `response` 改写，是 `Readonly` 提供的类型约束。只读约束也不是运行时冻结或深层安全边界，相关细节见 [TypeScript 对象类型文档](https://www.typescriptlang.org/docs/handbook/2/objects.html)。

也可以在运行命令末尾增加 `http`、`json` 或 `shape`，直接执行对应的本地失败场景。正常场景的正文不是实际 HTTP 响应记录。

**试一次类型错误**，把入口 `responses.success` 对象中的 `status: 200` 改为 `status: '200'`，执行 `npm run typecheck`。应看到字符串不能赋给数字字段的诊断。修改初始化值不违反只读要求，但值本身仍必须符合类型。观察后改回 `200`，再继续运行。

### 对象、数组与可选值

`interface` 也可以描述对象。下面是单独的语法示意，不要求加入配套代码，

```ts
interface TextResult {
  readonly text: string
  usage?: number
}

const result: TextResult = { text: '你好，Rein' }
const results: TextResult[] = [result]
const firstText = results[0]?.text ?? '没有结果'
const tokens = result.usage ?? 0
```

`usage?` 表示这个字段可以不存在，读取时类型包含 `undefined`。`TextResult[]` 与 `Array<TextResult>` 都表示这种对象的数组。在本仓库的严格配置下，按下标读取可能得到 `undefined`，即使你预期数组中有数据，也要处理空数组的可能性。

`?.` 在左边为 `null` 或 `undefined` 时停止继续读取，并得到 `undefined`；`??` 只在左边为这两种值时使用右边的默认值。因此实际用量为 `0` 时，`??` 会保留这个 `0`。这里的默认值用于展示语法；第 01 章没有回报用量时显示「未回报」，不会用 0 冒充真实统计。

`type` 还可以命名联合类型，

```ts
export type ReadingErrorKind = 'http' | 'json' | 'shape'
```

竖线连接三个允许的字符串值。把类别写成其他拼写会得到类型错误。对象用 `interface` 还是 `type`，本篇先按已有代码阅读；不需要为了统一写法重构项目。

## 对象与 JSON 文本不是同一个值 {#json}

程序里的对象可以读取字段，请求与响应正文则经常是一段字符串。二者之间通过序列化与解析转换。下面是独立的语法示意，

```ts
const payload = { text: '你好，Rein' }
const body = JSON.stringify(payload)
const parsed: unknown = JSON.parse(body)
```

`body` 是文本，不能用 `body.text` 提取回答；需要先解析。反过来，对象也不能直接充当需要字符串的请求正文。

即使 `JSON.parse` 成功，得到的值仍可能是数组、数字、`null` 或结构错误的对象。`unknown` 表示「暂时不知道」，编译器不允许直接读取它的 `text`。我们必须先执行检查，让类型范围逐步缩小。

## 失败怎样传回入口 {#errors}

先看 `extractText` 的返回类型，写的是 `string`。输入坏掉时，它显然拿不出字符串，失败怎样离开这个函数？

代码会抛出 `ReadingError`。正常结果沿返回值传递，失败则沿异常路径传递。函数签名没有列出它可能抛出的类别，需要结合实现和测试阅读。

`ReadingError extends Error` 定义一种错误对象。构造函数中的 `super(message)` 初始化基类信息，`kind` 保存机器可判断的类别。入口先用 `instanceof Error` 确认它是错误对象，再用 `'kind' in error` 检查属性是否存在，并输出 `kind=http` 这样的标签；这个检查本身不验证属性值是否属于约定的错误类别。这样正常文本走标准输出，失败诊断走标准错误，失败退出码设为 1。

`unknown` 同样适用于捕获到的错误，JavaScript 可以抛出不属于 `Error` 的值，不能不加判断就假定它必定有 `message`。

## 异步与异常，等到什么，失败去哪里 {#async}

`readText` 在同步解析函数外提供一个异步入口，返回 `Promise<string>`。调用这个函数得到 Promise，用 `await` 等待它成功得到字符串；如果内部抛错，Promise 会拒绝，`await` 在当前位置抛出相应错误。

`await` 暂停当前异步流程，不能简单理解成「堵住整个 Node.js 进程」。本例没有网络或计时等待，保留异步入口是为了练习调用方式；第 01 章会在调用过程中真正等待 HTTP 收发。

入口把 `await` 放进 `try`，因此 `catch` 可以接到本次调用的失败。假如只是调用异步函数而没有等待它，外面的普通 `try/catch` 不会自动捕获它之后发生的拒绝。练习时应确认等待的位置，而不是看到 `async` 就假定失败已经被处理。

### 练习 01，运行正常与失败场景 {#exercise-01}

在 `ts/` 中逐条运行。每条命令结束后，立即查看退出码，再执行下一条。

```bash
node --import tsx examples/reading-00/main.ts
node --import tsx examples/reading-00/main.ts http
node --import tsx examples/reading-00/main.ts json
node --import tsx examples/reading-00/main.ts shape
```

正常场景打印 `你好，Rein`，退出码为 0。其余三个场景分别报告 `kind=http`、`kind=json`、`kind=shape`，退出码为 1。macOS / Linux shell 用 `echo $?`，PowerShell 用 `$LASTEXITCODE`，CMD 用 `echo %ERRORLEVEL%` 查看退出码。

打开入口，比较 `http` 和 `json` 场景的状态码与正文，沿解析顺序说明为什么一个报告 HTTP 失败，另一个报告 JSON 失败。两版内置的 `http` 场景正文不同，下一组练习会统一改成 `{`，再检查状态失败是否仍然优先。

## 和 Rust 版放在一起看 {#comparison}

回到开头的修改。两版都能拒绝数字 `text`，判断过程却有不同的写法。

| 同一个问题 | TypeScript 这份练习 | Rust 对应位置 |
| --- | --- | --- |
| 状态和正文怎么放在一起？ | `LocalResponse` 对象类型 | [结构体与数据持有](./00-rust.md#types) |
| JSON 通过语法检查以后呢？ | `unknown` 经过实际判断再收窄 | [先解析 `Value`，再转换 `Payload`](./00-rust.md#json) |
| 失败怎样离开函数？ | 抛出带 `kind` 的 `ReadingError` | [`Result` 与错误枚举](./00-rust.md#errors) |
| 调用方怎样等到结果？ | `Promise`、`await` 与 `catch` | [Future、`.await` 与运行时](./00-rust.md#async) |
| 怎样认出代码的职责？ | `main.ts` 组装，解析模块提供规则 | [同一文件中的实现与测试模块](./00-rust.md#source) |

Rust 的所有权内容会更长，这是那种实现需要说明的数据传递规则。可以先完成 TS，再带着同一份输入去读它，不必逐行寻找对应语句。两版共同的输入与结果见[示例输入与结果表](./00.md#acceptance)。

需要补充时，可以打开 `ts/src/main.ts`，找到 `await chat(...)`，再到 `ts/src/chat.ts` 找到 JSON 检查。正式调用的完整路径见[第 01 章 TS 版](../chapters/01-ts.md)，无需先完成本页示例。

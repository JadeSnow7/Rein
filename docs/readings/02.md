# 阅读材料 2　把章节基线保存成可复核的快照

当你读完一章并准备继续修改时，工作区里的最新文件和这一章实际讲解的代码可能已经不是同一个时点。比如，第 05 章的循环已经验收，而后续章节还会继续沿着同一棵演进树增加能力。若把“当前目录”直接当成“第 05 章的代码”，读者就无法判断正文中的命令、源码和输出究竟对应哪一版。

本书为章节时点保存了快照。快照是一组文件内容、相对路径和校验信息；它帮助你回到一个已知的文件集合。它不是新的 Git 提交，也不是一个已经建立的发布标签。当前交付没有为 05 章及之后的文件快照建立 Git tag，因此这些正文和示例以 `chapter-snapshots/` 下的归档、清单和相邻补丁为依据；这不否认 `ch01` 等已有标签。

## 先区分三个对象

Git 提交记录的是一次版本控制操作以及它的父提交；标签是指向某个 Git 对象的名称，适合在仓库历史中定位提交。快照清单记录的是“这组文件在保存时的字节校验和”，可以在没有提交或标签的情况下核对文件是否被改变。相邻补丁则描述两个文件树之间的差异，适合把一个章节时点的改动复现到另一份目录。

三者用途不同：提交或标签回答“这份文件在 Git 历史的哪里”，清单回答“指定路径的字节是否相同”，补丁回答“从前一棵树怎样得到后一棵树”。单个文件的 hash 相同，只能证明该文件的字节相同；它不能证明循环行为、测试结果或教程命令都正确。功能仍要按照对应章节的离线验收命令重新执行。

## 从 ch05 快照开始

下面的命令从书仓库根目录运行。先保存根目录，再进入临时目标目录；这样归档和补丁路径不会因为 `cd` 而失效。目标目录由 `mktemp` 创建，原仓库不会被解包覆盖。

```bash
export REIN_BOOK_ROOT="$PWD"
export REIN_SNAPSHOT_DIR="$(mktemp -d)"
tar -xzf "$REIN_BOOK_ROOT/chapter-snapshots/rein-ch05.tar.gz" -C "$REIN_SNAPSHOT_DIR"
cd "$REIN_SNAPSHOT_DIR/rein-ch05"
printf '快照目录：%s\n' "$PWD"
```

归档包含一个顶层目录 `rein-ch05/`。进入后，TypeScript 和 Rust 仍是同一个章节快照中的两个实现。先在两种语言的命令之前准备同一份输入；因此只跟做 Rust 部分时，也可以直接使用这个目录：

```bash
export REIN_CH05_DIR="$(mktemp -d)"
printf 'marker: README alpha\n' > "$REIN_CH05_DIR/README.md"
printf 'marker: NOTES beta\n' > "$REIN_CH05_DIR/notes.md"
```

TypeScript 的安装、类型检查和离线运行从快照根目录执行：

```bash
npm ci
npm run typecheck
npm run ch05:offline --workspace ts -- workspace "$REIN_CH05_DIR" multi
```

Rust 的命令也从快照根目录执行，但 Cargo 的清单在 `rust/` 中，所以要显式给出 manifest 路径：

```bash
cargo build --manifest-path rust/Cargo.toml
cargo run --manifest-path rust/Cargo.toml --example ch05_loop -- workspace "$REIN_CH05_DIR" multi
```

两条运行命令都应在同一个输入目录上执行，并产生“读取 README 和 notes 后给出多文件摘要”的离线结果。`npm ci` 和首次 Cargo 构建可能需要安装依赖；它们不是快照校验本身，也不应把依赖目录打进章节归档。

## 用清单核对文件

快照旁有 `rein-ch05.manifest.json`。例如，只核对第 05 章 TypeScript 正文时，可以从仓库根目录执行：

```bash
cd "$REIN_BOOK_ROOT"
export REIN_CHECK_DIR="$(mktemp -d)"
tar -xzf "$REIN_BOOK_ROOT/chapter-snapshots/rein-ch05.tar.gz" -C "$REIN_CHECK_DIR"
EXPECTED="$(node -e 'const fs=require("fs"); const m=JSON.parse(fs.readFileSync(process.argv[1], "utf8")); console.log(m.files.find(f => f.path === "docs/chapters/05.md").sha256)' \
  "$REIN_BOOK_ROOT/chapter-snapshots/rein-ch05.manifest.json")"
ACTUAL="$(shasum -a 256 "$REIN_CHECK_DIR/rein-ch05/docs/chapters/05.md" | awk '{print $1}')"
test "$EXPECTED" = "$ACTUAL" || exit 1
printf 'docs/chapters/05.md: %s\n' "$ACTUAL"
```

`test` 成功只表示这个路径的 hash 与清单一致。若你编辑了文件，重新计算出的值不同，应该重新生成快照或明确把它当成工作区改动；不要手工改清单来掩盖差异。

## 从 pre-ch05 应用相邻补丁

有时你需要查看“第 05 章到底增加了什么”。这时可从前一时点的归档创建另一份临时目录，再应用相邻补丁。补丁命令在 `rein-pre-ch05/` 内执行，因为补丁中的路径相对于这棵文件树：

```bash
cd "$REIN_BOOK_ROOT"
export REIN_PATCH_DIR="$(mktemp -d)"
tar -xzf "$REIN_BOOK_ROOT/chapter-snapshots/rein-pre-ch05.tar.gz" -C "$REIN_PATCH_DIR"
cd "$REIN_PATCH_DIR/rein-pre-ch05"
git init -q
git apply --binary -- "$REIN_BOOK_ROOT/chapter-snapshots/pre-ch05-to-ch05.patch"
test -f docs/chapters/05.md
test -f docs/chapters/05-rust.md
```

`git apply` 成功表示补丁中的文本、文件、二进制内容和可执行位可以应用到这份前置目录；这里的 `git init` 只为让 Git 有一个工作树，并没有创建提交。它仍不替代第 05 章的 TypeScript 类型检查、Rust 编译、测试和离线场景验收。若目标目录已有相同改动，Git 会报告冲突，应停下来检查基线，而不是强行覆盖文件。

## 快照与演进树如何一起使用

完成本章后，你可以继续在自己的工作区开发。后续实现可能会改变循环入口、测试和文档，因此工作区的最新版本会逐渐领先于 `rein-ch05`。需要复现第 05 章时，重新解包 `rein-ch05.tar.gz` 到新的临时目录；需要研究第 05 章的改动时，从 `rein-pre-ch05.tar.gz` 解包并应用对应补丁。这样“章节正文所依据的时点”和“项目现在继续演进的状态”各自清楚。

不要把快照目录当作用户输入参数，也不要依赖某个代理留下的私有临时路径。读者只需在自己的书仓库根目录执行上面的命令；命令通过 `REIN_BOOK_ROOT` 形成归档和补丁的绝对路径，解包目标则是本机新建的临时目录。每次实验结束后可删除目标目录，源归档和清单不会受到影响。

当你要报告一个结果时，同时写清楚使用的归档、清单或补丁，以及实际运行的命令。可以说“`rein-ch05` 快照中的 `docs/chapters/05.md` 与清单 hash 一致”，不能仅凭这句话推断“第 05 章功能通过”。后一结论要有对应的运行输出和退出码。

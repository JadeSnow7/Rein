# 阶段汇总 1：真实资料问答原型

**状态：复查步骤已整理，阶段项目待验收｜永久免费 · Apache-2.0**

完成第一部分后，我们已经有三块基础：从终端调用模型、给任务设定可检查的要求，以及让程序读取文件并把结果交回模型。现在把它们放在一起，确认回答确实使用了这次取得的资料。

这里的“真实资料”指磁盘上实际存在并被程序读取的文件。第 03 章只开放两个教学文件名，完成的是一次读取与一次回答，还不具备搜索整个项目或修改文档的能力。

## 1、确认复查起点

使用你跟随[第 01 章](../chapters/model-hello.md)准备的当前工作副本，并完成[第 03 章](../chapters/tool-roundtrip.md)的 `ts/ch03.ts`。后面的命令都在 `ts/` 运行；依赖已安装，`.env` 已按所选服务填写，`hello.md` 是本次练习文件。

新版逐章输入与输出快照尚未冻结，因此本轮可以在自己的工作副本中复查，但还不能声称已通过统一的章节快照验收。记录当前代码版本和自己的改动，保留实际使用的 `ch03.ts` 与输入文件；有未提交改动时，单独一个 Git 提交号不足以描述这次运行。旧 `ch01-helloworld` 标签也不能代替新版第 03 章的结束快照。

## 2、让答案随文件变化

先在 `hello.md` 写入第 03 章的问候任务，然后运行：

```bash
node --import tsx --env-file=.env ch03.ts
```

保留终端打印的工具结果和模型回答。工具结果应包含成功标记、实际文件名和内容；回答应符合文件中的问候要求。两者都需要检查，单独一句熟悉的问候不足以证明读取过程正确。

接着，只把文件中的问候换成自己选取的另一句话，保持命令和用户请求不变，再运行一次。工具记录应出现新内容，模型回答也应随之变化。如果工具仍打印旧内容，先查工作目录和文件保存情况；如果工具内容已更新、回答却仍沿用旧问候，再查模型收到的消息和回答。

上述每次运行正常包含两次模型请求，会产生 API 用量。没有可用服务时，可先做第 03 章的本地执行器练习，并将这组模型对照记录为未运行。

## 3、检查失败是否被保留

确认练习目录中没有 `missing.txt`，再运行：

```bash
node --import tsx --env-file=.env ch03.ts missing.txt
```

工具应返回 `not_found`，模型应说明未取得文件，不能编造文件里的问候。程序成功打印一段“文件不存在”的回答时，进程仍可能正常退出；这说明通信过程完成了，不表示原先的读取任务成功。

随后执行第 03 章给出的本地参数检查，核对错误 JSON、越界文件名和缺失文件依次得到 `invalid_arguments`、`invalid_path`、`not_found`。这一项直接调用本地执行器，不需要模型密钥。它证明本地边界能处理指定输入，不能代替前面的真实模型往返。

## 4、判断第一部分的学习结果

用下面的问题逐项复查。某一项没有执行，就保留为未运行；执行后不符合预期，就记录实际结果及失败原因。

| 复查问题 | 可以查看的材料 |
| --- | --- |
| 能否解释是谁读取了文件？ | 第 00 章的角色说明与本次工具记录 |
| 能否区分请求失败与答案不合要求？ | 第 01 章的错误诊断与实际回答 |
| 任务有没有明确依据和成功条件？ | 第 02 章的任务说明、预期判断与反例 |
| 文件变化有没有进入下一轮请求并影响回答？ | 两次输入文件、工具结果与模型回答 |
| 读取失败有没有被当作失败资料传回？ | `not_found` 工具结果与后续说明 |

保存代码版本、工作目录、命令、输入文件、退出码和原始输出即可开始复查，记录中不要包含 API key。正式阶段验收还需要冻结并标识章节快照，再在该起点重跑成功、变化和失败场景；本地测试通过、产品运行时进展和一次示意回答都不能替代这些记录。

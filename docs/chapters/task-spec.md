# 02 把任务说清楚：提示词与成功标准

**状态：文字修订稿，待教学验收｜永久免费 · Apache-2.0**

上一章，我们把一句 `hello` 发给模型，收到了回答。现在把它换成“帮我更新 README”，程序仍然能够发出请求，任务却变得含糊：更新哪个部分，以什么为依据，允许直接修改吗，怎样才算完成？

这一章先不增加工具。我们仍使用上一章的调用入口，把资料随请求一起发给模型，并给回答设定可以检查的要求。学完后，你应能区分“请求说清楚了”“输出格式正确”和“结论有依据”这三件事。

## 1、把“帮我更新”改成可判断的任务

先用一组教学材料。假设项目维护者明确约定：当前预览命令只以给出的 `scripts` 清单为准，没有另外的启动入口。README 还写着 `npm run start`，清单中却只有 `dev`。

如果只让模型“优化 README”，它可能润色措辞，也可能补上我们没有提供的安装步骤。我们真正要查的是预览命令，所以应把任务、依据和输出要求放在同一个请求里。

我们把这样的完整输入称为提示词：它既包含要做的事，也包含模型这次判断可以使用的资料。本章的提示词会作为一条用户消息发出，消息里的 README 和配置片段都是教学材料，不是程序从当前仓库读取的结果。

先读下面的完整命令，暂时不要执行。它沿用上一章的 `hello-safe.ts`，需要在 `ts/` 目录运行，并已配置好 `.env`；执行会向配置的服务发送材料，产生 API 用量。外层单引号把多行文字合成一个命令行参数，适用于 macOS、Linux 或 WSL 的 shell。本例文字中没有单引号；修改练习时也要留意引号是否闭合。

```bash
node --import tsx --env-file=.env src/hello-safe.ts '请检查 README 的预览命令是否符合给定的当前项目约定。

任务边界：只比较下面两份材料，不读取或修改磁盘，不执行命令。
项目约定：预览命令只以这份完整的 scripts 清单为准，没有另外的启动入口。

材料 A，README 当前片段：
启动预览请运行 npm run start。

材料 B，同一版本的 package.json 片段：
{"scripts":{"dev":"vitepress dev docs"}}

请输出：
1. 结论：需要修改、无须修改，或依据不足。
2. 依据：分别引用与结论有关的材料原文。
3. 建议：只给出必要的文字替换；依据不足时说明缺少什么。
4. 验证办法：说明修改后应检查什么，不要声称已经执行。'
```

这里的“同一版本”和“完整清单”很关键。如果配置只是截取的一小段，或者与 README 来自不同版本，就不能直接断言启动入口不存在。任务需要保留这些条件，而不是让模型自行补全。

## 2、先人工写出预期，再看模型回答

在调用模型前，先用自己的话写下合格答案。本例应该指出 README 的预览命令与给定约定不一致，引用 `npm run start` 和 `"dev":"vitepress dev docs"`，建议把该处替换成 `npm run dev`。验证办法可以是检查替换后的文字与清单一致，并在允许运行命令的环境中另行验证预览是否启动。

注意最后一步仍是建议。我们没有启动服务器，也没有检查其他安装条件，因此不能写“新命令已经验证可用”。下面是人工编写的判定示例，不是模型运行记录：

> 需要修改。材料 A 使用 `npm run start`，材料 B 的预览入口是 `dev`；按题目给出的当前项目约定，应将这一处改为 `npm run dev`。修改后先核对文本与清单，再单独验证命令能否启动预览。目前未执行命令。

写好预期后，有可用配置时就可以在 `ts/` 执行第 1 节的完整命令。它只发送单引号中的文字，不会因为出现了 `package.json` 这个文件名就去打开文件。没有可用凭据时，先完成人工分析，真实模型结果留为未验证。

读回答时，不必要求措辞与示例一致。先看结论是否为“需要修改”，再回到材料中寻找它引用的原文，然后检查建议是否只针对预览命令，最后确认它没有声称已经修改或运行。任一步不满足，都应记下具体偏差。

例如，下面这份回答虽然有四个栏目，仍然不合格：

> 结论：需要修改。依据：package.json 中配置了 `"start":"vitepress dev docs"`。建议：统一改用 `npm start`。验证办法：已经启动预览，运行正常。

这里的 `start` 配置不在材料 B 中，建议也不符合题目给出的当前约定；最后一句还把没有做过的操作写成了事实。检查格式只能发现栏目是否齐全，发现这三个问题需要重新核对资料与任务范围。

## 3、用反例检查判断是否可靠

现在改变输入，看看先前的结论还是否成立。每次都从第 1 节的原始案例出发，只做下面指定的一组改动，其余要求保持不变。先写新预期，再发送包含全部任务和材料的完整输入；这个 CLI 不会自动带上上一次对话，不能只发送“把材料 A 改一下”。

- 把材料 A 改为 `npm run dev`，其余不变。合格答案应是无须修改，不能为了“完成任务”另造改动。
- 删除材料 B 及其标题，并把项目约定改为“预览命令需以当前配置为准，当前配置尚未提供”。合格答案应是依据不足，并指出需要当前配置或维护者说明，不能凭常见写法猜测。
- 把材料 B 标记为旧版本，并把项目约定改为“预览命令需以当前配置为准，以下只提供旧版本配置”。回答应先确认当前依据，不能把不同版本直接比较后要求替换；不要保留“同一版本”的矛盾标记。
- 把材料 A 改为两句：“当前预览请运行 `npm run dev`。历史用法曾使用 `npm run start`。”回答应判断当前预览说明无须修改，保留历史说明，不能全局替换所有同名字符串。

这些变化让我们看见：提示词中写了要求，并不保证模型会遵守。每次仍要拿实际回答与预先确定的条件对照。一次答对也不能说明换个模型、上下文或任务后仍然可靠。

## 4、建立四类固定任务

从这一章开始，保留一组任务，后面的工具、上下文和验证章节继续使用它们。先为每类写一个正例和一个反例，不必马上编写自动评分器。

| 类型 | 正例中的已知资料 | 预期判断 | 反例与预期变化 |
| --- | --- | --- | --- |
| 命令过期 | README 使用 `start`；同版本完整清单约定使用 `dev` | 引用两者，只建议替换这一处 | 当前说明已使用 `dev`：无须修改 |
| 参数变化 | 指南使用 `--dest`；同版本完整帮助文本明确只支持 `--output` | 引用参数说明，提出对应替换 | 缺少帮助文本：依据不足 |
| 相对链接失效 | `docs/guide.md` 链接 `./setup.md`；给定的完整目录清单没有 `docs/setup.md` | 说明按文档目录解析后的目标不存在 | 清单中有 `docs/setup.md`：目标存在，不因别处缺同名文件而改动 |
| 无须修改 | 指南和同版本依据中的命令、参数一致 | 明确保留原文，并引用一致的部分 | 只留下指南、删掉依据：无法继续确认是否一致 |

本章对链接的判断来自你提供的目录清单，不是程序亲自检查磁盘。清单不完整时，结论也应退回“依据不足”。第 03 章才开始接入实际读取，后面的章节再逐步增加更多检查能力。

给每条任务保存四样东西：完整输入、预期判断及理由、实际回答、检查结果。检查结果写明哪里符合、哪里偏离，例如“结论正确，但引用了材料中不存在的配置”，不要只写“看起来不错”。尚未调用时，实际回答和检查结果均记为“未运行”。修改案例后保留新版本，不用新条件悄悄覆盖旧记录。这样才能比较一次改动究竟改善了什么，而不是每次换题后只记下印象。

## 5、把任务、格式和正确性分开

任务要求决定做什么，例如“只检查预览命令”。输出格式决定结果怎样表达，例如分成结论、依据、建议和验证办法。正确性检查则要回到资料，看引用是否存在、推理是否成立、建议是否越过范围。

当下一段程序需要读取回答时，可以约定 JSON，例如 `decision` 只能取 `change`、`no_change` 或 `insufficient_evidence`，并保存 `sources`、`proposal` 和 `checks`。但约定字段只是第一步，程序还需要解析和检查结构；字段齐全以后，仍要核对引用和事实。本章先用自然语言输出和人工检查，JSON 解析不是这次练习的前置要求。

也要分清“提出任务边界”和“程序限制操作”。提示词写“不修改文件”是一项要求；程序根本没有开放写入工具，才是实际能力边界。本章的 `hello-safe.ts` 只把文字发给模型并打印回答，没有根据回答去读写项目文件。

## 6、完成本章练习

整理四类任务的正例与反例，先写预期判断，再检查回答。你应能解释至少一个“格式正确但结论错误”的例子，以及一个“依据不足时应停止判断”的例子。

记录结果时，人工示例、受控回放和真实模型回答分开保存。实际调用才记录调用时间、请求的模型名、输入和回答；没有调用就不填写成功次数、成本或延迟。第 13 章会把其中适合自动检查的规则做成验证器，第 24 章再扩充为四类各三例的评测案例。

下一章，我们不再由人把全部资料粘进输入，而是让程序响应模型的工具请求，读取一个真实文件。先把“想读取什么”和“实际读到了什么”接起来，才有条件让后续判断依赖当前资料。

## 提示词示例

第 1 节命令中单引号包住的文字就是本章的运行提示词，也可以交给学习助手分析。请它指出任务、依据、允许动作和成功标准分别在哪里，再用第 3 节的反例检查自己的解释。

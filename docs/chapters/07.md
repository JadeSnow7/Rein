# 07 上下文管理

本页是旧 TypeScript 上下文管理实现的完整对照，保留其快照命令和行为解释。当前主线入口是 [Rust core 版](./07-rust.md)；它负责权威的上下文状态，TypeScript 扩展不与本页组成语言变体。完成本页的历史比较后，回到 Rust core 继续后续混合路线。

上一章把模型回合、工具调用和取消放进了同一个循环。循环现在知道“最多再做几次”，却还不知道“这些消息能不能一起放进模型的预算”。任务运行得越久，历史越长；如果把所有历史原样重发，模型适配器可能在真正回答前就因为上下文过大而失败。更危险的是，随意删除一条消息会留下孤立的工具结果，模型看到的对话就不再是发生过的对话。

本章把上下文拆成四个对象：规则告诉模型必须遵守什么，当前目标说明这一轮要解决什么，完整审计历史保存已经发生过的对话，待发上下文则是从前三者构造出的本次模型输入。它们有不同的生命周期。规则和目标始终保留；完整历史只追加、不因裁剪而丢失；待发上下文可以在预算内删除最旧的完整回合。示例是公开的确定性离线适配器：它读取实际传入的工具结果拼出答案，不访问网络，也不代表真实模型的能力或服务 token 用量。

## 先让长历史失败

先准备一个临时副本。命令从仓库根运行，路径使用绝对路径，这样 npm 切换到 workspace 后仍能找到文件。不要改写仓库里的冻结案例。

```bash
export REIN_CH07_DIR="$(mktemp -d)"
cp fixtures/cases/ch07-context.json "$REIN_CH07_DIR/cases.json"
npm ci
npm run --silent ch07:context --workspace ts -- "$REIN_CH07_DIR/cases.json"
```

`npm ci` 只在依赖尚未安装时需要；本书使用已经存在的 `node_modules` 也可以直接运行最后一条命令。输出最外层是 `{unit, cases}`。每个案例包含 `result`、真正进入 adapter 的 `requests` 数量和 `sentMessages` 二维数组。先找 `unmanaged-overflow`：它和 `managed-window` 的 `rules`、`goal`、`history`、`budget` 完全相同，只有 `managed` 不同。这个固定历史的完整候选上下文是 644 个 `estimated-bytes-v1` 单位，规则与当前目标加最新完整工具组需要 239 个单位，预算是 300。

未管理案例的 `context_prepared` 事件显示 `mode: "unmanaged"`，`beforeUnits` 和 `afterUnits` 都是 644，`removedGroups` 为空。适配器实际收到的消息超过 300，于是抛出 `adapter_budget_exceeded`，循环把它报告为 `reason: "model_error"`，请求数为 1。CLI 的退出码表示程序成功打印了 JSON；业务结果仍由 `result.state` 和 `result.reason` 判断，不能因为进程退出码为零就说任务完成。

这次失败说明 `maxTurns` 不能替代上下文管理。它只限制循环次数，不会缩短已经构造好的消息。规则、目标、完整历史和待发输入也不能混成一个可随意截断的字符串，否则无法解释删掉了什么，也无法判断工具调用是否仍有对应结果。

<a id="context-inputs"></a>

## 四个输入对象各自做什么

`ContextConfig` 有四个字段：`rules` 是字符串数组，`history` 是既有 `Message` 的完整数组，`budget` 是非负安全整数，`manage` 是可选布尔值，默认开启管理。`runAgentLoop` 的 `prompt` 仍是当前目标。初始化时，程序先深复制 `history`，再在其末尾追加当前目标；这个追加位置固定为输入历史的长度，即使后面模型生成了更多消息，也不会把某个新 user 消息误认成目标。

规则不会写回审计历史。每次准备模型请求时，循环按原数组顺序把规则生成 `system` 消息，再拼接保留的历史组。因而 adapter 收到的 `messages` 含规则，而 `LoopResult.messages` 仍是没有注入规则的完整审计历史。规则消息也不参与可裁剪组；历史里的 `system`、未知 role、user 声明工具、assistant 声明的调用缺结果，都会在派发前以 `invalid_context_history` 停止。

完整历史不是“上一次发送的数组”。每一轮模型返回的 assistant 消息及其真实工具结果都会追加到它。adapter 只收到这个历史的独立快照：即使适配器在数组上 `push` 或修改消息，也不会改变审计历史和已经记录的事件。TypeScript 的 `readonly` 只阻止类型检查下的直接赋值，并不等于运行时深不可变；这里用 `structuredClone` 复制嵌套对象。它不能替代输入验证，也不能复制所有 JavaScript 值，所以本章的消息只接受字符串、有限数字、布尔、数组和对象组成的 JSON 数据。

## 用固定单位估算上下文

<a id="budget-estimate"></a>

`estimated-bytes-v1` 是教学用的可复算估算单位。它使用字符串的 UTF-8 字节数，却不是 JSON 序列化后的线上字节数，也不是服务提供商的 token。估算不包括工具 schema、HTTP 包络和服务端隐藏字段；固定值 8 只是本地模型消息结构的预算项。

令 `utf8(s)` 为字符串原始 UTF-8 字节数，JSON 值的估算为：`J(null)=4`，`J(true)=4`，`J(false)=5`，`J(number)=8`；字符串为 `2+utf8(s)`；数组为 `2+各元素 J 之和+max(0,n-1)`；对象为 `2+各键(2+utf8(键)+1+J(值)) 之和+max(0,n-1)`。每条消息为：

```text
M = 8 + utf8(role) + utf8(content)
    + (存在 toolCallId ? utf8(toolCallId) : 0)
    + Σ(8 + utf8(id) + utf8(name) + J(arguments))
```

一组消息的 `E` 是其中每条 `M` 的和。中文和 emoji 必须先转 UTF-8 再计数；例如 `你好 🌏` 的内容是 11 个 UTF-8 字节。实现入口是 `ts/src/rein/loop.ts` 的 `estimateMessages`，它调用同文件的 `estimateJson` 和 `estimateMessage`。数字必须有限，`budget` 必须是非负安全整数；这些是输入合同，不是“估算失败后随便继续”的建议。

## 只能整组裁剪

<a id="atomic-history"></a>

程序先验证全部历史，再把消息分组。没有调用的 user 或 assistant 是一组；声明调用的 assistant 与紧随其后的全部 tool result 是一组。稳定组 ID 使用该组在完整审计历史中的起始零基索引，例如 `g1` 表示从历史第 1 条开始的组。多调用回合允许结果按任意顺序出现，但每个调用 ID 必须恰好对应一个结果，且结果必须连续跟在声明后面。

当前目标组和最新的完整工具组是必要组。必要组与规则的估算已经超过预算时，循环记录 `context_rejected`，原因是 `context_budget_exhausted`，不调用 adapter，也不通过删除目标来制造成功。否则从最旧的非必要组开始整体移除，直到实际发送消息不超过预算。一个组中的两个调用不能拆开，也不能只留下 tool result；每轮都从完整审计历史重新计算，上轮被裁掉的组只是暂时不发送，仍保留在 `LoopResult.messages`。

## 管理后的正常运行

<a id="managed-run"></a>

`managed-window` 会保留规则、当前目标和最新完整工具组，移除旧的 `g0`。它的事件可以概括为：`beforeUnits: 644`、`afterUnits: 239`、`requiredUnits: 239`、`keptGroups: ["g1","g4"]`、`removedGroups: ["g0"]`。随后 `model_requested.messages` 才会真正进入 adapter。adapter 在收到最新 assistant 调用及两个 tool result 后，按声明调用顺序拼接 `最新事实 A\n最新事实 B`，这就是返回的答案。答案来自实际消息内容；它没有读取 `expected`，也没有按案例 ID 查表。

这个案例的 `history` 中的工具结果是预先给定的材料，所以 CLI 这一次展示的是“管理并发送固定历史”，不是现场读取文件。实际文件读取仍由 loop 测试覆盖：测试创建临时目录，第一回合读取一个文件，第二回合用不同 ID 读取另一个文件，第三次模型请求从新结果回答；事件会显示最新工具组替换，旧组可以被裁剪。读者运行共享 CLI 时不要把 fixture 中预置的 tool message 说成这次命令刚刚执行的文件操作。

未管理模式是明确的对照实验。`manage: false` 仍验证历史、组织规则和目标，仍记录 `context_prepared`，但不裁剪、不因为预算拒绝；完整消息直接交给有预算限制的离线 adapter，由 adapter 产生 `model_error`。这不是提前实现后续的四种上下文策略，而是让同一个输入显示管理开关的可观察差异。

## 失败要读停止原因

<a id="context-failure"></a>

`required-overflow` 的规则和当前目标本身就超过预算。它的 `requests` 是 0，`result.reason` 是 `context_budget_exhausted`；规则、目标和最新工具依据不能被静默删掉。`invalid-orphan` 含孤立 tool result，`invalid-missing` 的 assistant 调用没有结果；二者都在模型派发前返回 `invalid_context_history`，并记录稳定的 `errorCode`，请求数也是 0。非法历史中的 NaN、Infinity 等不支持 JSON 值使用 `invalid_context_history` 和 `errorCode: "invalid_context_history"`；负预算、非安全整数或非字符串规则才是配置错误，使用 `errorCode: "invalid_context_config"`。

预算事件包含 `budget`、`beforeUnits`、`requiredUnits` 和 `mode`；非法历史事件只保留适用字段：`turn`、`reason`、`unit`、`mode`、`errorCode`。`beforeUnits` 与 `afterUnits` 都包含注入规则：前者是完整候选消息，后者是实际发送消息；未管理模式没有裁剪，所以两者相等。`LoopResult.error` 只在非法输入时保存稳定短码，预算停止不伪造额外错误。旧的 ch05/ch06 停止控制仍然有效，最大回合、工具预算、重复动作、取消和超时仍在上下文检查之后按原规则工作。

## 从源码回到请求边界

入口仍是 `runAgentLoop(adapter, workspace, prompt, options)`。初始化部分建立独立历史副本；每轮开始时再次验证完整 `messages`，调用 `prepareContext` 计算组、必要内容和裁剪结果，然后记录 `context_prepared`，再记录 `model_requested`。传给 adapter 的调用使用 `structuredClone(sentMessages)`，因此日志中的请求快照和 adapter 实际拿到的数组都不会成为审计历史的可变别名。

调用方把配置和当前目标实际接到入口：

```ts
const context: ContextConfig = {
  rules: fixture.rules,
  history: fixture.history,
  budget: fixture.budget,
  manage: fixture.managed,
}
const result = await runAgentLoop(adapter, { root }, fixture.goal, { context })
```

这里 `fixture.goal` 是 `prompt`，`context.history` 是完整历史，`rules` 会生成 system 消息，`budget` 控制估算上限，`manage` 选择裁剪或未管理对照。完整源码仍见 `ts/src/rein/loop.ts`。

```ts
const prepared = prepareContext(messages, context, contextGoalIndex!)
if (prepared.rejected) {
  events.push({ type: 'context_rejected', reason: 'context_budget_exhausted', ... })
  return finish(messages, events, 'failed', 'context_budget_exhausted')
}
events.push({ type: 'context_prepared', ...prepared, turn })
model = await raceControl(
  () => adapter.complete(structuredClone(prepared.messages), tools, control),
  signal,
  remaining,
)
```

上面是流程的缩写，省略字段展开和控制竞态处理；完整实现请看 `ts/src/rein/loop.ts`。`prepareContext` 从 `messages` 重新建立组，不把上一轮的裁剪数组当成新历史。`readonly Message[]` 让调用方不能正常地 `push` 到共享数组，但 adapter 仍可能通过运行时手段改变收到的对象，因此深复制是审计隔离的实际边界。

node --input-type=module -e 'import{readFileSync,writeFileSync}from"node:fs";const x=JSON.parse(readFileSync("fixtures/cases/ch07-context.json"));for(const b of[239,238]){const c=structuredClone(x.cases.find(c=>c.id==="managed-window"));c.budget=b;writeFileSync(process.argv[b===239?1:2],JSON.stringify({unit:x.unit,cases:[c]}))}' "$REIN_CH07_DIR/practice-07-2-239.json" "$REIN_CH07_DIR/practice-07-2-238.json"

### 练习 07-3：删除一个结果

用 Node 从原 fixture 生成单案例文件，并删除 `managed-window.history` 中与 `latest-a` 对应的 tool message：

```bash
node --input-type=module -e 'import{readFileSync,writeFileSync}from"node:fs";const x=JSON.parse(readFileSync("fixtures/cases/ch07-context.json"));const c=x.cases.find(c=>c.id==="managed-window");c.history=c.history.filter(m=>!(m.role==="tool"&&m.toolCallId==="latest-a"));writeFileSync(process.argv[1],JSON.stringify({unit:x.unit,cases:[c]}))' "$REIN_CH07_DIR/practice-07-3.json"

```

预期该案例不进入 adapter，`result.reason` 为 `invalid_context_history`，`requests` 为 0。缺失结果不能被当成空字符串，也不能让模型“猜”出答案。若只删除 `latest-b`，同样应该失败；一个多调用回合必须完整保留或整体拒绝。

Rust 版本使用完全相同的输入和语义，命令是：

```bash
cargo run --quiet --manifest-path rust/Cargo.toml --example ch07_context -- "$REIN_CH07_DIR/practice-07-1.json"
```

两种语言的 `estimated-bytes-v1` 结果、组 ID、停止原因和动态答案应一致。离线 adapter 的一致性不等于两个真实模型服务的回答能力一致；服务 token、网络延迟和供应商上下文窗口仍需另行测量。本章只证明本地合同在给定输入上的可观察行为。

## 把一次裁剪手算出来

为了避免把预算当成神秘的模型数值，可以拿 `multi-tool-boundary` 做一次手算。它的完整候选上下文为 382，规则消息和当前目标先进入必要集合；最新的多调用组从 `g5` 开始，目标组是 `g8`。在预算 220 下，最旧的 `g0` 与 `g1` 先被逐组考虑。`g1` 含一个 assistant 声明和两个结果，不能只删除其中一个结果；删除完整组后，`g4`、`g5`、`g8` 的保留组合为 219，刚好不超过预算。事件中的 `keptGroups` 是按完整历史位置升序排列的，`removedGroups` 也是如此。这个过程没有重新排列消息，模型仍按历史顺序看到保留下来的内容。

这里的 219 与服务端 token 没有换算关系。一个供应商可能对中文、工具 schema 或消息角色使用不同 tokenizer；另一个供应商还可能把系统提示、响应格式和安全字段加入上下文。本地单位的价值在于它对两个离线实现给出同一个边界：同一输入、同一规则和同一预算会得到同一保留组。需要真实服务容量时，应把服务返回的 token usage 另行记录，不能用本章的 219 冒充线上用量。

输入验证也属于上下文构造的一部分。程序先确认每条消息的 role、content 和可选字段，再确认 assistant 调用与 tool result 的邻接关系。多调用结果可以是 `latest-b` 后 `latest-a`，因为程序按 ID 配对；但它们必须连续位于声明之后，不能在中间插入另一个 user 消息。调用 ID 在完整历史中不能复用，即便新一轮使用了不同的工具参数也不允许偷换关联。JSON 对象键的排列不影响估算和动作身份，数组顺序则保留，因为数组常常表达调用顺序。

在 TypeScript 测试中，临时目录的文件由 `writeFile` 写入，`dispatchReadonly` 真正读取它们。第一回合返回 `round-a`，第二回合返回 `round-b`，第三回合只从最后一个 tool message 生成答案；因此这项测试与 fixture 的预置历史实验不同。测试还验证第三轮发送的必要组 ID 已变化，旧组出现在 `removedGroups`，以及新文件内容确实成为答案。测试是代码的回归证据，读者自己的 CLI 运行仍应查看本次输出中的 `answer`、`requests` 和事件，而不是把测试输出当作命令已经做过的文件读取。

如果看到 `model_error`，先区分两层：未管理案例是 adapter 主动发现 `E(messages)>budget` 后抛错；如果是网络适配器或响应解析失败，则是另一种模型错误。`context_budget_exhausted` 说明循环在调用 adapter 以前就发现必要内容放不下；`invalid_context_history` 说明输入结构不能代表合法对话。三者的 `requests` 和事件位置不同，修复方法也不同。不要把提高 `maxTurns`、重复发送或删掉历史中的目标当成上下文管理。

从实现角度看，规则注入、历史保存和请求发送是三个不同的边界。规则数组可以由配置拥有，历史数组由循环拥有，adapter 只拥有一次请求的副本。这样的所有权划分让故障诊断有明确位置：规则错误属于配置校验，历史错误属于输入校验，预算错误属于构造阶段，服务拒绝则属于 adapter。后续增加摘要或检索策略时，也应保持这条边界，先产生可审计的待发消息，再交给同一个模型请求入口。

你也可以把事件当作一次运行的解释器：先看 `context_prepared` 知道删了哪些组，再看 `model_requested` 确认实际发送了哪些消息，最后看 `model_received`、`tool_result` 和 `stopped` 判断行为是否闭合。这样的阅读顺序比只看最后一句答案更可靠，因为答案可能恰好正确，却没有使用最新依据。对预算和历史的判断都应回到这些可观察字段。
这也是排查“看起来成功”的最短路径。

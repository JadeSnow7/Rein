# 16 批准、应用与修改后验证

**状态：已有离线集成示例，逐章衔接与实机验收待完成｜永久免费 · Apache-2.0**

## 进入这一章

第 15 章留下了一份候选和原文件摘要。本章把本地调用者的一次批准连接到工具派发：先检查候选和基线，再让 Node 宿主执行，最后由 Rust core 核对新状态。产物包含批准对象、实际写入回执和独立的任务验证结论。

候选差异通过审查后，才能获得一次具体批准。批准针对的是这个候选和这个文件版本，不是一张允许以后随意修改的通行证。

## 批准来自调用者

本地调用者审查差异后，通过core批准接口产生绑定记录。模型参数不能自称已批准，也不能将以前的批准挪给另一份候选。core在派发前再次核对候选摘要与当前基线；宿主应用时也检查路径和基线。

apply_patch通过09的通用信封执行，实际能力声明只有在处理器已经注册时才包含它。教学实现只替换已有普通文件，不跟随符号链接。多个补丁串行应用，每次读取实际当前基线；先前的修改可能使下一个候选失效。

## 一次修改经过哪些检查

1. 读取实际文件与依据，生成候选并展示差异。
2. 调用者决定是否批准这份具体候选；拒绝就停止，不写入。
3. Rust 核对批准与文件基线，不匹配则停止派发。
4. Node 宿主再次核对并应用，Rust 检查回执与实际磁盘状态。
5. 写入已确认后运行声明的验证规则；已知验证失败才进入有限修复。

任一步出现无法确定是否已发生的副作用，都停止并交人工核查。不能把未知写入当成一次普通失败再重复执行。

批准来自调用者。即使候选生成器输出了“用户已同意”，这段文本也不能替代批准记录。宿主拥有文件操作能力，但每次写入仍须经过 core 的派发检查。

## 先确认写入，再验证任务

工具返回新文件版本后，core重新核对磁盘状态，然后运行13的验收规则。写入成功和任务验证通过分别记录。如果进程在写入后断连，不能因为没收到成功消息就自动再写一次；该动作保留结果未知，交由人工核查。

验收使用临时工作区：无批准不能写；不同候选不能复用批准；文件改变后旧批准失效；批准的精确候选能应用并验证新状态；无须修改任务不产生写入。

## 检查一次批准究竟批准了什么

假设原文件是版本 H0，候选 A 把 `start` 改为 `dev`。批准记录与 A 的路径、H0 和替换内容绑定。模型随后提交候选 B，即使也声称“已批准”，core 仍应在派发前拒绝；B 没有对应的本地批准记录。

如果调用者批准 A 后，编辑器把原文件变成 H1，A 也不能直接应用。这里不是再次询问同一项授权，而是原来批准的执行条件已经变化。重新读取文件、生成候选并展示差异，才能形成新的具体批准。

宿主返回写入成功后，core 读取磁盘并核对新摘要。验证器再检查新内容是否满足任务规则。两步结论分别保存：可能写入成功而验证失败，也可能文件已经变化但回执丢失。后者保留“结果未知”，不能自动重放。

## 跑通离线集成示例

下面的命令从仓库根目录执行，创建一份新的受控夹具。`--approve-demo` 明确允许示例调用者批准这一份临时文档候选；去掉它，程序会展示差异并等待你输入 `y`。生成器只是根据实际 `package.json` 中唯一的脚本声明改写文档命令，这里不调用模型。

```sh
REIN_LESSON_TMP=$(cd "${TMPDIR:-/tmp}" && pwd -P)
node scripts/maintenance-fixture.mjs command-1 "$REIN_LESSON_TMP/rein-approved-lesson"
CARGO_TARGET_DIR="$REIN_LESSON_TMP/rein-v2-cargo-target" cargo run --quiet --locked --manifest-path rust/Cargo.toml --example document_maintenance -- --workspace "$REIN_LESSON_TMP/rein-approved-lesson" --target README.md --approve-demo
```

运行后打开临时目录中的 README：原来的 `npm run start` 应变成 `npm run dev`。报告的 `mode` 是 `offline_fixture`，`report.stop_reason` 是 `Completed`。正常首次成功需要四次宿主调用：读取文档、读取清单、应用补丁、运行验证。每条记录中的 `dispatched`、`reaped` 与退出状态分别说明是否真正派发、是否回收和如何退出。

如果再次运行同一条 `cargo run`，文档已经符合声明，生成器不再提供补丁。会话仍读取实际输入并运行验证，不能把“没有生成候选”直接当作任务成功。

这是一条可运行的集成演示。它使用当前实现，不替代本章从前驱快照开始的跟做验收；章节快照尚未冻结时，仍保留未验收状态。模型、token、成本及模型延迟字段为 `null`，不能把离线执行时间算作模型效果。

## 提示词示例

```text
请展示候选差异，等待本地批准接口确认该候选及文件基线。
派发和应用前都重新核对，变化后停止并重新生成候选。
应用后验证实际新文件；断连导致结果未知时不要自动重放。
```

“本地批准接口”标明授权来源；“派发和应用前”覆盖基线变化；“不要自动重放”保护未知副作用。**试用状态：未试用。** 使用前请阅读[《提示词示例使用说明》](../prompt-examples.md)。

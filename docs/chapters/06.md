# 06 循环控制

本页保留旧 TypeScript 控制循环，作为可恢复的历史对照。当前主线由 [Rust core 版](./06-rust.md)承载；跨进程扩展的实际操作见同章 [06 Plugin](./06-plugin.md)。两者不是 TS/Rust 平行正文：Rust 决定循环状态，Node 只运行受协议约束的插件。

上一章的循环已经能搜索、读取，再把真实文件内容交给下一轮模型。它还有一个容易被忽略的事实：模型“还能继续调用”不等于程序“应该继续调用”。一个运行可能被模型轮数、工具派发数、相同动作、外部取消或整体截止时间中的任一条件截断。本章把这些条件放到同一个可观察循环里，读者可以从事件和消息判断到底执行了什么。

本文按携带的 `rein-ch06.tar.gz` 阅读。它是文件树快照，不是 Git 提交或标签；历史快照可按需按[阅读材料 2](/readings/02.html)恢复；它不是当前主线前置。下面命令均从当前 workspace 或解包后的书根运行。先准备一个自己拥有的绝对工作区：

```bash
export REIN_CH06_DIR="$(mktemp -d)"
printf 'marker: ch06 alpha\n' > "$REIN_CH06_DIR/README.md"
printf 'marker: ch06 beta\n' > "$REIN_CH06_DIR/guide.md"
npm ci
```

## 从一个正常任务进入循环

<a id="loop-entry"></a>

先跑默认场景：

```bash
npm run ch06:offline --workspace ts -- normal "$REIN_CH06_DIR"
```

这是离线回放适配器，不会发网络请求。它在第一次模型回合请求 `search_files`，循环真实搜索工作区；第二次模型回合看到搜索结果后，返回两个 `read_file` 调用；两个调用都完成后，第三次模型回合才回答。输出中的关键事实是 `requests: 3`、三个 `tool_result`，以及 `answer: "完成：marker: ch06 alpha | marker: ch06 beta"`。这三个模型请求不是把答案预写在脚本里：第二、三回合都根据已经进入 `messages` 的工具消息决定下一步。

为确认输入确实参与结果，改写同一工作区再跑一次：

```bash
printf 'marker: ch06 changed\n' > "$REIN_CH06_DIR/README.md"
npm run ch06:offline --workspace ts -- normal "$REIN_CH06_DIR"
```

答案中 README 的片段随文件改变，而 `guide.md` 仍来自第二次真实读取。若把路径写成相对路径，npm workspace 切换 cwd 后就可能读错位置，所以跟做时始终传 `mktemp` 生成的绝对路径。

## 模型回合和工具预算不是一件事

<a id="budget-and-stop"></a>

`maxTurns` 限制进入模型适配器的请求数；`maxToolCalls` 限制真正进入只读分派器的调用数。一次模型回合可以返回多个工具调用，因此它们必须逐个检查：

```bash
npm run ch06:offline --workspace ts -- budget "$REIN_CH06_DIR"
npm run ch06:offline --workspace ts -- tool-zero "$REIN_CH06_DIR"
npm run ch06:offline --workspace ts -- zero "$REIN_CH06_DIR"
```

`budget` 的模型只返回 `one` 和 `two` 两个读取调用，预算为 1。输出有 `tool_result`（`one`），随后 `action_skipped`（`two`，原因 `tool_budget_exhausted`），最后是 `stopped`。`tool-zero` 的预算为 0，两个调用都跳过，但仍先发生一次模型请求。`zero` 把 `maxTurns` 设为 0，连模型也不请求，直接得到 `reason: "max_turns"`。三种场景都以 CLI 退出码 0 打印 JSON；这只表示示例程序正常报告了结果，不能把 `state: "failed"` 解释成业务任务已完成。

每一次真实工具结果都会同时出现在 `events` 的 `tool_result` 和 `messages` 的 `role: "tool"` 消息里。被跳过的调用只有 `action_skipped`，没有伪造的工具输出，也不会把不存在的 tool message 送进下一轮。

## 同义动作要按身份去重

<a id="duplicate-action"></a>

调用 ID 是消息协议中的关联字段，不是动作身份。运行 `duplicate`：

```bash
npm run ch06:offline --workspace ts -- duplicate "$REIN_CH06_DIR"
```

两轮模型请求的 ID 是 `duplicate-1`、`duplicate-2`，但它们都请求读取 `README.md`。`duplicateLimit: 1` 允许第一次真实派发，第二次写入 `action_skipped` 并以 `duplicate_action` 停止。循环用工具名和规范化参数组成身份：

```ts
const identity = `${call.name}\0${canonicalJson(call.arguments)}`
```

`canonicalJson` 对对象键排序、递归规范化值；因此同一对象即使键顺序不同也相等，数组顺序则保留，因为数组顺序可能就是参数语义。`duplicateLimit` 是允许同一身份进入分派器的次数，不是允许模型生成该动作的次数。它解决的是同一读取动作反复消耗资源的问题，而不是判断答案正确性。

## 取消发生在不同生命周期位置

<a id="cancellation"></a>

下面四个场景分别把取消放在请求前、请求等待中、模型返回的同一时刻，以及同一回合的两个工具之间：

```bash
npm run ch06:offline --workspace ts -- cancel-before "$REIN_CH06_DIR"
npm run ch06:offline --workspace ts -- cancel "$REIN_CH06_DIR"
npm run ch06:offline --workspace ts -- cancel-at-return "$REIN_CH06_DIR"
npm run ch06:offline --workspace ts -- cancel-between-tools "$REIN_CH06_DIR"
```

`cancel-before` 的 `requests` 为 0，因为循环在发模型请求前检查信号。`cancel` 的适配器故意等待 120ms，而 20ms 时触发 `AbortController`；`raceControl` 让循环立即以 `cancelled` 返回，迟到的 Promise 不能再添加答案。`cancel-at-return` 在适配器返回“迟到的最终答案”前设置 signal，循环在模型返回后再次检查，所以同样没有 `answer`。这不是撤回服务器已经处理的请求；它只是隔离本地迟到结果，并拒绝把它继续送入消息历史。

`cancel-between-tools` 的第一项 `one` 已有真实 `tool_result`。`onToolResult` 随后取消，第二项 `two` 只记录为 `action_skipped: cancelled`。已经完成的结果必须保留，因为它确实发生过；尚未开始的调用不能伪造输出。

<a id="deadline"></a>

整体截止时间覆盖等待模型和同一回合的工具间隔：

```bash
npm run ch06:offline --workspace ts -- timeout "$REIN_CH06_DIR"
```

这里 `timeoutMs: 30`，而回放适配器等待 120ms，结果为 `timeout`。它是整个循环的时间预算，不等于 HTTP 适配器可能设置的单次请求超时；本地延时只是控制实验，不能推出模型服务的性能。

## 空搜索与模型错误

新建一个不含 marker 的目录，观察正常错误路径：

```bash
export REIN_CH06_EMPTY="$(mktemp -d)"
printf 'unrelated\n' > "$REIN_CH06_EMPTY/other.txt"
npm run ch06:offline --workspace ts -- normal "$REIN_CH06_EMPTY"
```

搜索工具返回空内容后，回放适配器抛出 `no files match marker: ch06`；循环将它报告为 `state: "failed"`、`reason: "model_error"`，没有 `answer`。这说明 CLI 能打印失败结果并退出 0，不代表业务成功。模型适配、传输或响应解析异常属于 `model_error`；工具失败通常以结构化反馈回到模型，空的最终文本则是 `empty_final`，不能把它们混为一种原因。

## 走读实现：检查点必须靠近副作用

`ts/src/rein/loop.ts` 的选项和派发边界实际是这样连接的：

```ts
const maxTurns = options.maxTurns ?? 32
const maxToolCalls = options.maxToolCalls ?? Number.POSITIVE_INFINITY
const duplicateLimit = options.duplicateLimit ?? Number.POSITIVE_INFINITY
const controlReason = (): StopReason | undefined => {
  if (options.signal?.aborted) return 'cancelled'
  if (deadline !== undefined && Date.now() >= deadline) return 'timeout'
  return undefined
}
```

每轮进入模型前、返回后和每个工具前都调用 `controlReason`。通过预算和重复检查才会递增 `toolStarted` 并执行 `dispatchReadonly`（以下是相关节选，省略了为剩余调用生成 `action_skipped` 事件的循环）：

```ts
const identity = `${call.name}\0${canonicalJson(call.arguments)}`
const occurrences = (seen.get(identity) ?? 0) + 1
if (occurrences > duplicateLimit) {
  // 实际实现会为当前及剩余调用逐一追加 action_skipped
  return finish(messages, events, 'failed', 'duplicate_action')
}
seen.set(identity, occurrences)
toolStarted++
const result = await dispatchReadonly(call, workspace)
events.push({ type: 'tool_result', turn, call: structuredClone(call), toolCallId: call.id, result })
messages.push({ role: 'tool', toolCallId: result.toolCallId, content: result.ok ? result.output ?? '' : JSON.stringify({ ok: false, error: result.error }) })
options.onToolResult?.(call, result)
```

`raceControl` 在需要控制时注册 abort listener 和 deadline timer，并在 `finally` 中清理；它只让本地循环先结束。外部 signal 由调用方传入 adapter，再由实际 transport 传给 `fetch` 的 `signal`；不合作的适配器即使收到 signal，也可能留下迟到 Promise，因此循环必须隔离其结果。它不撤回服务器已经处理的请求。

模型消息写入历史并产生 `model_received` 后，循环逐项检查工具预算、控制原因和规范化重复身份。`onToolResult` 是本地调用方提供的任意 trusted hook；本例用它在结果后取消，但它不是权限隔离，也不保证不能写文件或排队工具。权限约束要到后续章节再建立。`finish` 总是追加最终 `stopped` 事件，所以读者可以用事件而不是退出码判断停止原因。

工具 schema 中的 `additionalProperties: false` 只是发给模型的声明；真正的路径安全和文件存在性仍由上一章的 `dispatchReadonly` 检查。结构化事件也不是持久恢复系统，它只是保存本次运行看得见的输入、调用和结果。

## 练习

<a id="practice-06-1"></a>

### 练习 06-1：把重复阈值改成 2

在快照的 `ts/examples/ch06-loop.ts` 中找到传给 `runAgentLoop` 的 `duplicateLimit`，将 `mode === 'duplicate' ? 1 : undefined` 改为 `mode === 'duplicate' ? 2 : undefined`，再运行：

```bash
npm run ch06:offline --workspace ts -- duplicate "$REIN_CH06_DIR"
```

预期是两次真实 `tool_result`，第三次才被拦截；因为示例每轮会改变调用 ID，但参数仍是 README。改回 1 后应恢复为一次真实读取。`maxTurns` 默认仍为 4，不会先挡住这个实验。检查 `events` 的 `tool_result` 数量和停止原因，不要只看进程退出码。

<a id="practice-06-2"></a>

### 练习 06-2：观察取消时机

保持示例模型延迟 120ms，分别运行四种模式：

```bash
for mode in cancel-before cancel cancel-at-return cancel-between-tools; do
  npm run ch06:offline --workspace ts -- "$mode" "$REIN_CH06_DIR"
done
```

实际计数应分别是：`cancel-before` 为 0 次模型/0 次工具，`cancel` 为 1/0，`cancel-at-return` 为 1/0，`cancel-between-tools` 为 1/1（第二个工具跳过）。每次都检查 `model_requested`、`model_received`、`tool_result`、`action_skipped` 和 `settledRequests`，不要用随机竞态推断结论。

<a id="practice-06-3"></a>

### 练习 06-3：允许同轮两个工具

在 `ts/examples/ch06-loop.ts` 的 `maxToolCalls` 分支，把 `budget` 的值从 1 改成 2，运行 `budget`。第一次模型回合返回的 `one`、`two` 都有真实结果；该回放下一回合仍返回工具调用，此时累计工具预算已满，所以第二次模型请求后两个调用都被跳过，预期 `requests: 2`、`tool_result` 为 2、`action_skipped` 为 2。把它改回 1 时，`two` 在第一次回合就只有 `action_skipped`，消息历史不应出现它的 `toolCallId`。这是工具预算的派发边界，不是模型回合预算；提高预算也不保证模型一定给出最终答案。

# 04 统一协议——隔离模型服务商差异

**状态：初稿，待审阅｜限时免费**

前三章，我们使用的均是 OpenAI 兼容的 API，如果我们想更换模型服务商，应该怎么办呢？结合第一章知识，我们可以修改 `baseURL`、API key 和模型名称。然而，如果模型服务商不提供 OpenAI 兼容的 API，那我们之前写的程序显然不能用了，因此，我们必须新增一层抽象——统一协议。

在前面的章节，我们已经了解怎么提交请求体，现在，要兼容不同格式的 API，只需要增加一个中间层，根据模型提供商和 API 格式的不同来构造对应的请求体即可。

本章对照 Chat Completions 与 Anthropic Messages 的非流式文本和工具响应子集，完成离线适配练习。本章不实现完整供应商客户端或流式处理，也不以这份离线练习证明真实服务已经接通。

## 1、先把两份工具请求放到一起

第 03 章收到的请求大致是下面这样。为了便于比较，这里只保留与本章有关的字段；两份数据都是手写示例。

```json
{
  "choices": [{
    "finish_reason": "tool_calls",
    "message": {
      "role": "assistant",
      "content": "我先读取笔记。",
      "tool_calls": [{
        "id": "call_note_1",
        "type": "function",
        "function": {
          "name": "read_file",
          "arguments": "{\"path\":\"note.txt\"}"
        }
      }]
    }
  }]
}
```

在 Anthropic Messages 中，同一个意图可以出现在 `content` 数组的工具内容块里。

```json
{
  "role": "assistant",
  "stop_reason": "tool_use",
  "content": [
    { "type": "text", "text": "我先读取笔记。" },
    {
      "type": "tool_use",
      "id": "call_note_1",
      "name": "read_file",
      "input": { "path": "note.txt" }
    }
  ]
}
```

两边都表达了调用编号、工具名称和参数，但结构不一样。Chat Completions 把参数放在 JSON 字符串中，Anthropic Messages 的 `input` 已经是一个对象。后者还把文本与工具请求放进同一个内容数组，可以按顺序出现。

这些字段可以分别从 [OpenAI 的工具调用说明](https://developers.openai.com/api/docs/guides/function-calling)与 [Anthropic 的工具调用说明](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)核对。本章只取这两个接口交汇的一小部分，其他内容块不能在未经处理的情况下直接套进示例。

如果继续让文件工具自己读取 `choices` 或 `content`，它很快就会掺入服务商判断。等到增加搜索工具，每个工具又要做一遍相同的判断。我们可以先在模型响应进入程序时完成转换，让工具只看到自己需要的名称和参数。

## 2、定义我们接下来真正需要的数据

回到 `ts/` 目录，新建 `ch04.ts`。把本章各段 TypeScript 代码按顺序写进这个文件；上面的两段 JSON 只用于对照，不需要另外保存。

```ts
export type ContentBlock = {
    kind: 'text';
    text: string;
} | {
    kind: 'tool_call';
    callId: string;
    name: string;
    arguments: Record<string, unknown>;
};
export type ToolResult = {
    callId: string;
    ok: true;
    value: unknown;
} | {
    callId: string;
    ok: false;
    error: {
        code: string;
        message: string;
    };
};
export type Normalized = {
    blocks: ContentBlock[];
    stopReason: 'end' | 'tool_use';
};
```

工具请求保留 `callId`、`name` 和 `arguments`，分别回答“这是哪次调用”“调用什么”“输入是什么”。这里暂时只知道参数是一个对象，具体到 `read_file` 是否允许这个路径，仍然要交给上一章的执行器判断。

我们把一轮回答表示为内容块数组，而不是提前收窄成一个文本字段。这样遇到文字说明和工具请求同时出现时，两者都能留下来。Anthropic 的内容块顺序直接保留；Chat Completions 本身把文本与调用分开，本章约定先放文本，再按 `tool_calls` 的顺序放调用，这不能用于还原服务没有提供的交错顺序。

`stopReason` 则说明这一轮为什么停下来。正常完成、等待执行工具与输出被截断，需要走向不同的处理方式。本练习遇到截断会直接报错，防止把半份参数交给工具执行；以后加入更完整的协议时，可以把这种失败扩展成显式状态。

这里的统一协议是模型服务商适配器内部的消息合同：它把 Chat Completions 与 Anthropic Messages 转成同一组内容块，供后续循环使用。第 06 章的 core/plugin stdio 协议属于另一条边界，负责 Rust core 与受控 TS 工具宿主之间的会话、调用身份、取消和证据回传；它不会替代本章的供应商格式适配。下一章从 [Rust core 的 05 章](/chapters/05-rust.html)继续，TS 工具仍作为生态扩展保留。

工具结果同样带着 `callId`。成功结果提供数据，失败结果提供错误。这份对应关系要穿过整个转换过程，不能在切换服务商时重新生成调用编号。

## 3、在适配器入口检查外部数据

接下来，我们写两个转换函数：一个接收 Chat Completions 响应，另一个接收 Anthropic Messages 响应。这样的函数通常叫适配器，它负责把接口的数据形状转换成程序内部使用的形状。

```ts
const object = (v: unknown, label: string): Record<string, unknown> => {
    if (typeof v !== 'object' || v === null || Array.isArray(v)) {
        throw new Error(`${label} 必须是对象`);
    }
    return v as Record<string, unknown>;
};
const args = (raw: unknown): Record<string, unknown> => {
    if (typeof raw !== 'string') {
        throw new Error('工具 arguments 必须是 JSON 字符串');
    }
    let value: unknown;
    try {
        value = JSON.parse(raw);
    }
    catch {
        throw new Error('工具 arguments 不是合法 JSON');
    }
    return object(value, '工具 arguments');
};
/** 教学子集：先保留文本，再按 tool_calls 的数组顺序保留调用。 */
export function fromChat(value: unknown): Normalized {
    const root = object(value, 'Chat response'), choices = root.choices;
    if (!Array.isArray(choices) || choices.length !== 1) {
        throw new Error('Chat response 缺少唯一 choices');
    }
    const choice = object(choices[0], 'choice'), message = object(choice.message, 'message');
    const blocks: ContentBlock[] = [];
    if (typeof message.content === 'string' && message.content) {
        blocks.push({ kind: 'text', text: message.content });
    }
    else if (message.content !== null && message.content !== undefined) {
        throw new Error('Chat content 必须是字符串或 null');
    }
    const calls = message.tool_calls;
    if (calls !== undefined) {
        if (!Array.isArray(calls) || calls.length === 0) {
            throw new Error('tool_calls 必须是非空数组');
        }
        for (const item of calls) {
            const c = object(item, 'tool call'), fn = object(c.function, 'function');
            if (c.type !== 'function' || typeof c.id !== 'string' || !c.id || typeof fn.name !== 'string' || !fn.name || typeof fn.arguments !== 'string') {
                throw new Error('工具调用字段无效');
            }
            if (blocks.some(b => b.kind === 'tool_call' && b.callId === c.id)) {
                throw new Error('重复 callId');
            }
            blocks.push({ kind: 'tool_call', callId: c.id, name: fn.name, arguments: args(fn.arguments) });
        }
    }
    if (!blocks.length) {
        throw new Error('响应没有文本或工具调用');
    }
    const stop = choice.finish_reason;
    if (stop !== 'stop' && stop !== 'tool_calls') {
        throw new Error('截断或未知 stop_reason');
    }
    if (stop === 'tool_calls' && calls === undefined) {
        throw new Error('tool_calls 结束却没有调用');
    }
    if (stop === 'stop' && calls !== undefined) {
        throw new Error('stop 与 tool_calls 不一致');
    }
    return { blocks, stopReason: stop === 'tool_calls' ? 'tool_use' : 'end' };
}
export function fromAnthropic(value: unknown): Normalized {
    const root = object(value, 'Anthropic response'), content = root.content;
    if (!Array.isArray(content)) {
        throw new Error('Anthropic content 必须是数组');
    }
    const blocks: ContentBlock[] = [];
    let hasToolUse = false;
    for (const item of content) {
        const b = object(item, 'content block');
        if (b.type === 'text' && typeof b.text === 'string' && b.text) {
            blocks.push({ kind: 'text', text: b.text });
        }
        else if (b.type === 'tool_use' && typeof b.id === 'string' && b.id && typeof b.name === 'string' && b.name) {
            if (blocks.some(x => x.kind === 'tool_call' && x.callId === b.id)) {
                throw new Error('重复 callId');
            }
            blocks.push({
                kind: 'tool_call', callId: b.id, name: b.name, arguments: object(b.input, 'tool input')
            });
            hasToolUse = true;
        }
        else
            throw new Error('未知或非法 content block');
    }
    if (!blocks.length) {
        throw new Error('响应没有文本或工具调用');
    }
    if (root.stop_reason !== 'end_turn' && root.stop_reason !== 'tool_use') {
        throw new Error('截断或未知 stop_reason');
    }
    if ((root.stop_reason === 'tool_use') !== hasToolUse) {
        throw new Error('stop_reason 与 tool_use 不一致');
    }
    return { blocks, stopReason: root.stop_reason === 'tool_use' ? 'tool_use' : 'end' };
}
```

函数的入口使用 `unknown`，因为我们接到的是程序外部的数据。即使 SDK 提供了 TypeScript 类型，网络返回的内容也不会因为一个类型声明就自动通过运行时检查。这里依次检查对象、数组、字符串和结束原因，再把确认过的字段放进内部结构。

这一步只检查协议层的信息。对于 `{"path":"../.env"}`，适配器可以确认它是一个参数对象，但能否读取这个路径，依然由工具执行器决定。否则我们每接入一家服务，都得重新实现一份文件权限逻辑。

代码也没有把未知内容块直接过滤掉。例如接收到一个尚未支持的块，悄悄删掉它可能会改变回答含义，甚至破坏后续回传所需的信息。本章选择明确报错，等到确实需要这类能力时再扩展协议和检查。重复调用编号也会被拒绝，否则后续收到结果时，我们无法确定它对应哪一项请求。

到这里，两份响应都可以转成同一种数据，文件工具也就不用知道响应来自哪家服务了。

## 4、结果回传也需要经过适配器

只有输入转换还不够。读完文件之后，程序内部拿到的是工具结果，服务商还在等待各自规定的消息格式。

在 Chat Completions 中，我们把结果写进 `role: 'tool'` 的消息，并填写 `tool_call_id`。在 Anthropic Messages 中，工具结果是下一条 `user` 消息里的 `tool_result` 内容块，使用 `tool_use_id` 指回原调用；失败时还可以设置 `is_error`。这里的 `user` 是接口的消息角色，不表示用户亲手输入了这段内容。具体回传约定见 [Anthropic 的工具调用处理文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)。

继续加入结果转换函数，通过 `provider` 选择目标格式。

```ts
export function encodeToolResult(result: ToolResult, provider: 'chat' | 'anthropic') {
    const body = result.ok ? { ok: true, value: result.value } : { ok: false, error: result.error };
    if (provider === 'chat') {
        return { role: 'tool', tool_call_id: result.callId, content: JSON.stringify(body) };
    }
    return {
        role: 'user', content: [
            {
                type: 'tool_result', tool_use_id: result.callId, is_error: !result.ok, content: JSON.stringify(body)
            }
        ]
    };
}
```

两边都通过 JSON 文本保留我们内部的成功或失败信息。Anthropic 额外带上它自己的错误标记，Chat Completions 则由结果正文中的 `ok` 表达业务错误。

这里生成的只是工具结果消息。真正发出下一次请求时，还必须保留原来的对话与 assistant 工具请求；Anthropic 的原始 assistant 内容块也应留存，不能用这份精简结构去覆盖完整历史。第 03 章已经演示了保留请求再追加结果的顺序，适配器不会替我们完成对话管理。

## 5、用同一组输入检查转换是否一致

现在我们先不请求任何模型，直接使用开头的两份数据。这样一旦发现结果不一致，可以定位到自己的转换代码，不会把模型生成内容的变化混在里面。

```ts
export const samples = {
    chat: {
        choices: [
            {
                finish_reason: 'tool_calls', message: {
                    content: '我先读取笔记。', tool_calls: [
                        {
                            id: 'call_note_1', type: 'function', function: { name: 'read_file', arguments: '{"path":"note.txt"}' }
                        }
                    ]
                }
            }
        ]
    },
    anthropic: {
        stop_reason: 'tool_use', content: [
            { type: 'text', text: '我先读取笔记。' },
            {
                type: 'tool_use', id: 'call_note_1', name: 'read_file', input: { path: 'note.txt' }
            }
        ]
    },
};
import { pathToFileURL } from 'node:url';
import assert from 'node:assert/strict';
if (process.argv[1] && import.meta.url === pathToFileURL(process.argv[1]).href) {
    const chat = fromChat(samples.chat);
    const anthropic = fromAnthropic(samples.anthropic);
    assert.deepEqual(chat, anthropic);
    const failure: ToolResult = {
        callId: 'call_note_1',
        ok: false,
        error: { code: 'not_found', message: '文件不存在。' },
    };
    console.log(JSON.stringify({ chat, anthropic }, null, 2));
    console.log(JSON.stringify(encodeToolResult({ callId: 'call_note_1', ok: true, value: { project: 'Rein' } }, 'chat'), null, 2));
    console.log(JSON.stringify(encodeToolResult(failure, 'chat'), null, 2));
    console.log(JSON.stringify(encodeToolResult({ callId: 'call_note_1', ok: true, value: { project: 'Rein' } }, 'anthropic'), null, 2));
    console.log(JSON.stringify(encodeToolResult(failure, 'anthropic'), null, 2));
}
```

在 `ts/` 目录执行。

```bash
node --import tsx ch04.ts
```

如果两份内部结果不一致，`assert.deepEqual` 会抛出错误，程序以失败退出。检查通过时，终端会打印两份相同的内部结构，再打印成功与失败结果在两个接口中的四份消息。这里的成功数据也是手写样例，没有在本章重新读取文件。

这段检查比较的是完整的内部结果，而不只是工具名称。调用编号、参数、文本和结束原因都要相同。示例特意给两份手写输入用了同一个编号，方便做直接比较；真实服务生成的编号不必相等，各自的适配器应原样保留它们。

接着对照同一种结果在两个接口中的消息：外层格式可以不同，但它们必须指向原来的 `call_note_1`，而且保留成功或失败的信息。如果转换之后编号丢了，或者错误变成普通成功文本，这个适配器就还不能交给下一章使用。

你还可以在示例中做几次有针对性的修改。

| 修改输入 | 应当观察到什么 |
| --- | --- |
| 把 Chat Completions 的 `arguments` 改成未闭合的 JSON | 转换报错，不生成可执行调用 |
| 给 Anthropic 增加一个本章未支持的内容块 | 转换报错，不悄悄丢掉内容 |
| 把两次调用的编号写成相同值 | 转换报错，避免结果归属不清 |
| 把结束原因改成 `length` 或 `max_tokens` | 转换报错，不把截断输出视为完成 |
| 将失败结果交给两个结果转换函数 | 原编号与失败信息都得到保留 |

本稿对上述关键分支做了离线检查。这证明的是所选数据格式在本练习中的转换行为，不能据此宣称已经接通两家服务，也没有验证它们所有可能的响应类型。

## 6、让两种语言遵守同一份约定

如果后面还要写 Rust 版，仅仅把 TypeScript 的类型逐个翻译一遍，并不能保证两边行为一致。比如一个版本遇到未知内容块报错，另一个版本直接跳过，两边即使都能编译，也已经在处理不同的任务。

我们需要把共同约定落到可比较的输入和结果上。对于本章，同一份工具调用应保留编号与参数；失败结果不能变成成功；非法 JSON、重复编号和未支持的内容块，都应得到明确失败。这样的约定可以使用共享 JSON 样例表达，再由 TypeScript 和 Rust 分别读取、检查。

未来整合主线时，可以把这些样例整理进 `contracts/`，并为它们标明协议版本。如果改变内容块含义或失败处理方式，就需要同时检查两种语言的实现与样例。本稿尚未把这些约定写成正式共享合同，也没有实现 Rust 适配器；这里先明确它们要对齐的行为。

现在，我们可以画出下一章将要依赖的边界。

```text
服务商响应 → 适配器 → 内部工具请求 → 工具执行器
                                      ↓
下一次请求 ← 服务商结果消息 ← 适配器 ← 内部工具结果
```

文件工具仍然负责检查路径和读取文本，适配器负责理解服务商格式，后面的循环负责决定何时继续调用模型。沿着这个边界，我们会在[第 05 章 Rust core](./05-rust.md)把一次“请求工具—执行—回答”接成能够持续推进任务的 Agent Loop。

# 08 上下文管理方法：同一份资料的四种取法

长历史由四个对象共同管理：规则说明约束，目标保存任务与问题，完整历史保留交互，发送上下文决定本次回答实际看到的消息；[第07章](./07-rust.md) 对这四个对象有完整回顾。本章把问题落到同一份六文档资料和四个任务上，观察哪些消息真正进入回答器，以及证据缺失时系统如何停在可解释的结果上。继续把完整历史原样塞给回答器，会让消息变长，却无法说明哪些资料真正有用；裁剪之后，回答又可能看似完整而没有依据。

以下命令都从 Rein 仓库根目录执行，并假定已经完成 `npm ci`、拥有 Node.js、Rust/Cargo 和本地 `node_modules`。先确认位置：

```bash
test -f package.json && test -d node_modules && test -f rust/Cargo.toml
```

入口仍是 Rust core 的 `context_methods`：Rust 负责方法选择、预算和证据采纳，通过既有 `StdioExecutor` 启动真实 Node `read_file` 宿主。TypeScript 只承担领域文件工具，不复制 Harness，也不扩展 M1 协议。独立进程提供进程边界，不自动成为安全沙箱。回答器是离线共同回答器，只看最终 `messages`，不会读取 `expectedFacts`，不会调用真实模型服务。

## 从运行实验开始

```bash
export CARGO_TARGET_DIR="${CARGO_TARGET_DIR:-$PWD/rust/target}"

```

输出固定为四任务乘四方法的16行。每行包含 messages、读取操作、估算单位、来源、离线回答、质量和 StdioExecutor 的真实进程记录。估算是 UTF-8 消息单位，不是服务 token；本章不调用真实模型服务。可以用下面的断言检查默认根对象和行数：


预期短输出为 `rows=16 unit=estimated-bytes-v1 serviceTokens=null`。这只证明默认数据的离线输出形状，不证明真实模型质量、网络延迟或线上吞吐量。

<a id="fixed-dataset"></a>

## 固定资料与回答边界

索引只保存 `unit`、预算和文档的 `id/path/title/keywords/order`，事实只在六份 Markdown 正文。四个任务分别询问早期传输方式与协议、最新发布检查命令、批准与失败处理、资料未提供的生产吞吐量。每条规则是独立 system message，问题是普通 `user` message；读取结果也作为普通 `user` message，但必须带精确前缀 `[来源:docId]\n`。回答器只看 messages，不能读取 expectedFacts，也不能由 taskId 选择答案。

`quality` 是正确且在来源消息中出现的必需事实数除以必需事实总数，范围 0..1：两个事实找到一个就是 0.5，两个都是 1，没有依据就是 0。task-04 没有必需事实，claims 为空且 `insufficientEvidence=true` 时，unknown 才是 1。没有依据的 claims 必须进入 `unsupportedClaims`。`selectedSources` 是最终进入 messages 的去重来源。

<a id="four-methods"></a>

## 四种方法

### on-demand：索引命中后才读取

输入是 question、rules 和 index 元数据。Rust 先检查 title/keywords，再对命中的文档发 `read_file`；未命中文档没有 read operation。返回正文被包装成 `[来源:doc-01]` 的 user message，task-01 因此能看到 `传输方式：JSON Lines` 与 `协议版本：rein-extension/0.1`。关键词只导航，不是事实；索引写着“协议”并不能单独生成 claim。

### window：按 paragraph 保持最近后缀

输入仍是按 order 读出的正文段落。Rust 从最近的完整 paragraph 后缀开始尝试放入 messages，预算不够就丢最早片段；rules/question 永不裁剪，来源片段可以整段消失。保留的 paragraph 按 `(order, paragraphIndex)` 恢复原序，调用历史仍留在 operations/callRecords。若 task-03 的两个来源中只保留批准段落，回答仍成功但只能有一个 claim，quality 就是 0.5；若 task-01 的两个事实在同一段中而该段被整段删除，quality 才会是 0。

### summary：压缩背景，保留事实行

输入是实际读取的段落，操作是筛出含 `字段：值` 且非背景的行。`doc-01` 的背景自然段被丢弃，两个事实行和来源前缀仍进入 user message，所以 rawAnswer 仍能引用 JSON Lines。修改正文为 HTTP 后，summary 读取到新行就会使用 HTTP；这是规则式离线提取，不是 LLM 摘要。

### retrieval：正文段落评分后选取

输入是完整正文段落和 question 词：ASCII 词按完整词匹配，非 ASCII 文本使用连续 2..8 字符 n-gram。Rust 为每个候选 paragraph 记录 `type=retrieval`、`score`、`source`、`order`、`paragraphIndex`、`text`、`selected`，按 score 再按 order/index 稳定排序。task-03 的批准规则与失败处理段落有匹配词，因而可进入 messages；改成无匹配词后候选仍可被记录为 0 分，但 selected 全为 false，最终来源为空。score 是选择信号，不是答案或 task ID 查表，也不是嵌入检索能力。

实现定位可以从 `rust/src/rein/context_methods.rs` 的 `base`、`run_one_with_executor`、`paragraphs` 和 `answer` 开始：先组装 rules/question，预算通过后读取正文，再给段落保存来源/order/index，最后只把最终 messages 交给回答器。预算检查的关键形状是：

```rust
let mut messages = base(&task_view);
if budget == 0 || estimated_units(&messages) > budget {
    return empty(task, strategy, budget, "context_budget_exhausted", start);
}
// read_file -> paragraphs -> strategy selection -> sourced user messages
let answer = answer(&messages);
```

因此权威预算检查发生在文档读取之前；裁剪、评分和 call record 仍以该文件的完整实现为准。

你可以把每行的消息构建想成三步：先放入两条独立 rule 的 `system` 消息，再放入 question 的普通 `user` 消息；每次真实读取通过 StdioExecutor 产生一条 operations 与一条 callRecords，最终只把带 `[来源:docId]` 的正文作为普通 `user` message 放入回答上下文；方法在这个阶段筛选、裁剪或改写正文消息；最后把剩下的 messages 原样交给同一个回答器。于是 task-01 的 `doc-01` 事实若被保留，rawAnswer 会出现 `JSON Lines` 和 `rein-extension/0.1`；window 若裁掉其中一段，claims 只能覆盖仍在消息中的事实；summary 去掉背景段仍能保留字段行；retrieval 即使给 `doc-03` 较高分，也必须从实际段落找到字段，不能从分数推导答案。真实调用历史只看 operations/callRecords，不能根据 message role 猜工具调用。

## 比较结果

任务一验证传输方式与协议版本，任务二验证发布检查命令，任务三跨批准与失败文档，任务四询问资料没有给出的生产吞吐量。每行字段包括 `taskId,strategy,question,budget,status,messages,estimatedUnits,selectedSources,operations,answer,quality,unsupportedClaims,elapsedMs,serviceTokens,modelCalls,callRecords`。`serviceTokens` 始终为 null；`elapsedMs` 是由单调时钟测得的本地端到端阶段耗时，包含 Node 宿主进程启动、文件 I/O、退出回收以及构造、回答和评分，不包含模型服务请求。budget 为0在文档 I/O 前返回 `context_budget_exhausted`，modelCalls、operations、callRecords 都是0，answer 为 null，estimatedUnits 为0，quality 为 null。

可用下列命令生成真实短表，不手写结果：

```bash
export CARGO_TARGET_DIR="${CARGO_TARGET_DIR:-$PWD/rust/target}"
npm run --silent ch08:compare | node -e 'let x="";process.stdin.on("data",d=>x+=d).on("end",()=>{const o=JSON.parse(x); for(const r of o.results) console.log([r.taskId,r.strategy,r.status,r.quality,r.estimatedUnits,r.selectedSources.join(","),r.answer?.claims.length??"null",r.modelCalls].join("\t"))})'
```

比较时固定 data-root、任务、预算和版本，只改变 strategy。`modelCalls:1` 是一次离线回答器调用，不是供应商模型调用。

<a id="method-failure"></a>

## 故障是可观察终态

缺失文件、越界路径、协议响应异常和 Node 宿主异常返回 `error`、answer 为 null、modelCalls 为0，并保留真实 callRecords。记录中的 dispatched、reaped、child_pid、exit_code 和 terminal 来自进程生命周期，不能用 passed 字段或策略名替代行为。重复 ID/order、非法 path 或非法 CLI 则非零退出，不能折叠成普通结果行。

预算和故障的最小检查：

```bash
export CARGO_TARGET_DIR="${CARGO_TARGET_DIR:-$PWD/rust/target}"
BAD_ROOT="$(mktemp -d /tmp/rein-ch08-bad-metadata.XXXXXX)"
cp -R fixtures/ch08-context/. "$BAD_ROOT/"
node -e 'const fs=require("fs"); const p=process.argv[1]+"/index.json"; const x=JSON.parse(fs.readFileSync(p)); x.documents[1].order=x.documents[0].order; fs.writeFileSync(p,JSON.stringify(x));' "$BAD_ROOT"
if npm run --silent ch08:compare -- --data-root "$BAD_ROOT" >"$BAD_ROOT/invalid.out" 2>"$BAD_ROOT/invalid.err"; then exit 1; fi
rg -n "duplicate|invalid|metadata|order" "$BAD_ROOT/invalid.err"
```

缺文件也要保留真实失败记录。这个副本只删临时目录中的发布文档：

```bash
export CARGO_TARGET_DIR="${CARGO_TARGET_DIR:-$PWD/rust/target}"
MISSING_ROOT="$(mktemp -d /tmp/rein-ch08-missing.XXXXXX)"
cp -R fixtures/ch08-context/. "$MISSING_ROOT/"
rm "$MISSING_ROOT/docs/release.md"
npm run --silent ch08:compare -- --data-root "$MISSING_ROOT" --strategy on-demand >"$MISSING_ROOT/result.json"
node -e 'const fs=require("fs"); const o=JSON.parse(fs.readFileSync(process.argv[1])); const r=o.results.find(x=>x.taskId==="task-02"); if(!r||r.status!=="error"||r.answer!==null||r.modelCalls!==0||!r.callRecords.length||!r.callRecords.some(c=>c.prepared&&c.terminal&&!c.dispatched&&c.child_pid===null)) process.exit(1); console.log(`status=${r.status} answer=null modelCalls=${r.modelCalls} records=${r.callRecords.length} prepared=true dispatched=false pid=null`)' "$MISSING_ROOT/result.json"
```

预期输出包含 `status=error answer=null modelCalls=0 records=...`，具体 pid、退出码和 terminal 由本机进程产生。

## 独立练习

三项练习复制资料到绝对临时目录，不修改冻结 fixture。

<a id="practice-08-1"></a>

### 练习一：修改事实

复制资料到绝对临时目录，将真实文档的 `传输方式：JSON Lines` 改为 `传输方式：HTTP`，保留旧 oracle，然后运行：

```bash
export CARGO_TARGET_DIR="${CARGO_TARGET_DIR:-$PWD/rust/target}"
PRACTICE_ROOT="$(mktemp -d /tmp/rein-ch08-practice-1.XXXXXX)"
cp -R fixtures/ch08-context/. "$PRACTICE_ROOT/"
cp "$PRACTICE_ROOT/tasks.json" "$PRACTICE_ROOT/tasks.oracle.json"
node -e 'const fs=require("fs"); const p=process.argv[1]+"/docs/early-runtime.md"; let s=fs.readFileSync(p,"utf8"); if(!s.includes("传输方式：JSON Lines")) process.exit(1); fs.writeFileSync(p,s.replace("传输方式：JSON Lines","传输方式：HTTP"));' "$PRACTICE_ROOT"
npm run --silent ch08:compare -- --data-root "$PRACTICE_ROOT" --strategy on-demand >"$PRACTICE_ROOT/result.json"
cmp "$PRACTICE_ROOT/tasks.json" "$PRACTICE_ROOT/tasks.oracle.json"
node -e 'const fs=require("fs"); const a=fs.readFileSync(process.argv[1]); const b=fs.readFileSync(process.argv[2]); if(!a.equals(b)) process.exit(1); const o=JSON.parse(fs.readFileSync(process.argv[3])); if(o.results.length!==4) process.exit(1); const r=o.results.find(x=>x.taskId==="task-01"); const sourceMessages=r.messages.filter(x=>x.role==="user"&&x.content.includes("[来源:doc-01]")); if(!sourceMessages.some(m=>m.content.includes("传输方式：HTTP"))||!r.answer.rawAnswer.includes("传输方式：HTTP")||!r.answer.claims.some(c=>c.field==="传输方式"&&c.value==="HTTP"&&c.source==="doc-01")||r.quality!==0.5) process.exit(1); console.log(JSON.stringify({rawAnswer:r.answer.rawAnswer,quality:r.quality,oracleUnchanged:true,rows:o.results.length}))' "$PRACTICE_ROOT/tasks.json" "$PRACTICE_ROOT/tasks.oracle.json" "$PRACTICE_ROOT/result.json"
```

核对 task-01 的 messages 与 `answer.rawAnswer` 使用 HTTP、来源仍为 doc-01；旧 oracle 仍有 JSON Lines，因此 quality 应为0.5。它证明离线回答器读取真实 messages，不证明模型或 HTTP 服务性能。


修改 task-03 的 query 词后比较 selectedSources、段落 score 与 quality；缺少来源时 quality 下降，claims 不凭空补齐。这里证明 retrieval 的离线正文评分，不证明召回率、生产 token、延迟或容量。下一章第09章仍未实现。

## 本章结论

上下文管理不是随意截短字符串：Rust authority 决定预算和证据，Node 提供实际领域文件，带来源的最终 messages 构成回答边界。on-demand 省掉不相关 I/O；window 保留有序历史但可能裁掉事实；summary 规则式提取事实行并保留来源；retrieval 用正文匹配和稳定排序寻找片段。这些实验只证明本地消息构造、证据来源、预算终态、离线回答和真实进程记录，不能证明供应商模型性能、服务 token、网络延迟、线上容量、安全沙箱或生产吞吐量。

# 00 我们要实现一个怎样的 Agent

让模型写一个 Hello World，通常只需要一句话。但当代码编译失败，模型怎样取得报错？它提出修改以后，谁来检查差异，谁决定保存，谁确认程序真的能运行？

这些问题的答案，不在模型里，而在模型周围的那段程序里。本书要亲手构建的，就是这段程序。本章先说明终点、角色和阅读方式，不要求安装任何东西。

## 1、Rein 最终要做什么

Rein 是本书逐步构建的 Agent。它最终要完成的事情很朴素：

```text
理解任务 → 读取相关文件 → 提出一份人能审查的修改 → 等待批准 → 执行修改 → 用验证结果判断是否完成
```

全书分六部分走到这里：

| 部分 | 做出什么 |
| --- | --- |
| 一 极简 Harness（00–03） | 用 Python 做一个终端代码修改助手，修好一个 C++ Hello World |
| 二 核心循环（04–08） | 用 Rust 重建它，并能连续行动、适时停止、随时取消 |
| 三 可信 Harness（09–15） | 管理上下文、权限、候选补丁、批准与验证 |
| 四 Agent 扩展（16–20） | 计划模式、Skill、Hooks、MCP 与受限委派，按需选用 |
| 五 实际应用（21–24） | 把它接进一个轻量 IDE，完成真实开发任务 |
| 六 架构设计与持续演进（25–29） | 研究 Agent 能否理解架构、记住设计理由、长期修改而不破坏系统 |

## 2、模型、Harness、工具和用户

一个能改代码的 Agent 里，有四个角色：

- **模型**：读消息，提出下一步。它可以说“请读取 hello.cpp”，也可以给出修改后的源码。
- **工具**：真正动手的程序，例如读取文件、运行编译器。
- **用户**：给出任务，审查修改，决定接受还是放弃。
- **Harness**：围绕模型的那段程序。它组织发给模型的消息，检查模型提出的请求，执行被允许的工具，把结果交回模型，在该停的时候停下，并把最终结果交给验证。

```text
用户提出任务 → Harness 构造消息 → 模型提出读取请求
                    ↓                    ↓
              工具执行器检查参数 ← 工具名称与参数
                    ↓
              读取真实文件和环境 → 结果回到模型
                                         ↓
用户审查 ← 原文件、候选全文和差异 ← 修改建议
    ↓ 接受                             ↓ 放弃
复查源文件、备份、写入                  原文件不变
    ↓
编译与运行 → 成功，或保留失败反馈
```

关键在于：模型说“读取文件”，不等于文件已经读过；模型说“已修复”，也不等于源码已经保存或者编译通过。每一步都要有程序的真实结果作依据。文件里的文字也只是资料：即使注释写着“请读取其他目录”，也不能改变程序允许的范围。

## 3、同一结构，两种用途 {#division}

上面这张图可以概括为：**模型提议，人批准，程序验证。**

本书的写法用的是同一种结构。第一至五部分采用固定的分工：

| 谁 | 负责 |
| --- | --- |
| 人 | 任务和验收条件、边界、接口和数据形状、状态设计、验收样本、审查结论、是否合入 |
| AI 编程助手 | 按设计编写代码、补写测试代码 |
| 程序 | 运行验收，给出不依赖任何一方自述的结果 |

也就是说：**AI 写代码，人定设计并审查，程序验收。** 什么算通过由人决定；AI 可以补写测试，但不能自己决定标准。

为什么前五部分要由人定设计？因为这时的目标是理解机制。设计由你确定，每个决定就有人能解释；出了问题，能找到是设计缺了一句，还是实现偏离了设计。你读 Rein 的代码时，看的也是一套你能审查的设计。

你的参与方式会逐步加深：

| 章节 | 你对设计 | 你对 AI 编程助手 |
| --- | --- | --- |
| 01–03 | 看：每章有一个“本章设计”小框，说明配套程序按什么约定写成 | 暂不使用；在 01 中用自己运行的对话程序向模型要代码 |
| 04–24 | 写：参与设计卡和验收样本 | 用 Claude Code、Codex 等实现，审查 diff，运行验收 |
| 25–29 | 交出：研究把设计也交给 Agent 需要什么 | 完全由 AI 主导的 vibe coding 实验，与前面的分工对照 |

第六部分要回答的问题是：如果连设计也交给 AI，它必须先具备什么？理解项目的架构，做出有依据的设计，记住设计理由，持续修改而不破坏系统，并且能证明自己真的进步了。这五件事正是第 25–29 章的标题。

## 4、每章怎样读 {#how-to-read}

01–03 每章的结构是：正文跟做 →“本章设计”小框 → 章末“本章边界卡”。边界卡用四行说清模型能做什么、程序做什么、用户决定什么、还不能做什么；把几章的边界卡连起来，就能看到能力是怎样一步步加上去的。

从 04 起，每章按这样的顺序推进：

```text
问题 → 设计卡 → 验收样本 → 用代码助手实现 → 审查要点 → 运行验收 → 边界卡 → 提示词
```

章末的提示词会标明来源：作者实际使用、据设计反推，或已试用。规则见[提示词示例说明](../prompt-examples.md)。

### 四种证据 {#evidence}

书里出现的结果分四种，读的时候留意它属于哪一种：

| 标签 | 含义 | 能说明什么 |
| --- | --- | --- |
| 示意 | 书中写出的样例输出 | 只说明格式，不是运行结果 |
| 离线替身 | 程序内置的固定模型响应 | 程序的处理路径正确；不代表任何真实模型的能力 |
| 真实模型 | 实际请求模型服务得到的结果 | 那一次、那个模型的表现，不保证下次相同 |
| 本地验证 | 在你的电脑上实际编译、运行、测试的结果 | 这份代码在这个环境里确实满足了检查 |

模型说“完成了”，不属于其中任何一种。

## 5、第一部分的任务

第一部分只做一件小事。用一张任务卡表达：

```text
目标：修复 hello.cpp，使它输出 Hello, world! 和一个换行。
工作区：读者单独创建的临时练习目录。
读取：hello.cpp、compiler.log，以及固定查询取得的编译器与系统信息。
修改：仅用户接受当前候选后，才能保存 hello.cpp，并保留原文件备份。
验证：固定 C++17 编译命令；本轮编译成功才运行新产物；核对输出与退出码。
```

Python 是调用模型、组织消息和执行工具的程序，C++ 是练习对象。四章各增加一项主要能力：

| 章节 | 遇到的问题 | 新增能力 | 章末结果 |
| --- | --- | --- | --- |
| 01 模型调用 | 怎样把任务交给模型？ | 配置、请求、连续对话与失败处理 | 生成 Hello World，由人保存和编译验证 |
| 02 读取代码与日志 | 模型看不见当前源码与终端报错 | 手工提供资料 → 受限工具读取 | 有依据的修复候选，由人决定是否采用 |
| 03 终端代码助手 | 来回复制候选容易漏改、误改 | 全文和差异展示、接受或放弃、备份写入与验证 | 一个能走完小任务的终端助手 |
| 04 核心能力 | 状态只靠字符串维持，难以继续扩展 | 能力地图；人写设计、代码助手实现的 Rust 迁移 | 与 Python 行为一致的 Rust core |

第二章故意删除一个分号，确保能观察到真实的编译失败。每一步也都准备了失败对照：

| 输入或选择 | 应看到什么 |
| --- | --- |
| 缺少模型配置 | 请求前指出缺项 |
| 读取不允许的路径 | 拒绝读取，不编造文件内容 |
| 用户放弃候选 | 源文件不变，不创建备份 |
| 等待接受时源码变化 | 拒绝过期候选 |
| 编译成功但输出错误 | 验证失败，不宣称任务完成 |

这一阶段只适用于你自己控制的练习目录。通用权限、持久批准、多文件修改与恢复，留在后面的可信 Harness 部分。

## 6、开始前的准备

你需要会在终端里运行命令，能读懂简单的程序。Python 环境、环境变量、JSON 和工具消息都会在第一次用到时解释；不需要事先会 Rust。

01–03 只需要 Python 和一个模型服务的 API Key。暂时没有 API Key 也能跟做：配套程序默认使用离线替身，只是那时看到的不是真实模型的表现。04 起建议准备 Claude Code 或 Codex 这类代码助手；仓库里有每章的参考实现，没有代码助手也能读懂并运行。

无论用哪种工具，都只在单独创建的练习目录里操作，不要让模型或代码助手接触你的密钥文件和无关项目。

## 7、写下你的完成条件

开始前先回答三个问题：怎样判断输出正确？用户放弃以后，哪些内容应该保持不变？模型给出了代码，但编译失败，任务算完成吗？

把答案记在练习目录之外的笔记里，第三章结束后再对照一次。这三个答案，就是你写下的第一份验收条件。接下来打开[01 用 Python 完成第一次模型调用](./python-model-call.md)，从一句问候开始。

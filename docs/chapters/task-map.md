# 00 从一次文档维护任务认识 Rein

**状态：文字修订稿，待教学验收｜永久免费 · Apache-2.0**

你可能遇到过这样的项目：代码已经更新，README 里的启动命令却没有改。照着说明操作会失败，翻过项目配置才发现应该换一条命令。如果请 AI 助手处理这件事，它需要做的不只是写出一段更通顺的文字，还要找到依据，判断是否真的需要修改，并检查修改后的说明能否使用。

本书用这个小任务学习 Agent Harness，也就是组织模型调用、工具执行与任务状态的程序。我们把逐步搭建的项目叫作 Rein。本章先画清任务和分工；从下一章开始，再让程序一步步获得完成任务所需的能力。

## 1、从一处过期的说明开始

假设一个教学项目的 README 写着“运行 `npm run start` 启动预览”，项目维护者提供的新说明却要求使用 `npm run dev`。这是一组假设材料，不能据此判断你手边的真实仓库也有同样的问题。

最直接的做法是把两段文字交给模型，请它建议修改。模型可能很快给出正确的替换，但接下来仍有几个问题：它看的是哪个版本？是不是只改了该改的部分？建议有没有写进文件？新命令是否真的能运行？这些问题需要不同的动作和证据。

一次完整的文档维护可以分成下面几步。这里展示的是全书要逐步实现的流程，第一部分只做到读取资料并回答。

| 步骤 | 要做的事 | 用什么判断结果 |
| --- | --- | --- |
| 说清任务 | 指定目标文档、依据和允许的修改范围 | 一份可以逐项检查的任务说明 |
| 读取资料 | 取得文档和项目配置的当前内容 | 实际读取的路径、内容或错误 |
| 提出修订 | 解释差异，给出候选改动 | 引用与原文吻合，改动符合任务 |
| 批准并应用 | 确认候选后修改目标文件 | 批准对应的差异与实际文件变化 |
| 检查结果 | 检查内容、链接或允许执行的命令 | 修改后状态及实际检查结果 |

如果两份材料本来就一致，合理的结果是保留原文；如果没有足够依据，合理的结果是说明缺少什么。并不是每次任务都应该产生修改。

## 2、分清模型、工具、环境和 Harness

模型接收上下文，产生回答或工具请求。它可以提出“读取 README”，但这句话本身不会打开文件。

工具把一种具体操作提供给程序，例如读取文件、搜索文字或检查链接。工具返回成功，通常只说明这次操作按其约定完成了。例如，读取成功表示拿到了内容，并不表示内容中的启动说明正确。

环境保存真实状态，包括磁盘上的文件、正在运行的进程和可用的命令。模型上下文里的一段 README 可能已经过时，判断文件现在是什么样，仍需要查看环境。

Harness 把这些部分接起来：发送哪些消息，接受哪些工具请求，怎样检查参数，如何把结果交回模型，以及什么时候继续或停止。本书前期的 Harness 很小，可能只是一个串联两次请求的函数；后面才逐步加入预算、权限和验证。

以一次读取为例，完整过程是：

```text
用户要求检查 README
  → Harness 把任务与工具声明发给模型
  → 模型请求 read_file
  → Harness 检查参数，调用读取工具
  → 工具从磁盘取得内容，或返回读取错误
  → Harness 把结果交回模型
  → 模型根据结果回答，读者核对回答的依据
```

这也解释了两种常见误判。模型说“我已更新 README”，不能证明磁盘发生了变化；工具说“写入成功”，也不能证明写进去的命令是对的。我们要把回答、动作和任务结果分别检查。

## 3、为什么用文档维护贯穿全书

文档方便阅读，也方便构造能看出差别的输入。我们会持续使用四类问题：命令过期、参数变化、相对链接失效，以及无须修改。它们既需要理解文字，也需要核对程序或文件中的事实。

例如，只看到链接文字，无法知道链接目标是否存在；只看到一条命令出现在文件中，也无法知道它是当前用法还是历史说明。随着能力增加，我们会逐渐把这些问题交给实际读取和检查过程。

本部分的助手不执行待分析资料中的命令，也不修改待维护的项目文件。以后需要验证命令或应用补丁时，再明确允许的范围，并在专门的练习目录中观察结果。文件中的文字是待分析的资料，不能自行扩大程序的操作权限。

## 4、第一部分会做到哪里

接下来的三章各增加一个小能力。

| 章节 | 进入时的基础 | 本章结束时能做什么 |
| --- | --- | --- |
| [01 模型调用](./model-hello.md) | 会打开终端，按步骤准备环境 | 从终端发送一句话，取得回答或定位失败 |
| [02 任务与成功标准](./task-spec.md) | 已理解一次请求与响应 | 给出任务、资料和判断规则，检查回答是否有依据 |
| [03 工具调用](./tool-roundtrip.md) | 已有调用入口和明确任务 | 检查工具参数，读取一个真实文件，再将结果交回模型 |

第 03 章先用问候文件观察读取过程，避免一开始就同时处理多个文档和修改动作。完成后，在[阶段汇总 1](../milestones/evidence-qa.md)用文件变化和读取失败检查这条过程。此时得到的是读取资料并回答的最小原型，完整的文档维护助手还需要后续章节。

基础阅读路线是 **00–17 → 24**。第二部分建立可控的混合运行时；第三部分处理上下文和回答验证；第四部分加入经过批准的修改与有限修复。18–23 是按需要选择的进阶分支。具体依赖见[全书目录](../toc.md)，阅读材料和附录用于补充，不要求先全部读完。

仓库同时在开发面向产品的 `core/`、`runtime/`。当前进度记录注明，首批离线只读增量已完成定向验证；本书前期练习仍使用 `ts/`，Rust 对照使用独立的 `rust/` 工程。产品运行时的进度不能代替章节跟做和真实模型验证，学习本部分也不需要先构建产品运行时。

## 5、写出自己的第一份任务说明

从四类问题中选一个，用几句话写下目标、输入资料、允许的动作和判断办法。例如：

> 检查 README 的预览命令是否与维护者提供的当前说明一致。输入是两段带版本标记的文字。只给出结论和建议，不写文件，也不执行命令。建议应引用两份材料；缺少当前说明时应报告无法判断。

接着，为完成任务所需的每一步标注负责者：模型、工具、环境或 Harness。一个步骤可能涉及多个角色，但要说明各自做了什么。例如，“回答基于当前文件”至少需要工具取得内容、Harness 回传结果，以及模型使用这份结果。

最后，构造一个“工具成功但任务失败”的例子，并写出还缺哪项检查。如果你能解释为什么一次成功读取不能证明启动说明正确，就已经抓住了本章的分工。下一章从最小的一次模型调用开始，把图里的第一段过程变成可以运行的程序。

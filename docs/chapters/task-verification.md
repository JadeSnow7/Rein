# 13 验收条件、验证器与证据

**状态：已有离线集成示例，逐章衔接与实机验收待完成｜永久免费 · Apache-2.0**

## 进入这一章

上一章已经把相关资料送入上下文，并在依据不足时停止回答。这一章新增一个独立问题：程序怎样检查文档里的命令确实存在？离开时应留下规则、可复现的失败输入和绑定输入版本的验证结果，而不是一句“看起来没问题”。

程序成功退出，回答就一定正确吗？一个检查器可能只验证JSON能解析，也可能真的比较了修改后的文件。先确定它检查的对象和规则，再讨论结果。

## 把02的验收问题变成规则

命令过期案例比较文档命令与项目清单；参数案例使用当前帮助文本；相对链接按源文档目录解析目标；无须修改案例要求文件字节不变。每条规则保留规则ID、输入版本和结论。规则只覆盖它表达的条件，不能据此宣布整份文档正确。

固定案例位于 `fixtures/document-maintenance/cases.json`。其中expected只给评测器使用；把正确答案送给模型再报告效果，会失去比较意义。

## 验证命令也是工具

run_verification通过09的通用扩展点接入。调用只传允许的规则和目标，不接收任意shell字符串。宿主运行受信任的配套检查入口，限定参数、工作目录、截止时间和输出量。验证器没有绕过权限的特权，命令的副作用也必须留在受控夹具中。

一次证据要绑定任务、调用、规则、文件版本与实际输出。文件改变后，旧证据可以证明当时的状态，却不能直接证明当前状态。执行超时、检查失败和输出无法确定分开表达。

## 检查验证器自己

给它一个格式正确但结论错误的答案；让引用指向不存在的文件；把通过后目标文件替换掉；让检查进程退出非零。逐项确认不会被记录成通过。验证器本身的测试、一次文档任务验收、证据绑定和系统评测分别记录。

## 先校准规则，再接入会话

在仓库根目录创建一份独立输入。下面的路径必须尚不存在；重复练习时换一个路径，不覆盖上次失败现场。

```sh
REIN_LESSON_TMP=$(cd "${TMPDIR:-/tmp}" && pwd -P)
node scripts/maintenance-fixture.mjs command-1 "$REIN_LESSON_TMP/rein-command-lesson"
```

夹具中的 README 使用 `npm run start`，而 `package.json` 只声明 `dev`。生成器只复制输入文件，不复制评测器的正确答案。进入夹具目录后，使用仓库中的受信验证器，检查器不从被检查目录加载同名脚本：

```sh
REIN_LESSON_REPO="$PWD"
cd "$REIN_LESSON_TMP/rein-command-lesson"
node "$REIN_LESSON_REPO/examples/document-maintenance/verify.mjs" --rule command-v1 --target README.md
```

第一次检查应报告 `ok: false`，并以非零状态退出。它发现的是命令声明不一致，没有执行 `package.json` 中的命令。将 README 的 `start` 改为 `dev` 后再检查，才应得到 `ok: true`。手工修改用于校准检查器；第 16 章再把修改交给批准后的工具调用。

这条直接执行命令是读者对验证器的校准，不是 core 的权限测试。运行时必须通过 `run_verification` 派发，再检查任务身份、调用身份和文件版本。单独运行脚本得到的 JSON 不能冒充该工具回执。

命令、参数、链接各用一条明确规则。`command-v1` 不证明命令能运行成功；它只检查文档提及的脚本名存在。项目实际构建和更广的正确性需要另外声明规则与运行条件。

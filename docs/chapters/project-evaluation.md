# 24 文档维护助手：评测与复盘

**状态：新版初稿，未完成逐章衔接验收｜永久免费 · Apache-2.0**

本章把“连续维护”限定成一个可检查的单文档纵切。它不声称已经证明 AI 有长期架构能力，也不把普通子进程当作盲测或安全沙箱。章节责任以全书目录与已批准方案为准。

## 24.1 先固定继承关系

每条轨迹只有一个 `seedFile`。第 1 轮读取种子，后续轮次只能读取上一轮实际生成的 `artifact`，不能重新读取种子或从全局目录拼出“正确答案”。runner 为每轮写入 `task.txt`，并通过参数把它传给适配器、检查器和独立 validator。每轮保存输入/输出 SHA-256、原始 stdout/stderr、进程状态和检查结果，所以可以判断它究竟继承了哪个文件。

执行基准测试：

```bash
node --test scripts/evolution/runner.test.mjs
```

运行两条确定性 12 轮校准：

```bash
node scripts/evolution/demo.mjs
```

`adapter-good.cjs` 逐轮把本轮任务写进文档，所有检查都通过。`adapter-regressing.cjs` 在第 7 轮引入一个历史格式回归；新检查仍然通过，但此前已经通过的 `legacy-contract` 失败。报告中的 `regressions` 只记录从通过变为失败的事件，后续仍失败的轮次进入 `stillFailing`。这说明评分器能区分“新增要求通过”和“历史要求退化”，并不说明适配器具备架构设计能力。

## 24.2 检查持续、退役和失败

检查在某轮声明后会自动继承到后续轮次。需求确实替代旧规则时，计划必须使用旧检查的 id 并提供非空 `retirementReason`；同一轮加入新的检查 id 是可审计的替代方案，runner 不假设所有退役都必然有一条一对一替代检查。未知检查、无理由退役、重复 id、输出目录已存在、路径重叠和含 shell 语义的命令都会在启动子进程前拒绝。

适配器退出 0 只代表进程正常结束。validator 仍然独立读取输出；它失败、超时、进程错误或适配器没有生成输出时，该轮不能通过。输出目录必须全新，stdout/stderr 保留为证据；token、cost、人工时间和修改文件数没有可靠来源时记录为 `null`，不能用估算值冒充测量。

## 24.3 如何解读这次 demo

这次 demo 只校准四种机制：真实前轮继承、任务显式传递、旧检查连续运行和故意历史回归检测。它使用普通用户权限下的本地 Node 子进程，不隐藏未来任务，也没有对抗式隔离；因此不能作为安全边界、盲测或模型能力结论。章节仍保留初稿状态，工具通过不等于完整章节验收。

## 24.4 后续三组真实实验

要研究“设计记忆是否改善连续维护”，应冻结同一项目、同一预算、同一工具权限和多条需求序列，然后比较三组：普通助手只得到当前任务；设计记忆组额外得到经版本绑定的模块职责、决策理由、前提和复审条件；完整闭环组还必须写入每轮计划、沿用旧检查、运行独立验证并留下回滚证据。每组使用多个独立序列，后续任务在前轮完成后才揭示，避免把公开 fixture 当作盲测。

主要指标包括新需求通过率、历史回归事件数、仍未修复回归、实际变更文件数（当前单文档纵切为 0 或 1）、恢复失败的成本和人工介入时间。所有组共享同一时间、模型调用和工具预算；报告同时保留失败和未确定状态。应把“架构设计更好”限定为后续变化下的累计代价更低，而不是把一次初始方案评审分数当作长期能力。

# 18 计划与任务审查

**状态：新版初稿，未完成逐章衔接验收｜永久免费 · Apache-2.0**

本章补充一个小而实用的维护环节：把架构决定写成带前提的登记项，再在每次重要变更后检查前提是否仍成立。它解决的是“决定为什么成立、什么时候要重新审查”的记录问题，不是让检查器替人证明架构正确。

## 先记录决定，再记录前提

一条决定至少需要说明决定内容、理由、适用范围、考虑过的替代方案、复审条件和来源。最容易被遗忘的是前提：例如“核心边界由 `core/` 维护、运行时边界由 `runtime/` 维护”，可以绑定到两个当前文件的 SHA-256。摘要是一个复审触发器；它不能证明文件里的架构设计合理，也不能替代代码审查。

登记表放在 `architecture/decisions.json`。`status` 是维护者的人工采纳状态，使用 `accepted`、`proposed` 或 `superseded` 等值；检查器另行输出机器状态。机器不会把 `proposed` 自动提升为 `accepted`，也不会替 `superseded` 刷新历史摘要。

## 运行检查

在仓库根目录运行：

```bash
node scripts/architecture/decisions.mjs \
  --root . \
  --registry architecture/decisions.json
```

检查器逐个读取登记的普通文件并比较 SHA-256。前提匹配是 `applicable`；文件已改变是 `review_required`；缺失、不可读、非普通文件或没有声明前提是 `undetermined`。混合结果会逐项保留原因，任何未知都不能成为通过。工具拒绝绝对路径、越界路径和符号链接，避免把仓库外的内容伪装成仓库事实。登记表不会被改写。

退出码的含义很窄：至少存在一条 `accepted` 决定，且所有 `accepted` 决定的全部前提都匹配时为 0；没有 accepted 决定、任一 accepted 决定需要复审或无法确认时为 1；输入格式或运行错误时为 2。`proposed`、`superseded` 等其它生命周期仍会报告机器状态，但不计入 0 的通过条件。空登记表不会产生“没有问题所以通过”的空集合结论。

## 为后续变化选择边界

维护助手的核心架构有两个可比较的方向。核心直接负责文件和进程 I/O，初期代码较少、调用路径直观，但崩溃恢复、未知副作用和第二宿主接入会把 I/O 假设扩散进领域逻辑；另一方向是核心只执行纯步进，driver 负责执行已经提交的意图，重试资格由 core 根据操作语义确定，接口与测试成本更高，却能把恢复边界和副作用集中在一个可替换层。选择前应做一个小原型：中断写入后能否恢复、外部调用结果未知时能否安全重试、换第二个宿主是否只改 driver。未知副作用应先核对结果，不应由 driver 自动重放。若当前只有单宿主、单进程且无可重试副作用，直接 I/O 的成本优势可能成立；一旦出现第二宿主、需要恢复或副作用结果不确定，就应按登记的复审前提重新比较，而不是继续添加抽象层来预支所有未来。

## 维护时如何处理失效

如果一个摘要变化，先检查变化是否触及决定的适用范围，再决定接受新设计、回滚变更或生成新版本登记。不要把当前摘要写回旧记录来消除告警；这样会丢失“旧决定曾经在哪些事实下成立”的历史。新记录应说明新的理由、前提和复审条件，并保留旧记录为历史。

```bash
node --test scripts/architecture/decisions.test.mjs
```

测试覆盖匹配、变更、缺失和空前提、混合未知、人工状态、重复或畸形 ID/hash、越界和符号链接路径，以及输入不变性。通过这些测试只说明登记和检查机制按声明工作；它不构成 R1/P0 或完整章节验收，也不代表 AI 已经具备长期架构维护能力。

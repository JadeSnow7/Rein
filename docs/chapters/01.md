# 01 从模型调用开始

公共导读已提供 · TypeScript 正文与实现已提供 · Rust 待补齐 · 永久免费

这一章从一次正式模型调用开始。把提示词接到模型服务，让回答从网络另一头回来，会多出哪些事情？

地址要填对，密钥要传过去，返回的正文也未必长成我们期待的样子。有时候等了很久，终端只留下一句错误。光知道怎么提取字符串，已经不够了。

这一章就沿着这次交换往前走。从一句终端输入出发，跟到请求、响应和错误出口，再用固定样本检查这条路径。

你可以直接进入 [TypeScript 版](./01-ts.md#first-run)动手，也可以先读这份公共导读。需要补充本地解析、异步或错误处理知识时，再按需查阅[阅读 0](../readings/00.md)。Rust 正式调用尚待补齐；当前没有对应的 Rust 运行步骤。

## 本章要完成什么 {#from-reading-0}

本章自足说明正式调用的请求、响应和失败处理。若不熟悉本地 JSON 检查、异步或错误传播，可按需回看阅读 0；那里的示例不是本章的前置步骤。

| 本章要解决的问题 | 当前行为 |
| --- | --- |
| 响应从哪里来 | 从模型服务、本地桩或历史录制取得响应 |
| 回答位于哪里 | 沿 `choices[0].message.content` 读取回答 |
| 失败如何分类 | 区分配置、网络、HTTP、超时与 `response-format`，保留具体原因 |
| 等待边界在哪里 | 等待连接、响应头和完整响应体，并执行超时控制 |
| 什么证据足够 | 分别检查请求构造、响应解释和收发行为；真实端点另行记录 |

本章沿用仓库选定的 OpenAI 兼容 Chat Completions 接口，只处理非流式文本回答。其他接口的适配留到第 04 章。这里还没有工具调用、多轮循环或自动重试。

## 先完成一次离线检查 {#first-run}

仓库已有一份成功回答和一份额度不足的历史响应。我们先把它们交给调用代码，观察正常文本能否取出、失败原因能否保留。输入固定，结果就有了可以反复检查的依据。

具体命令见 [TS 版的离线检查](./01-ts.md#first-run)。这一步不读取密钥，也不请求模型服务；首次安装依赖仍需要网络。

<span id="确认环境-先完成一次离线检查"></span>

遇到测试失败时，先看哪个断言没有满足。安装报错、字段解析失败和远程服务拒绝请求，是三件不同的事。暂时没有端点的读者，可以先把本地部分走完。

### 再连接真实服务 {#live-call}

真实调用需要端点地址、密钥和模型名，见 [TS 配置与运行](./01-ts.md#live-call)。那条命令会发出请求并产生 API 用量，返回文本也不固定。

运行后留下调用时间、模型标识、退出码和结果摘要。没有运行，就记为未验证。这份记录回答的是你的端点是否在那次调用中可用。

## 一句话怎样变成请求与响应 {#request-response}

输入的提示词先进入程序，由配置决定发往哪里、使用哪个模型。调用层把消息组织成请求，收发层取回状态码和正文，调用层再检查并提取结果。

```text
提示词 + 配置 → 构造请求 → 收发 → 检查状态 → 解析正文 → 输出结果
                 任一步失败，都需要带回对应阶段的线索
```

本章的请求把提示词放在 `messages` 的 `user` 消息中，用 `model` 指定模型。响应则沿 `choices → 第一个候选 → message → content` 取出文本。完整的请求与响应示意见 [TS 版对应小节](./01-ts.md#request-response)，其中的 JSON 形状与编程语言无关。

这里很容易漏掉一件事，HTTP 200 只让程序继续检查正文。正文可能不是合法 JSON，也可能缺少候选，或者 `content` 根本不是字符串。

取到字符串之后，还可以查看服务端回报的模型名、结束原因和用量。本章保留这些信息供读者检查，尚未根据结束原因安排下一步行动，也没有判断回答是否正确。

试着沿这条路径解释一次失败。你能确认程序走到了哪里？还有哪一步没有证据？

## 失败分成几类 {#failures}

程序只说一句解析失败，你还得回头加打印。要是同时留下出错的字段路径、状态码和响应片段，就能接着判断。

| 失败类别 | 最后确认了什么 | 下一步查看什么 |
| --- | --- | --- |
| `config` | 本地配置检查未通过 | 错误指出的环境变量 |
| `network` | 收发过程中发生非超时故障 | 地址、底层原因与故障阶段 |
| `http` | 已读到完整的非 2xx 响应 | 状态码和服务端正文 |
| `timeout` | 到达截止时间，仍未取得完整响应 | 超时值、连接和服务端耗时 |
| `response-format` | 已通过 HTTP 状态检查，正文未通过解析或字段检查 | JSON 语法、错误路径和值 |

网络中断或超时，不能证明服务端没有处理请求。连接可能在读取正文时才断开。本章把错误交还入口并退出；当前 TS 的网络错误提示含有「未能送达」，诊断时仍应结合实际阶段，不能凭这句话断定服务端未执行。

仓库中的 429 样本带有 `insufficient_quota`。它提醒我们，状态码只给出一部分信息，限流和额度问题需要不同的后续处理。先读响应体，再决定下一步。具体错误类与示例见 [TS 失败处理](./01-ts.md#failures)。

## 为什么再切出 transport {#transport}

想检查服务返回坏 JSON 时程序会怎样，总不能等远程服务真的出错。正式调用同样需要可替换的输入来源。

于是，把取得响应的工作交给 transport。调用逻辑只关心拿回的状态与正文，可以选择真实收发，也可以选择按顺序返回历史样本。

这样，测试与真实调用能经过同一份请求构造和解析代码。

不过，它们的证据范围并不相同。当前回放只按顺序返回响应，不比对录制中的请求，不模拟延迟或超时。请求是否拼对，由记录输入的本地桩检查；网络行为由本地 HTTP 服务测试。TS 的接口和实现见[对应小节](./01-ts.md#transport)。

## 录制与离线验证 {#verification}

<span id="先使用已有样本"></span>

`fixtures/responses/` 中的两份录制，一份是 `opencode-go/hello-1.json`，保存 HTTP 200 的文本回答；另一份是 `openai/insufficient-quota-1.json`，保存 HTTP 429 的额度不足响应。

打开其中一份，先看外层的 `response.status`，再看 `response.body`。正文仍然是字符串，里面又有一层 JSON。录制加载器读取外层文件，调用代码再解释内层正文。当前 TS 加载器没有完整校验外层录制结构，所以这里只使用仓库中的已知样本。

具体测试范围与命令见 [TS 离线验证](./01-ts.md#verification)。看见测试通过后，再说明它验证了哪种输入、哪条规则。历史样本只描述当时收到的响应，不能证明服务今天可用。

### 需要新样本时再录制 {#recording}

录制会另外发出一次真实请求，保存的是这次交换，不会追溯之前运行 CLI 得到的结果。操作、命名与检查步骤见 [TS 录制说明](./01-ts.md#recording)。

保存成功也不一定代表调用成功。非 2xx 响应同样可以成为有用的失败样本；连接失败或超时没有完整响应，不能充当成功录制。提交样本前，还需检查正文和请求头中的敏感信息。

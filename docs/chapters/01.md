# 01 从模型调用开始

**状态：永久免费**

本章做完一件事：向模型发一次请求，把回答取出来，并且在失败时说清楚失败在哪一步。

这件事本身不复杂，几十行就能跑通。本章的篇幅花在另外两处：一是让失败可以分类，二是让这次调用不必真的联网也能重放。后面十五章的每一个能力都要经过这两处，现在把它们放正，比第 05 章回头改要省事。

## 先跑起来

本项目支持 Node 22 或更高版本，以及一个 OpenAI 兼容端点的密钥。仓库根安装一次依赖：

```bash
npm ci
```

把密钥模板复制成本地配置：

```bash
cd ts
cp .env.example .env
```

填好 `.env` 里的三项。`REIN_BASE_URL` 指向兼容端点的根路径，通常以 `/v1` 结尾：

```
REIN_BASE_URL=https://api.example.com/v1
REIN_API_KEY=sk-...
REIN_MODEL=...
```

然后跑：

```bash
npx tsx --env-file=.env src/main.ts "用一句话说明什么是 Agent Harness"
```

标准输出是模型的回答，标准错误是一行元信息：

```
一个把模型、工具和环境接起来的运行时。

[<服务端回报的模型名>] finish_reason=stop tokens=21
```

回答的内容取决于你配置的模型，这里只用来说明两条流的分工：回答走标准输出，便于接管道；元信息走标准错误，不污染输出。

`tsx` 不会自动加载 `.env`，所以命令中要显式传入 `--env-file=.env`。`.env` 已在 `.gitignore` 中，不会入库。

如果这一步没跑通，先不要改代码。错误信息应当已经指出了原因，本章后半会逐条解释它们的形状。

## 拆解一：配置

程序启动要先知道三件事：往哪发、用谁的身份、调哪个模型。这三件事都从环境变量来，由 `src/config.ts` 读取。

```ts
export interface Config {
  /** OpenAI 兼容端点的根路径，末尾斜杠已去除 */
  readonly baseUrl: string
  readonly apiKey: string
  readonly model: string
}

export function loadConfig(env: Env = process.env): Config {
  return {
    baseUrl: readBaseUrl(env),
    apiKey: readNonEmpty(env, 'REIN_API_KEY'),
    model: readNonEmpty(env, 'REIN_MODEL'),
  }
}
```

值得注意的是这里没有任何默认值。缺变量就报错，报错时指名道姓：

```ts
function readNonEmpty(env: Env, variable: string): string {
  const raw = env[variable]
  if (raw === undefined) throw new ConfigError(variable, '未设置')
  const value = raw.trim()
  if (value.length === 0) throw new ConfigError(variable, '为空')
  return value
}
```

空字符串和纯空白与未设置同等对待。`.env` 里留下一行 `REIN_API_KEY=` 是很常见的情况，让它通过配置检查，故障就会推迟到服务端返回 401 时才暴露，而 401 有十几种可能的原因。

一个悄悄回退到内置端点的配置读取会更"好用"：不填也能跑。代价是"为什么调到了别的模型"这个问题，无法从任何一条错误信息里得到回答。本书后面会反复遇到同一种取舍——在出错时多说一句，比在正常路径上少写一行更划算。

`REIN_BASE_URL` 还多一层检查：必须是合法 URL，协议必须是 http 或 https。这两种写错都很常见，而且错法各不相同：

```
失败（config）：REIN_BASE_URL 不是合法 URL。参考 ts/.env.example，复制为 ts/.env 后填写。
```

## 拆解二：可替换的 transport 层

这是本章唯一一处"多做一步"的结构决定，也是最值得停下来看的地方。

调用模型在运行时是一次 HTTP 请求。但在测试里，它不能是一次 HTTP 请求——CI 在没有密钥的环境中运行，且任何依赖外部服务可用性的测试都会在某个早晨无故变红。于是把"把请求发出去、拿回状态码和响应体"这件事单独切出来，让上层不知道字节从哪里来。

`src/transport.ts` 的全部对外约定就是这个接口：

```ts
export interface Transport {
  send(request: TransportRequest, options: SendOptions): Promise<TransportResponse>
}
```

以及两侧的数据形状：

```ts
export interface TransportRequest {
  readonly method: 'POST'
  readonly url: string
  readonly headers: Readonly<Record<string, string>>
  /** 已序列化的请求体 */
  readonly body: string
}

export interface TransportResponse {
  readonly status: number
  readonly statusText: string
  readonly headers: Readonly<Record<string, string>>
  readonly body: string
}
```

这里刻意保持贫瘠。`body` 是字符串而不是对象，接口里没有 `messages`、没有 `choices`、没有任何与模型有关的词。transport 只搬运字节；认识字节里写了什么，是下一节 `chat.ts` 的职责。

两个实现。真实那个走 `fetch`：

```ts
export function createFetchTransport(): Transport {
  return {
    async send(request, options) {
      const signal = AbortSignal.timeout(options.timeoutMs)
      let response: Response
      let body: string
      try {
        response = await fetch(request.url, {
          method: request.method,
          headers: { ...request.headers },
          body: request.body,
          signal,
        })
      } catch (cause) {
        // AbortSignal.timeout 触发时抛出 name 为 TimeoutError 的 DOMException。
        if (isTimeoutAbort(signal, cause)) {
          throw new TimeoutError(request.url, options.timeoutMs)
        }
        throw new NetworkError(request.url, cause)
      }
      try {
        body = await response.text()
      } catch (cause) {
        if (isTimeoutAbort(signal, cause)) {
          throw new TimeoutError(request.url, options.timeoutMs)
        }
        throw new NetworkError(request.url, cause)
      }
      return {
        status: response.status,
        statusText: response.statusText,
        headers: Object.fromEntries(response.headers),
        body,
      }
    },
  }
}

function isTimeoutAbort(signal: AbortSignal, cause: unknown): boolean {
  if (!signal.aborted) return false
  const reason = signal.reason
  return reason === cause || (reason instanceof Error && reason.name === 'TimeoutError')
}
```

回放那个读录制好的样本，请求发往哪里都不重要，因为它根本不发：

```ts
export function createReplayTransport(recordings: readonly Recording[]): Transport {
  let next = 0
  return {
    async send(request) {
      const recording = recordings[next]
      if (recording === undefined) {
        throw new Error(
          `回放样本已用尽：第 ${next + 1} 次请求（${request.url}）没有对应录制，` +
            `当前共 ${recordings.length} 条。`,
        )
      }
      next += 1
      return recording.response
    },
  }
}
```

一个接口、两个实现，是很小的代价。但它决定了后面每一章的测试能不能写：第 05 章的循环要断言"第三轮模型返回了工具调用"，第 06 章要造出"预算耗尽"，第 10 章要制造各种失败——这些都要求响应可以被指定，而不是求来的。等到那时再回头切分，已经写好的调用代码就得全部改一遍。

## 拆解三：一次调用

`src/chat.ts` 把配置、transport 和一句提示词组装成一次请求：

```ts
export async function chat(
  config: Config,
  transport: Transport,
  request: ChatRequest,
): Promise<ChatResult> {
  const url = `${config.baseUrl}/chat/completions`
  const messages: Array<{ role: string; content: string }> = []
  if (request.system !== undefined) {
    messages.push({ role: 'system', content: request.system })
  }
  messages.push({ role: 'user', content: request.prompt })

  const response = await transport.send(
    {
      method: 'POST',
      url,
      headers: {
        'content-type': 'application/json',
        authorization: `Bearer ${config.apiKey}`,
      },
      body: JSON.stringify({ model: config.model, messages }),
    },
    { timeoutMs: request.timeoutMs ?? DEFAULT_TIMEOUT_MS },
  )

  if (response.status < 200 || response.status >= 300) {
    throw new HttpError(url, response.status, response.statusText, response.body)
  }

  return parseChatResponse(url, response.body)
}
```

这段代码是直白的：它知道 OpenAI 兼容接口的路径是 `/chat/completions`，知道消息是一个数组，知道 system 放在 user 前面。这些知识现在散落在函数体里，没有被抽象成协议或适配器。

这是有意的。第 04 章会拿 Anthropic Messages API 的响应回来对照，那时"两家对不上"是一个具体的、看得见的麻烦，从麻烦里提炼出的合同才有说服力。现在先把它写成一个只服务于一家的样子。

取回答文本的部分稍长一些，因为每一层都可能对不上：

```ts
const choices = root['choices']
if (!Array.isArray(choices)) {
  throw new ResponseFormatError(url, 'choices', '不是数组', body)
}
const first = choices[0]
if (first === undefined) {
  throw new ResponseFormatError(url, 'choices[0]', '不存在（choices 为空数组）', body)
}
```

`tsconfig.json` 里开了 `noUncheckedIndexedAccess`，`choices[0]` 的类型因此是"元素或 undefined"。这个开关经常被抱怨啰嗦，但在这里它恰好逼出了一条有用的错误信息：空的 `choices` 数组是真实会发生的情况，内容过滤命中时就是这样。

## 拆解四：失败分成几类

第 10 章整章在讲如何把失败信息组织成模型可以使用的形式。那一章能不能写，取决于第 01 章有没有留下可用的材料。所以这里不把失败压成一个 `Error`，而是分成五类，各自带着现场：

| 类型 | 何时发生 | 携带的信息 |
| --- | --- | --- |
| `ConfigError` | 环境变量缺失或格式不对 | 具体变量名 |
| `NetworkError` | 请求没能送达 | URL、底层原因 |
| `HttpError` | 服务端返回非 2xx | 状态码、响应体、按状态给出的线索 |
| `TimeoutError` | 超过 `timeoutMs` 未完成 | URL、超时值 |
| `ResponseFormatError` | 响应能读到但形状不对 | 出错路径、响应体片段 |

它们共享一个基类和一个 `kind` 判别字段，调用方可以按需区分，也可以统一兜住：

```ts
} catch (error) {
  if (error instanceof ReinError) {
    console.error(`失败（${error.kind}）：${error.message}`)
    return 1
  }
  throw error
}
```

不是 `ReinError` 的错误会继续上抛。程序里的空指针不应该被伪装成一次模型调用失败。

"携带的信息"这一列是本章的重点。对比两条消息：

```
解析响应失败
```

```
https://api.example.com/v1/chat/completions 的响应在 choices[0].message.content 处不是字符串，而是 null：{"id":"chatcmpl-...","choices":[{"index":0,"message":{"role":"assistant","content":null,"tool_calls":[...]}}]}
```

第二条直接说明了发生什么：模型没有返回文本，而是返回了工具调用——第 03 章要处理的正是这件事。第一条则会迫使读者回头加一行 `console.log`。这本书后面的每一次失败，都会按第二条的标准来写。

`HttpError` 还按状态码给出下一步：401 提示检查 `REIN_API_KEY`，404 提示检查 `REIN_BASE_URL` 是否指向端点根路径，429 说明是限流，5xx 说明请求本身可能没问题。这些不是聪明的推断，只是把每次都要重新想一遍的事写下来一次。

## 录制与测试

`ts/scripts/record.ts` 把一次真实的请求与响应落盘：

```bash
cd ts
npx tsx --env-file=.env scripts/record.ts --scenario hello
```

它写到 `fixtures/responses/<provider>/hello-1.json`，写盘前去掉 `authorization` 头、丢弃响应头里的账号与追踪标识、把密钥字面量从请求和响应体中抹掉。被动过的字段名记在文件的 `redacted` 数组里，读样本的人能看出哪里不是原样。除此之外响应体保持原貌——录制的价值全在形状的真实性上，一旦有人为整理，后面章节的对照就失去了依据。

模型 API 的形状会变。现在不录，第 04 章要对照两家差异时就无从写起。

有些端点要求额外的请求头。脚本用一个通用的 `--header name=value` 接收它们，可以重复传：

```bash
npx tsx --env-file=.env scripts/record.ts --scenario hello \
  --header x-opencode-session=rein-record-hello --header user-agent=rein/0.1
```

这样 `record.ts` 不必认识任何一家端点的专有约定，而主线的 `chat.ts` 也不会被某一家的要求污染。

录到什么就存什么，包括失败。仓库里现在有两份样本：`opencode-go/hello-1.json` 是一次成功调用，`openai/insufficient-quota-1.json` 是一个额度耗尽的 429——录制时那个账号恰好没有余额。失败样本照样有价值：`chat.ts` 对非 2xx 的处理从此有了一份真实响应可以对照，而不是只对着自己编的字符串做断言。脚本在录到非 2xx 时会警告并以非零码退出，提醒场景名要与录到的内容相符，别让失败样本顶着成功场景的名字入库。

测试在 `ts/tests/`，全程不访问外网：

```bash
npm run typecheck
npm test
```

五个文件对应五个层次。`config.test.ts` 检查三个变量各自缺失、为空、格式不对时的行为，其中一条专门断言"全空环境直接失败"——它守的是"不提供默认值"这个决定本身，而不是某段代码。`chat.test.ts` 用本地桩喂进各种响应，覆盖成功路径与四类失败，并断言错误信息里确实出现了路径和变量名。`transport.test.ts` 用回环地址上的临时 HTTP 服务检验 `fetch` 实现：起一个不响应的服务测超时，起完就关掉一个端口测连接失败。`record.test.ts` 离线检查录制命令的 provider 参数与默认推导结果，不发起请求。`recorded.test.ts` 回放 `fixtures/responses/` 里的真实样本：成功样本要能取出回答文本、模型名与 usage，429 样本要落到 `HttpError` 且服务端给的原因出现在错误信息里，两份样本都不含密钥。它断言的是形状而不是模型说了什么——回答内容每次都不同，把它固定下来只会得到一个下次就红的测试。

这些测试的作用不是证明代码今天能跑，而是在后面十五章改动这段代码时，能立刻说出哪一类行为变了。

## 这一章留下的东西

三个可以被后面直接继承的结构：一个只搬字节的 transport 接口、一组带现场信息的失败类型、一条不提供默认值的配置路径。第 03 章加工具调用时，工具执行的失败会加入同一组类型；第 05 章的循环会在同一个 transport 接口上跑；第 04 章会把 `chat.ts` 里那些散落的协议知识收拢成合同。

还没有做的事同样重要：没有 provider 适配器，没有统一消息协议，没有重试，没有流式输出。它们各自有自己的章节，提前做会让那些章节失去起点。

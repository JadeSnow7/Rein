# 03 做一个终端代码修改助手

上一章，模型已经能请求读取 `hello.cpp`、编译日志和有限的环境信息，并提出修复候选。我们也留下了一个权限问题：模型既能提出工具请求，也能在回答里说“已经修好”，但这些输出并不完全可靠。是否允许修改本地文件，必须由运行在本机的程序和使用它的人决定。

这一章先用最简单的人工审核：把候选保存为另一份文件，亲自找到它改了哪里。接着写一个只读的终端 diff 工具，让程序计算差异；最后接上明确的人工确认，接受后才写回，并编译运行。可以把它看成理解 Cursor 一类编码助手的最小练习；配套程序只处理一个 `hello.cpp`。

::: info 本章设计
配套程序按下面的约定写成：

- 差异由本地程序根据原文件和候选全文计算，不采信模型自报的改动范围。
- 只有用户在 `[y/N]` 提示后明确输入 `y`，才进入写入；放弃直接结束，不碰工作区。
- 写入前再读一次 `hello.cpp`，内容与生成候选时不同就拒绝；相同才备份、再写入。
- 验证只用固定的编译和运行命令，且只运行本轮新编译的程序。
:::

## 1、先人工审核模型的建议

继续从仓库根目录执行命令，沿用前两章的临时工作区。若想从本章重新开始，可以准备一个新副本：

```bash
hello_workspace=$(mktemp -d)
cp python/hello_world/fixtures/broken.cpp "$hello_workspace/hello.cpp"
```

先用固定入口编译一次，取得与当前源码对应的报错：

```bash
python/hello_world/.venv/bin/python python/hello_world/cli.py check --workspace "$hello_workspace"
echo $?
```

`check` 会读取练习源码，在临时目录中生成新的编译产物，捕获编译结果，并在工作区写入 `compiler.log`。它只在本轮编译成功后运行新产物，检查输出是否恰好是 `Hello, world!` 加换行。坏样本应编译失败，命令退出 `1`，不会运行先前留下的可执行文件。

这一步不访问模型。`check` 生成的日志分段记录 `compile exit=…` 和 `run exit=…` 及各自的输出，比第二章手工重定向的日志多了运行结果：程序编译成功却输出错误时，下一次诊断也能读到这一点。每次手工改变源码后，先重新运行 `check`，避免用旧报错解释新文件。

第二章的 `diagnose` 只提出候选，不写 `hello.cpp`。先把它的结果保存起来：

```bash
python/hello_world/.venv/bin/python python/hello_world/cli.py diagnose --workspace "$hello_workspace" --read-mode tool > "$hello_workspace/proposal.json"
python/hello_world/.venv/bin/python - "$hello_workspace/proposal.json" "$hello_workspace/candidate.cpp" <<'PY'
import json
import sys
from pathlib import Path

proposal = json.loads(Path(sys.argv[1]).read_text(encoding="utf-8"))
Path(sys.argv[2]).write_text(proposal["code"], encoding="utf-8")
print(proposal["reason"])
PY
```

`proposal.json` 保留候选和理由，`candidate.cpp` 是供审查的副本；原来的 `hello.cpp` 没有被修改。默认离线模式只演示缺分号样本。希望使用真实模型时，给 `diagnose` 加 `--mode live`；它会向服务发送源码、日志和有限环境信息，且建议可能与示例不同。

先读模型给出的理由，再分别打开两份源码。对于这个小文件，可以直接在终端加行号阅读：

```bash
nl -ba "$hello_workspace/hello.cpp"
nl -ba "$hello_workspace/candidate.cpp"
```

找出候选在哪一行增加了分号，也检查其余行有没有变化。人工审核至少回答：输出字符串是否还正确，是否只修复必要语法，是否新增了文件访问或命令执行。模型的理由只能帮助定位，不能代替阅读候选；它说“只改一行”时，也要自己核对。运行生成的 C++ 会执行本地程序，所以在编译运行前完成这次审查。

## 2、写一个对比改动的终端工具

逐行肉眼找改动可以完成第一次审核，但文件稍长就容易漏看。现在让 Python 读取**两份指定文件**，自己算出差异。先不要加入写回动作；这个工具只负责回答“哪里变了”。在仓库根目录运行下面的命令，创建练习目录里的 `review_diff.py`：

```bash
cat > "$hello_workspace/review_diff.py" <<'PY'
import difflib
import sys
from pathlib import Path

if len(sys.argv) != 3:
    raise SystemExit("用法: python3 review_diff.py 原文件 候选文件")
before_path, after_path = map(Path, sys.argv[1:])
before = before_path.read_text(encoding="utf-8")
after = after_path.read_text(encoding="utf-8")
diff = difflib.unified_diff(
    before.splitlines(keepends=True),
    after.splitlines(keepends=True),
    fromfile=str(before_path),
    tofile=str(after_path),
)
result = "".join(diff)
print(result if result else "两份文件没有差异。", end="" if result else "\n")
PY
cd "$hello_workspace" && python3 review_diff.py hello.cpp candidate.cpp; cd - > /dev/null
```

这段程序接收两个路径，读取全文，再用标准库 `difflib.unified_diff` 比较每一行。`keepends=True` 保留换行，文件名来自你实际比较的两个参数。模型只提供候选内容；**diff 由本地程序计算**，不信任模型自报的行号或改动范围。这个小工具会读取你指定的路径，只在自己的练习目录里使用；后面的成品入口仍限定 `hello.cpp`。

对缺分号样本，输出是：

```diff
--- hello.cpp
+++ candidate.cpp
@@ -1,5 +1,5 @@
 #include <iostream>
 
 int main() {
-    std::cout << "Hello, world!\n"
+    std::cout << "Hello, world!\n";
 }
```

`-` 表示原文件中被删除的行，`+` 表示候选中新增的行，前面是空格的是未改动的上下文。`---`、`+++` 是文件头；`@@ -1,5 +1,5 @@` 表示这一段对应原文件从第 1 行起的 5 行、候选从第 1 行起的 5 行。它们都不是 C++ 源码。把 diff 中的每一处变化与刚才人工看到的候选全文对照；如果出现意料外的变化，先停止，不要接受。

试着只改 `candidate.cpp` 里的输出文字，再运行 `review_diff.py`。它应同时指出分号修复与文字变化。随后用第一节的提取命令，从 `proposal.json` 重新生成 `candidate.cpp`，再继续。这个反例能检查工具有没有漏掉任务之外的改动。

## 3、把 diff 接到修改助手里

手写的小工具只负责对比。配套的 `edit` 入口把同样的计算接到诊断后面：展示原文件全文、候选全文，最后展示带上下文的 diff。完整文件带行号，差异保留加减号；接受与否仍由你决定。

```bash
python/hello_world/.venv/bin/python python/hello_world/cli.py edit --workspace "$hello_workspace" --color auto
```

这里再次诊断当前文件，候选可能与之前保存的 `proposal.json` 不同；以本次屏幕上显示的全文和 diff 为准。初次运行先选择放弃。配套实现的展示函数可以对照你写的只读工具阅读：

## 4、人工确认以后才能写入

先看一眼这一章要走完的全部状态。每一步都由固定的一方决定，失败时停在明确的位置：

```text
候选（模型提出，程序已校验形状）
  │
  ├─ 用户放弃 ─────────────────────────→ rejected：不读、不写、不备份
  │
  └─ 用户输入 y
       │
       ├─ 复查源文件：内容已变 ─────────→ source_changed：停止，不写入
       │
       └─ 内容未变 → 备份 → 写入候选
                               │
                               ├─ 写入出错 ──────→ write_failed
                               │
                               └─ 编译 ─ 失败 ──→ 保留日志，验证未通过
                                    │
                                    └─ 运行 ─ 超时或输出不对 → 验证未通过
                                         │
                                         └─ 输出正确、退出码 0 → 验证通过
```

候选显示后，程序等待终端输入。在 `[y/N]` 提示后输入 `y` 并回车表示接受；输入 `n`、直接回车或输入结束表示放弃，保留原文件。只有明确选择接受才会继续写入。

先做一次放弃实验：记录原文件摘要，运行编辑入口，在提示时选择放弃，再比较摘要。

```bash
python/hello_world/.venv/bin/python - "$hello_workspace/hello.cpp" <<'PY'
import hashlib
import sys
from pathlib import Path
print(hashlib.sha256(Path(sys.argv[1]).read_bytes()).hexdigest())
PY
```

上面的命令在放弃前、放弃后各执行一次，两次结果应相同，目录中也不应因为放弃而新增备份。这能确认“模型给出了建议”没有被程序偷偷变成“已经应用”。

再运行一次编辑入口，读过全文和差异后选择接受。程序接下来再读一次 `hello.cpp`，确认它仍与生成建议时读取的字节相同。如果等待期间你在编辑器里改了源文件，当前摘要就会不同。此时程序报告 `source_changed` 并停止，而不是用旧候选覆盖新内容；重新生成建议需要从新的文件重新开始。

通过检查后，程序把刚才核对过的字节存为一个独立备份，再写入候选。结果会显示备份路径；备份文件名带时间戳，第二次接受不会覆盖第一次的备份。放弃不会创建备份，接受也不会改动工作区中的其他源码。

## 5、把“写好了”变成“验证过了”

写入成功后，编辑入口调用与第一节相同的 `check` 流程，也就是状态图的下半段。程序用参数数组启动固定命令，而不是执行模型提供的命令字符串。核心调用形状如下；临时目录和异常处理由完整实现负责：

```python
subprocess.run(
    ["c++", "-std=c++17", "hello.cpp", "-o", output_path],
    cwd=workspace,
    capture_output=True,
    text=True,
    timeout=10,
)
```

`capture_output` 取得标准输出与错误输出，`returncode` 表示进程结果，`timeout` 限制等待。配套程序限制编译最多等待 10 秒，运行最多等待 2 秒。模型没有传入编译器路径、额外参数或 shell 指令的入口。

完整实现位于 `python/hello_world/core.py`。按“诊断 → 展示 → 接受决定 → 应用 → 检查”的顺序阅读，再回到 `cli.py` 看参数如何连到这些函数。相比第二章，这次新增的是显示、人工决定和写入验证；模型请求与读取工具仍然复用原来的实现。

完成条件必须同时满足：

| 检查 | 要求 |
| --- | --- |
| 编译 | 本轮编译退出码为 `0` |
| 运行 | 本轮产物正常退出，退出码为 `0` |
| 输出 | 标准输出恰好是 `Hello, world!\n` |
| 修改 | 用户明确接受，只更新约定的源码，并保留修改前备份 |

“接受了候选”与“验证通过”是两个不同的结果。模型说已经修复、文件保存成功，或者编译成功，都不足以单独判定整个任务完成。

## 6、失败以后怎样继续，完成一次完整实战

如果候选仍然不能编译，程序保留刚生成的 `compiler.log`，显示失败，不报告成功，也不静默恢复你已经接受的文件。备份仍在；你可以查看它，决定恢复还是继续修复。选择继续时，再运行同一个编辑命令：它重新读取当前源码和新日志，产生新的候选，你再次审查并决定。上一轮的接受只针对上一份候选，不代表下一次修改也自动获得同意。

如果编译已经成功，但运行输出不对，编译日志本身未必有报错。程序把运行结果写进日志，判断“编译成功但任务不合格”，不会给模型一句虚假的编译错误。运行超时同样保留具体阶段，不能归为网络超时。读结果时先确定失败发生在哪一步，再决定是修正配置、补足环境、重新提供资料，还是让模型继续修改代码。

离线替身只会处理本章的缺分号样本；对已经修好的文件再运行 `edit`，它会报告 `unsupported`。真实服务可能返回不同修改，每次都要重新审查。练习中建议最多尝试三轮，仍未完成就停下来检查原因，不把重试次数当成修复能力。

现在用一个新临时目录，从坏样本重复完整流程：

1. 执行 `check`，确认真实编译失败并生成日志。
2. 执行 `edit`，检查原文件全文、候选全文和红绿差异。
3. 第一次选择放弃，确认源码摘要未变、没有新增备份。
4. 第二次选择接受，确认备份包含旧源码、新文件包含修复。
5. 检查本轮编译、运行退出码及输出，确认全部达到要求。
6. 使用 `--color never` 再查看一次，确认没有颜色仍能理解内容。

然后做两个反例。第一个是在等待接受时用编辑器改动源文件，再输入 `y`，确认过期候选不会覆盖它。第二个是手工把输出改成别的文字，运行 `check`：程序应能编译，却因输出不符合要求而失败。这两个反例分别检查修改依据和任务验收，单纯跑一次正确样本无法覆盖它们。

配套自动检查仍从仓库根运行：

```bash
python/hello_world/.venv/bin/python -m unittest discover -s python/hello_world/tests -v
```

这组检查包含读取边界、消息内容、候选校验、拒绝与接受、源文件变化、颜色关闭以及编译运行结果。受控模型响应验证的是程序行为，真实模型的建议质量和新手独立跟做仍需分别记录。

## 7、第一部分总作业：写一个“简易 Cursor”

用你熟悉的任何语言，写一个可以在终端运行的简易代码助手。给它一个你自己准备的小项目目录和一个修改目标，它能**自动读取项目中的目标文件**，把当前内容交给模型，输出修改建议，并显示原文件与候选的 diff。第一版可以只读，不要求写回；不要让模型拿到整个硬盘或密钥文件。可以继续使用本章的 C++ Hello World，也可以换成另一种语言的小项目。

最低完成条件是：

1. 运行时指定项目目录和目标文件；程序自行读取当前文件，不靠你手工粘贴源码。读取失败或目标越界时给出明确错误。
2. 模型给出候选内容与理由；终端标明建议来自真实模型还是固定离线替身，不把离线样本称为真实修复效果。
3. 程序用原文件与候选计算 diff，标出文件名和改动位置。原文件保持不变；至少用一次额外改动验证 diff 能揭示意料外的变化。
4. 保存一次运行记录：输入目标、读到的文件、候选、diff、人工审查结论，以及你实际执行过的检查。没有执行的编译或测试不要写成“已验证”。

愿意继续扩展时，再加入本章的 `[y/N]` 确认、接受前复查原文件、备份、写回和项目原有测试。每次候选都单独确认；确认写入与验证通过仍是两件事。

如果你已经在用 Claude Code、Codex 这类代码助手，可以换一种做法：先用一页纸写下这个小工具的设计（读哪些文件、调用什么、diff 怎样展示、什么情况必须报错），再交给代码助手实现，最后用上面的四条完成条件检查它的产出。这正是下一章开始的工作方式。

## 本章边界卡

| 角色 | 本章结束时 |
| --- | --- |
| 模型 | 读取现场、给出候选与理由；不能决定是否写入 |
| 程序 | 计算 diff；只在明确接受后复查、备份、写入；用固定命令编译、运行并判定结果 |
| 用户 | 审查全文与差异，决定接受或放弃；失败后决定是否再来一轮 |
| 还不能 | 多文件修改、自主多轮修复、通用权限与持久批准、中途取消 |

前三章至此连成一条线：发送请求生成代码，读取真实文件与报错，审核建议并计算差异，明确确认后才写入，再用本地执行判断结果。保留练习前后的源码、编译日志、一次拒绝和一次接受的记录，以及模型来源说明。`python/part1/` 中的旧 README 只读建议器和 S1 清单属于前一版练习，仍可对照，但不能替代本轮记录。

回头看，这四个状态目前只靠 Python 的函数返回值和几个字符串维持，例如 `"accepted"`、`"rejected"`。只处理一个文件、一轮决定时还够用；要加入连续行动、预算和取消，就得把它们明确写成状态。下一章[Agent 的核心能力](./agent-capabilities.md)先对照代表性编码 Agent 整理这些能力，再换一种工作方式：**由我们确定设计和验收条件，让 Claude Code、Codex 这类代码助手编写代码**，把这里的行为等价地迁移到 Rust。

# 03 做一个终端代码修改助手

上一章，模型已经能请求读取 `hello.cpp`、编译日志和有限的工作区检查结果，并提出修复候选。不过你还得在回答和编辑器之间来回复制，自己找出改动，再保存、编译。现在把这些动作接成一个可以使用的小工具。

我们做一个终端里的简易代码助手：展示文件全文与修改段落，等待你接受或放弃，接受后才保存，再编译运行。可以把它看成理解 Cursor 一类编码助手的最小练习；本章只处理一个 `hello.cpp`，没有多文件编辑、任意命令执行或后台自主修复。

## 1、接上同一份出错程序

继续从仓库根目录执行命令，沿用前两章的临时工作区。若想从本章重新开始，可以准备一个新副本：

```bash
hello_workspace=$(mktemp -d)
cp python/hello_world/fixtures/broken.cpp "$hello_workspace/hello.cpp"
```

这一章将编译与结果检查收进一个固定入口：

```bash
python3 python/hello_world/cli.py check --workspace "$hello_workspace"
echo $?
```

`check` 会读取练习源码，在临时目录中生成新的编译产物，捕获编译结果，并在工作区写入 `compiler.log`。它只在本轮编译成功后运行新产物，检查输出是否恰好是 `Hello, world!` 加换行。坏样本应编译失败，命令退出 `1`，不会运行先前留下的可执行文件。

这一步不访问模型。日志现在由程序在验证过程中生成，后面的诊断读取同一份日志。每次手工改变源码后，先重新运行 `check`，避免用旧报错解释新文件。

接着运行编辑入口：

```bash
python3 python/hello_world/cli.py edit --workspace "$hello_workspace" --color auto
```

默认离线模式只演示缺分号样本的修复流程。模型部分使用确定性替身，文件读取、差异计算、用户输入、写入和 C++ 编译运行都是真实的本地动作。希望使用真实模型时，改用第一章虚拟环境的 Python，并加上 `--mode live`；它会向服务发送源码、日志和有限环境信息。

先不要急着接受。看清下一节的三种展示，再作选择。

## 2、展示全文，再突出修改段落

只看一小段红绿文本，可能不知道修改发生在哪个文件、是否顺便删除了其他内容。因此，终端先显示原文件全文，再显示候选文件全文，最后显示差异。完整文件带行号，差异保留上下文。

候选来自模型返回的两个字段：

```json
{
  "code": "完整的候选 C++ 源码",
  "reason": "为什么需要这次修改"
}
```

对于 Hello World 这样的小文件，让模型返回全文比要求它生成一份严格补丁更容易理解。模型负责候选内容，**差异由 Python 比较原文件与候选生成**。程序不会相信模型自报的行号或“我只改了一行”。

核心算法来自标准库 `difflib`。下面的解释片段中，`before` 与 `after` 都是已经取得的字符串：

```python
import difflib

lines = difflib.unified_diff(
    before.splitlines(keepends=True),
    after.splitlines(keepends=True),
    fromfile="hello.cpp（修改前）",
    tofile="hello.cpp（候选）",
)
print("".join(lines))
```

缺分号样本的关键差异应类似下面这样：

```diff
-    std::cout << "Hello, world!\n"
+    std::cout << "Hello, world!\n";
```

删除行显示为红色并保留 `-`，新增行显示为绿色并保留 `+`。差异中的 `---`、`+++` 是文件头，`@@` 给出改动附近的行范围，它们不是 C++ 源码。颜色有助于扫读，但不能承担唯一的含义。

`--color auto` 在适合显示颜色的终端启用颜色；需要复制日志时可以用 `--color never`，强制检查颜色时用 `--color always`。无论是否有颜色，都应该能通过文件名、行号和加减号判断改动。

审查时至少回答三个问题：输出字符串是否还正确；是否只修复必要语法；是否新增了文件访问、命令执行等本任务不需要的行为。运行模型生成的 C++ 是执行本地程序，固定编译命令并不意味着生成的源码自动安全。

## 3、让用户决定接受或放弃

候选显示后，程序等待终端输入。在 `[y/N]` 提示后输入 `y` 并回车表示接受；输入 `n`、直接回车或输入结束表示放弃，保留原文件。只有明确选择接受才会继续写入。

先做一次放弃实验：记录原文件摘要，运行编辑入口，在提示时选择放弃，再比较摘要。

```bash
python3 - "$hello_workspace/hello.cpp" <<'PY'
import hashlib
import sys
from pathlib import Path
print(hashlib.sha256(Path(sys.argv[1]).read_bytes()).hexdigest())
PY
```

上面的命令在放弃前、放弃后各执行一次，两次结果应相同，目录中也不应因为放弃而新增备份。这能确认“模型给出了建议”没有被程序偷偷变成“已经应用”。

再运行一次编辑入口，读过全文和差异后选择接受。程序接下来做两项检查：候选是否有效，当前 `hello.cpp` 是否仍与生成建议时读取的字节相同。

如果等待期间你在编辑器里改了源文件，当前摘要就会不同。此时应该报告 `source_changed` 并停止，而不是用旧候选覆盖新内容。重新生成建议需要从新的文件重新开始。

通过检查后，程序创建一个独立备份，再写入候选。结果会显示备份路径；它保存的是本轮接受前的原始字节。备份文件名不会因第二次接受而覆盖第一次备份。放弃不会创建备份，接受也不会改动工作区中的其他源码。

应用函数的实际实现如下。阅读时沿着“放弃返回、基线检查、备份、保存”四个动作走；入口已经把用户选择转换成 `accept`，模型不能自己设置它：

<<< ../../python/hello_world/core.py#apply_candidate

这套检查面向自己控制、没有其他程序同时写入的练习目录。摘要复查能发现等待期间的变化，但不构成通用文件系统事务，也不能保证检查和写入之间绝对没有并发竞争。后面的可信 Harness 部分会把这些边界扩展到真实项目。

## 4、把“写好了”变成“验证过了”

写入成功后，编辑入口调用与第一节相同的 `check` 流程。验证顺序不能颠倒：

```text
候选通过检查 → 用户接受 → 复查源文件 → 保存备份 → 写入候选
             → 编译新源码 → 编译成功才运行 → 核对输出和退出码
```

程序用参数数组启动固定命令，而不是执行模型提供的命令字符串。核心调用形状如下；临时目录和异常处理由完整实现负责：

```python
subprocess.run(
    ["c++", "-std=c++17", "hello.cpp", "-o", output_path],
    cwd=workspace,
    capture_output=True,
    text=True,
    timeout=10,
)
```

`capture_output` 取得标准输出与错误输出，`returncode` 表示进程结果，`timeout` 限制等待。配套程序限制编译最多等待 10 秒，运行最多等待 2 秒。模型没有传入编译器路径、额外参数或 shell 指令的入口。

完整实现位于 `python/hello_world/core.py`。按“诊断 → 展示 → 接受决定 → 应用 → 检查”的顺序阅读，再回到 `cli.py` 看参数如何连到这些函数。相比第二章，这次新增的是显示、人工决定和写入验证；模型请求与读取工具仍然复用原来的实现。

完成条件必须同时满足：

| 检查 | 要求 |
| --- | --- |
| 编译 | 本轮编译退出码为 `0` |
| 运行 | 本轮产物正常退出，退出码为 `0` |
| 输出 | 标准输出恰好是 `Hello, world!\n` |
| 修改 | 用户明确接受，只更新约定的源码，并保留修改前备份 |

“接受了候选”与“验证通过”是两个不同的结果。模型说已经修复、文件保存成功，或者编译成功，都不足以单独判定整个任务完成。

## 5、失败后把结果带回下一轮

如果候选仍然不能编译，程序保留刚生成的 `compiler.log`，显示失败，不报告成功，也不静默恢复你已经接受的文件。备份仍在；你可以查看它，决定恢复还是继续修复。

选择继续时，再运行同一个编辑命令。它重新读取当前源码和新日志，产生新的候选，你再次审查并决定。上一轮的接受只针对上一份候选，不代表下一次修改也自动获得同意。

```bash
python3 python/hello_world/cli.py edit --workspace "$hello_workspace" --color auto
```

离线替身只会处理本章的缺分号样本，不能用它反复尝试其他问题。真实服务可能返回不同修改；每次都要重新审查。练习中建议最多尝试三轮，仍未完成就停下来检查原因，不把重试次数当成修复能力。程序本身每次调用也有模型请求次数上限。

如果编译已经成功，但运行输出不对，编译日志本身未必有报错。程序会把运行结果纳入验证反馈，判断“编译成功但任务不合格”，不能给模型一句虚假的编译错误。运行超时同样需要保留具体阶段，不能归为网络超时。

编译、运行与诊断会产生不同状态。读结果时先确定失败发生在哪一步，再决定是修正配置、补足环境、重新提供资料，还是让模型继续修改代码。

## 6、完成一次完整实战

先保留刚才的结果，再用一个新临时目录从坏样本重复完整流程：

1. 执行 `check`，确认真实编译失败并生成日志。
2. 执行 `edit`，检查原文件全文、候选全文和红绿差异。
3. 第一次选择放弃，确认源码摘要未变、没有新增备份。
4. 第二次选择接受，确认备份包含旧源码、新文件包含修复。
5. 检查本轮编译、运行退出码及输出，确认全部达到要求。
6. 使用 `--color never` 再查看一次，确认没有颜色仍能理解内容。

然后做两个反例。第一个是在等待接受时用编辑器改动源文件，确认过期提案不会覆盖它。第二个是手工把输出改成别的文字，运行 `check`：程序应能编译，却因输出不符合要求而失败。这两个反例分别检查修改依据和任务验收，单纯跑一次正确样本无法覆盖它们。

配套自动检查仍从仓库根运行：

```bash
python/hello_world/.venv/bin/python -m unittest discover -s python/hello_world/tests -v
```

这组检查包含读取边界、消息内容、候选校验、拒绝与接受、源文件变化、颜色关闭以及编译运行结果。受控模型响应验证的是程序行为，真实模型的建议质量和新手独立跟做仍需分别记录。

## 7、留下下一阶段可以复用的结果

到这里，前三章已经连成一条完整的小任务：发送请求生成代码，读取现场提出修复，展示差异，由用户决定写入，再用本地执行验证结果。

保存练习前后的源码、编译日志、一次拒绝和一次接受的记录，以及模型来源说明。配套 README 列出入口与检查方法。新配套目录是 `python/hello_world/`；`python/part1/` 中的 README 只读建议器和 S1 清单属于前一版练习，仍可用于对照，但不能替代本轮的写入和编译验证记录。

# 第六部分：直击 Agent 痛点——架构设计与持续演进

本部分承接第五部分 S5：同一“预览小站”已经能从 IDE 发起任务、查看 diff、批准和验证。现在研究 Agent 如何理解项目、提出有依据的设计、记住决定并连续修改而不破坏仍有效的要求，最后用受控实验判断是否真的改善。阶段成果 S6 是计划中的设计依据、设计记忆、连续演进轨迹和比较方案，不是当前仓库已经完成的真实多文件 Agent 产品。

本部分也是全书分工的转折（D18）：前五部分由人确定设计、AI 编写代码；这里研究把设计也交给 Agent 的完全 vibe coding 需要哪些前提。25–29 分别检验其中一项：理解架构、有依据地设计、记住设计理由、持续修改不破坏系统、证明确有进步。实验结论只以同条件对照的实际产物为准。

章节关系分两条再汇合：25 先建立模块职责、数据流、依赖、接口、约束和来源；26 在此基础上比较备选方案并做小原型；27 把理由、前提和失效条件保存成可复审记忆；28 让下一轮继承上一轮真实产物，持续检查历史要求并记录回归；29 冻结普通助手、设计记忆、完整闭环三组，评测新需求、历史回归、返工和实际成本。`docs/chapters/task-planning.md` 的已有正文主要支持 26–27 的设计决策复审，不能当作运行时计划或长期能力证据。

现有 `scripts/architecture/` 与 `scripts/evolution/` 只提供本地工具和单文档离线校准。其原始证据显示 12 轮正例通过、负例第 7 轮检测到 `legacy-contract` 回归，且 token、cost、人工时间为 `null`；这些结果验证记录机制，不证明 AI 架构能力提升。所有后续实验都必须冻结模型、工具权限、预算、任务序列和独立检查，使用多条序列与多次重复，并保留失败、未知、返工和人工介入。

## 25 让 Agent 理解项目的架构

### 进入条件

读者已完成第五部分，能从 IDE 观察任务状态、diff、批准和验证结果，拥有预览小站的实际文件、运行命令和 S5 产物。当前 runner 的单文档 seed 不是多文件项目理解证据；本章先交付分析模型和可核对的项目地图。

### 问题与失败现象

Agent 看到一个文件就修改局部文本，却不知道模块职责、数据流、依赖、接口、约束和来源。结果可能通过局部检查，却破坏配置到启动入口的关系；一份没有来源的“架构摘要”也无法判断是当前代码还是旧记忆。

### 核心概念

项目理解是一组带来源和版本的事实：模块及职责、入口/出口、数据流、依赖方向、接口字段、运行约束、测试/验证规则与未知项。每条事实绑定文件路径、符号或配置位置、摘要和观察时间；图是导航和待核查清单，不自动证明架构正确。理解输出要区分已读源码、已有执行证据、计划新增和尚未核实。

### 小节安排

1. **从预览小站画模块地图**：列出页面、表单校验、配置、启动入口和检查器的职责；IDE 与 Harness 只作为外部调用上下文。
2. **分开启动流、业务流和检查流**：配置供启动入口加载页面；用户输入经校验后提交；独立检查器驱动输入并观察结果，不把这些不同方向强连成一条调用链。
3. **依赖与接口约束**：检查页面到配置、配置到启动入口、检查器到结果的关系，以及哪些字段需要版本和摘要。
4. **为事实绑定来源**：用代码、配置、事件和实验记录分别标注证据强度。
5. **理解快照与 `F25`**：冻结地图、未知列表、输入 digest 和后续复核问题。

### 贯穿示例

输入是S5任务及项目快照。Agent读取页面、校验逻辑、配置、启动脚本和检查器，分别核对“配置→启动入口→页面资源”“用户输入→校验→提交副作用”“检查器→测试输入/结果观察”三条关系。箭头是本轮建议的分析起点，只有实际源码或执行记录支持时才成为事实；IDE发起任务与Harness生成候选画在外部边界。输出每个结论的路径/摘要及未知项，不把建议结构冒充现有实现。

### 实现增量

计划新增教学格式 `ArchitectureMap`、`ModuleFact`、`FlowEdge`、`InterfaceFact`、`Constraint`、`SourceRef` 和 `UnknownFact`。它们是分析产物建议，不替代 `architecture/decisions.json` 的正式登记。读取动作复用第三部分权限和证据绑定；多文件索引、符号解析、图持久化和 runtime 接入均待设计，不能从单文档 runner 推断已实现。

### 验收设计

正常：地图覆盖声明范围，事实能回指实际文件和事件，数据流方向与已观察调用一致。失败：缺文件、过期摘要、循环依赖、矛盾接口和未读取事实必须保留未知或冲突，不由模型补齐。回归：S5 的批准、验证、C08 脏缓冲区语义不被架构摘要绕过；检查同一输入重复生成的来源集合稳定。

### 产物与练习

产物是预览小站架构地图、数据流图、接口/约束表、来源清单、未知列表和计划 `F25`。练习要求删去唯一来源后重新生成，证明相关事实降为未知；完成标准是至少覆盖模块、数据流、依赖、接口、约束、来源六类信息，并能解释一条不确定结论。

### 交接

向 26 交付带来源的当前地图、候选边界和未知列表。26 只能把已核实事实作为设计前提，必须把地图中的假设列为待验证项；任何实际代码变更仍回到第五部分 diff、批准和验证。

### 复用与证据

复用 [设计决策检查器说明](../../scripts/architecture/README.md)、[任务审查正文](../../docs/chapters/task-planning.md)、[维护会话契约](../../contracts/maintenance-session-v1.md) 和 S5 的产品事件记录。决策检查器的 `applicable` 只表示声明摘要匹配，不证明架构正确；`ArchitectureMap`、多文件来源和 F25 是计划新增，当前单文档证据不能扩大结论。

## 26 让 Agent 做出有依据的设计

### 进入条件

读者已有 25 的项目地图、来源、未知项和 S5 的可运行纵切，知道设计前提必须绑定实际事实。已有 `docs/chapters/task-planning.md` 的决定登记和失效检查可复用，但其正文不是本章运行时计划完成证据。

### 问题与失败现象

Agent 直接选一个“看起来现代”的架构，省略备选方案、代价和关键假设；接口改变后旧前提失效，却仍引用原结论。一次成功的原型也可能只证明样例输入，不能证明后续变化下的选择更好。

### 核心概念

有依据的设计记录问题、候选方案、取舍、关键假设、适用范围、来源、小原型和后续变化检查。页面内直接解析配置初期简单，独立的规范化/校验接口增加代码却可能降低版本变化的影响，是否值得须在本项目上比较。设计结论与机器摘要匹配、人类采纳状态、实验结果分别记录；现有core/driver讨论仅作为同类取舍的来源侧栏。

### 小节安排

1. **定义设计问题与约束**：从预览小站页面配置解析、表单错误展示和启动入口兼容列出不可违反条件。
2. **比较两个项目方案**：对照页面直接解析校验与规范化配置/独立校验边界，记录成本和风险。
3. **写关键假设和替代方案**：为配置版本、错误接口和启动兼容性标适用前提、反例和来源。
4. **做两个小原型再复审**：分别测试非法字段映射、v2/v1 兼容和校验器替换后的接口变化。
5. **设计决策与 `F26`**：登记人类状态、机器状态、变化触发器和后续检查。

### 贯穿示例

问题是“预览小站要在页面内直接解析配置并校验时，如何保持配置错误可见且不污染启动入口”。方案 A 在页面内直接解析并即时校验；方案 B 先规范化配置，再交给独立校验边界。假设包括配置格式变更频率、错误是否需要逐字段展示、启动入口是否继续接受旧配置。小原型一模拟非法字段和空值的错误映射，小原型二模拟配置 v2/v1 兼容与校验器替换；后续检查接口字段、错误码和启动调用是否变化。core/driver 方案只作来源侧栏对照，不能声称是预览小站实现。

### 实现增量

计划新增DesignQuestion、Alternative、Tradeoff、Assumption、PrototypeResult、DecisionRecord与ReviewTrigger等分析格式。复用architecture/decisions.json字段模式，在目标项目练习副本建立自己的登记，不能把小站决定冒写成Rein仓库已采纳决定。小原型在独立副本比较两种校验接口，不改变S5正式产物；decisions.mjs只读检查摘要，不替代设计评审。

### 验收设计

正常：至少两个可行方案、明确取舍、来源和小原型输出，结论能说出适用条件。失败：缺假设、来源不足、原型与问题不对应、摘要变更和未知副作用不得自动标 accepted。回归：25 的地图事实仍可追溯；决策前提变化时保留 `review_required`/`undetermined`，不刷新旧记录。

### 产物与练习

产物是设计问题说明、方案矩阵、假设表、小原型记录、复审清单和计划 `F26`。练习要求在配置 v3 或校验错误接口变化后重做选择，写出哪些前提失效及新检查；完成标准是每个取舍都有证据，机器摘要匹配与人类采纳状态明确分开。

### 交接

向 27 交付已采纳或待审的决定、理由、前提、来源、失效条件和原型记录。27 要保留旧版本历史，不能把当前 hash 写回旧记录消除告警；向 28 交付可用于持续回归的检查和设计约束。

### 复用与证据

复用 [架构决策检查器源码](../../scripts/architecture/decisions.mjs)、[任务计划正文](../../docs/chapters/task-planning.md) 和 [实现规格](../../records/REIN-EVOLUTION-20260922/implementation-spec.md)。源码和历史记录是已有实现/证据入口；`applicable` 不等于正确，新的方案比较、原型和 F26 验收是计划新增。

## 27 让 Agent 记住设计理由

### 进入条件

读者已有 26 的方案、理由、前提、来源和小原型，理解设计结论可能随代码与需求变化。现有登记表可保存决定和摘要，但需要把“为什么、何时失效、何时复审”变成可读取的设计记忆。

### 问题与失败现象

只保存“页面先规范化配置再独立校验”会丢掉当初为何选择、哪些条件成立以及考虑过什么替代方案。反过来，摘要仍匹配也不证明理由继续适用；把人工 `accepted` 和机器 `applicable` 混为一谈，会把检查器误当评审者。

### 核心概念

设计记忆包含决定、理由、适用范围、关键前提、来源、替代方案、失效条件、复审触发器、人工生命周期和机器检查结果。摘要是事实变化的触发器，不是理由正确性的证明；`accepted` 是维护者状态，`applicable`/`review_required`/`undetermined` 是机器观察。复审必须产生新版本并保留旧记忆。

### 小节安排

1. **从决定写出理由**：把 26 的选择拆成可被后续读者检查的事实和取舍。
2. **绑定前提与来源**：使用仓库内普通文件和 SHA-256，解释路径/符号链接限制。
3. **区分人类状态与机器状态**：演示 accepted 但 review_required 的组合。
4. **失效、替代与历史保留**：需求变化时新增记录，旧记录不覆盖。
5. **记忆快照与 `F27`**：保存读取输入、复审结果和未决定问题。

### 贯穿示例

登记预览小站“页面提交先经过规范化配置与独立校验，再进入启动入口”，理由是让字段错误可见并保持旧配置兼容；前提绑定配置 schema、校验器和启动入口文件摘要，复审条件是配置 v3、错误接口或启动参数变化。改变其中一个文件后，沿用当前决策工具输出 `review_required`，即使人工状态仍 `accepted`；读者必须重新评审而不能只刷新摘要。core/driver 的决策可作为工具链侧栏记忆，不能替代这个项目决定。

### 实现增量

复用 `architecture/decisions.json` 的登记字段和 `decisions.mjs` 的只读检查；计划新增版本链、记忆读取视图、`ReviewRecord` 和来源/前提的教学展示。机器只读仓库内普通文件，不执行登记内容；跨项目记忆、多文件语义索引和自动采纳待设计。

### 验收设计

正常：理由、前提、来源、失效条件和状态可独立读取，前提匹配输出 `applicable`。失败：摘要变化、缺失前提、空前提、畸形 ID/hash、符号链接和重复记录保留明确状态，不能自动接受。回归：26 的替代方案和 25 的来源映射未被覆盖；旧决定仍可追溯。

### 产物与练习

产物是版本化设计记忆、状态对照表、变更后的复审记录和 `F27`。练习要求构造“人类 accepted + 机器 review_required”和“proposed + applicable”两例，写出各自允许的下一步；完成标准是不能从任何单一状态推断设计正确。

### 交接

向 28 交付当前有效约束、活动历史检查、复审触发器和退役规则。28 必须在每轮继承并检查它们；若历史需求确实退役，要保存理由、来源和版本，不把旧检查静默删掉。

### 复用与证据

复用 [架构工具 README](../../scripts/architecture/README.md)、[决策工具源码](../../scripts/architecture/decisions.mjs)、[已采纳决策回执](../../records/REIN-EVOLUTION-20260922/evidence/accepted-decisions.json) 和 [决策复审记录](../../records/REIN-EVOLUTION-20260922/evidence/decision-review.md)。这些证明工具曾按声明运行，不证明设计理由正确或 Agent 会主动读取记忆；版本化记忆与 F27 为计划新增。

## 28 让 Agent 持续修改而不破坏系统

### 进入条件

读者已有 25–27 的项目地图、设计选择和可复审记忆，以及第五部分 S5 的可观察修改/验证流程。现有演进 runner 只支持单文档离线轨迹；多文件工具、任务隔离和真实 Agent 适配器仍待设计。

### 问题与失败现象

新需求通过，却悄悄破坏旧接口、配置或历史检查；下一轮重新从 seed 开始，导致“连续演进”只是重复演示。适配器退出 0 也可能输出错误产物；把失败或未知轨迹改写成成功，会污染后续输入和实验结论。

### 核心概念

连续演进要求后一轮 input digest 等于前一轮实际 output digest，任务与输出完整留证；每轮进行影响分析、接口演进、分步重构、兼容迁移、历史回归和新需求检查。活动检查自动继承，退役须有非空理由；失败、未运行、仍失败和未知保留原状。文件数/行数只作辅助指标。多文件演进必须先冻结操作 allowlist、逐文件基线、变更清单、批准绑定、部分写入和未知处理；13 的单文件候选/apply 边界不自动扩展到新增、删除、重命名或跨文件原子性。

### 小节安排

1. **冻结第一轮与继承规则**：用 runner 的 seed、round input/output 和 digest 追踪真实产物；先说明这只是单文档校准。
2. **规划预览小站多轮演进**：按页面校验模块、配置版本、异步校验、取消和接口迁移拆分影响范围。
3. **保留兼容迁移与历史检查**：新增检查、持续旧检查、带理由退役，并冻结逐文件 allowlist 与批准。
4. **处理失败、回归和未知**：区分 validator/check 非零可进入下一轮、适配器错误/输入篡改/无输出停止及后续 notRun。
5. **连续快照与 `F28`**：记录每轮证据、失败轨迹、成本 null 和复审入口。

### 贯穿示例

分开看两层证据。现有 runner 的单文档 12 轮正/负 fixture 只校准继承、检查持续和回归记录：正例通过，回归例第 7 轮触发 `legacy-contract`，不能称为 S5 多文件实验。计划中的 S5 序列沿同一预览小站执行：r01 提取表单校验模块；r02 引入配置 v2 并兼容 v1；r03 把校验改为异步；r04 加入取消和迟到结果处理；r05 分步迁移页面到新校验接口；r06 依据明确来源退役旧配置。每轮记录输入、改动文件和基线、新检查、持续历史要求与来源，后一轮 input digest 必须等于前轮实际 output digest。

| 计划轮次 | 输入与变更范围 | 新检查 | 必须保留的历史要求 |
| --- | --- | --- | --- |
| r01 | S5项目；在扩展后的操作合同内提取校验模块、更新页面调用 | 独立模块与页面调用行为一致 | 空/空格拒绝、有效值只提交一次、README命令仍可用 |
| r02 | r01实际产物；增加配置v2规范化和v1适配 | 两个版本合法配置均可加载，非法字段错误可定位 | r01与S5全部仍有效规则 |
| r03 | r02实际产物；校验接口异步化，保留兼容包装 | 延迟/失败返回可见，不提前提交 | 配置v1/v2兼容、空输入和单次提交 |
| r04 | r03实际产物；加入取消和请求身份 | 取消后的迟到结果不触发提交，不伪造远端撤销 | 正常异步校验与先前业务检查 |
| r05 | r04实际产物；页面分步迁移到新接口，保留旧适配层 | 新旧调用点合同测试、每个小步可回归 | r01–r04规则，不因重构降低断言 |
| r06 | r05实际产物；仅在明确退役需求已登记时移除v1入口 | 旧配置返回明确迁移提示；v2行为不变 | 仅退役指定v1兼容检查，其余持续；记录来源、版本和替代检查 |

每轮先比较影响到的模块、调用点与设计前提，再产候选清单。多文件写入采用有界工作副本与逐文件读回；不假定事务原子性。发生部分写入时保留清单和实际状态，停止并核对；后轮只有明确记录了恢复产物才能继续，不能悄悄回到seed。独立复验仍执行未退役检查。

### 实现增量

复用 `scripts/evolution/runner.mjs` 的显式 argv、无 shell 子进程、全新 outputDir、每轮 `result.json`、输入/输出 hash、原始 stdout/stderr、regressions、stillFailing、elapsedMs 和 `null` 成本。当前规则是：validator/check 非零保留失败产物并可进入下一轮；adapter 错误、输入或任务篡改、无输出/输出被改写则停止轨迹，剩余轮次 `notRun`，绝不偷换 seed。计划新增多文件 `ProjectSnapshot`、逐文件 allowlist/基线、部分写入恢复和真实 Agent adapter；当前实现不支持这些能力，不得提前声称。

### 验收设计

正常：连续继承、活动检查、validator 独立运行和新要求通过均可由报告复算；validator/check 非零时仍保留产物并明确是否进入下一轮。失败：历史回归、仍失败、适配器错误、超时、输入/任务篡改、输出篡改、重叠路径和重复报告路径按实际状态保存；前置 allowlist、逐文件基线、批准和部分写入未知处理未冻结时不得进入多文件实验。回归：单文档基准的 24 轮输入/任务/输出保护、C09 历史要求和 S5 的批准验证语义。

### 产物与练习

产物是影响分析表、接口迁移计划、现有单文档 12 轮正/负校准报告、计划中的 S5 六轮多文件序列说明、失败轨迹和 `F28` 快照。练习要求在不改 seed 的情况下加入新检查并制造历史回归，确认 `regressions` 与 `stillFailing` 分开；完成标准是后轮 input digest 由前轮真实 output 产生，失败不被覆盖。

### 交接

向 29 交付冻结的序列、任务、活动检查、每轮事实和成本字段，明确哪些是离线校准、哪些仍为未知。29 必须以同一输入/预算/权限建立比较组，不得把正例校准报告直接当 AI 效果基线。

复用 [演进工具说明](../../scripts/evolution/README.md)、[实现规格](../../records/REIN-EVOLUTION-20260922/implementation-spec.md)、[演进校准回执](../../records/REIN-EVOLUTION-20260922/evidence/accepted-calibration.json) 和 [逐轮报告](../../records/REIN-EVOLUTION-20260922/evidence/calibration-final/report.json)。这些是已有离线执行证据：能证明继承和回归记录机制，不证明多文件 Agent、盲测、隔离或能力提升。

## 29 如何判断 Agent 真的进步了

### 进入条件

读者已有 28 的真实连续轨迹、设计记忆、活动历史检查和失败/成本字段，能区分机制通过与 Agent 能力结论。尚未有真实多文件模型实验，比较方案、校准方法和重复数需要冻结为后续计划。

### 问题与失败现象

一次成功任务可能来自简单 fixture、记忆主动泄漏、更多预算或人工介入；只看新需求通过率会忽略历史回归、返工、未知和成本。单文档 runner 的确定性适配器不回答真实 Agent 是否理解架构或长期维护是否改善。

### 核心概念

冻结三组：普通助手得到同一项目当前快照、当前任务、同样文件工具和可用历史检查，但不得到结构化设计记忆；设计记忆组在同样条件下额外读取由该组此前真实产物生成的版本化模块/决策记忆；完整闭环组还被要求主动执行计划、影响分析、历史检查、独立验证和回滚记录。三组共享同一独立评价器、同样历史检查、同样文件工具访问、模型、总预算、时间窗和任务序列；完整闭环不拥有独占 oracle 或工具。多条独立序列、多个随机重复，后续任务在前轮完成后揭示。若使用第 16 章计划模式，须把它作为本实验分支前置；否则使用相同的轻量分析表。报告区分算法是否主动请求并消费记忆，不能只因上下文存在就归因。

### 小节安排

1. **先定义比较问题**：明确新需求完成与历史回归是两类目标，写出非目标和未知项。
2. **建立可运行校准层**：复用单文档 runner 验证继承、检查持续和故意回归，不称为 AI 实验。
3. **冻结三组与公平条件**：确定固定模型、权限、预算、序列、重复数和独立评测。
4. **记录结果与实际成本**：统计新需求、回归、仍失败、返工、人工介入、elapsedMs、token、cost。
5. **判别结论与 `F29/S6`**：给出有效、条件性有效、无明显改善或尚无法判断的规则。

### 贯穿示例

同一预览小站经历“提取表单校验模块、配置 v2 兼容 v1、异步校验、取消迟到结果、分步迁移接口、依据明确退役旧配置”六轮任务。每组从相同项目快照出发，使用相同文件工具和独立评价器；各组可用同一历史检查，但普通组没有结构化设计记忆。记忆组只有在 Agent 实际请求、读取并在工具轨迹中消费该组此前生成的记忆时才记为使用；人工预写 golden 方案不得注入。输出是每序列/每次重复汇总，失败和人工接管保留，不用最佳序列代表总体。

### 实现增量

计划新增 `ExperimentManifest`、`Arm`、`Sequence`、`Repeat`、`MetricRecord`、`AttributionFlag` 和 `ConclusionRule`。初始建议每组 5 条独立序列、每序列 3 次重复仅作为探索起点，不能当功效保证；先用 runner 做机制校准，再用固定模型与小规模多文件 fixture 试运行。事前冻结主要指标（新需求通过、历史回归、仍失败/返工、人工介入、实际 elapsedMs/token/cost）、重要差异阈值、配对区间和成本权衡。多文件工具、隔离环境、模型调用计量和独立盲评均待设计。

### 验收设计

正常：所有组共享规格，输入/输出和检查可复算，独立评价器与任务执行分开，统计单位是序列/重复而非每轮。工具轨迹和记忆摘要能绑定到 Agent 的实际请求，证明记忆被真实消费。失败：预算不等、模型/工具漂移、任务泄漏、记忆未读取、人工补救、序列中断和成本缺失均标限制或 `null`。差异不显著不能证明等效；观察到退化必须报告，可归为无明显改善。缺成本只能限制效率判断，质量证据充分时仍可作条件性质量结论。回归：28 的历史检查持续，C09 同时报告新需求通过与历史回归。不能以文件数或代码行数单独判优。

### 产物与练习

产物是实验manifest、校准报告、三组协议、原始记录、记忆请求/工具轨迹、成本/介入表、按序列/重复统计汇总和F29/S6。练习模拟四类结论：改善超过预先定义的实际差异阈值、配对区间支持且回归/成本满足约束时，判为在已测范围有效；仅部分任务/条件成立为条件性有效；没有观察到明确收益为无明显改善，若明显退化必须直写退化幅度；缺输入、协议失效或不确定性过大则尚无法判断。没有显著差异不等于已证明等效，缺费用只限制成本相关结论。

完成标准是另一位作者能按冻结协议复算校准结果、检查三组条件是否相同，并把每条结论追溯到序列/重复与原始回执。尚未执行真实实验时，只交协议和机制校准，结果表明确not_run；不能填写模型效果结论来满足篇幅或交付要求。

### 交接

向后续作者交付完整实验协议、初始重复数建议、校准证据和限制清单。任何声称“Agent 进步”的文字都必须引用多序列、多次重复和共享评测；若只完成 runner 校准，应只报告机制已验证，等待真实实验。

# 第五部分：实际应用——构建一款集成 Agent 的轻量 IDE

本部分把 S3（第 15 章完成的可信 Harness）接到 Web Studio 风格的轻量 IDE。教学版的重点是工作区、编辑器上下文、Agent 面板、diff 审阅和验证结果；通用界面骨架可以作为脚手架，Rust runtime 才是任务、运行、授权、预算、事件和证据的权威，界面只保存视图状态与事件游标。产品线让用户从 IDE 操作同一个“预览小站”：先修正 README 启动命令，再修复规格规定的空白表单输入缺陷。工程线另取一个有界功能，由前文 S3 Agent 辅助开发 IDE 自身；两条线分别验收，不能把一个产品的演示当成另一个的工程证据。

## 依赖与阶段成果

从 S3（15）即可独立进入本部分，不强制完成 16–20 的 Skill、MCP 或多智能体扩展。教学路线使用第 15 章已有的教学 Rust Harness 作为后端，经 21 新增的薄适配层消费 Control API 语义；不能把当前根 `runtime` 当作已经具备 S3 写入能力的起点。读者需有一个能产生候选、请求批准、应用并验证的 Rust Harness，理解候选 digest、文件基线、取消、`outcome_unknown`、事件游标和验证状态。仓库的 [整合规格](../../REIN-INTEGRATION-SPEC.md) 是跨项目语义权威；[runtime README](../../runtime/README.md) 与 [R1A 摘要](../../records/REIN-RUNTIME-R1A-20260921/task-summary.md)说明当前根 runtime 只有离线只读纵切，不能把旧 `rust/` 维护实现自动等同于根 runtime 的写入和客户端能力。具体 DTO 继续从正式合同或单一教学权威生成，不维护第二套权威 DTO。计划新增 S5/F21–F24，覆盖 INT-S01–S07 的教学裁剪及 INT-B01–B12 的映射；完整 R1c、P0、发行和原生 UI 验收仍是独立缺口，R1b 外部委派是完整 R1c 的前置范围。

## 21 设计 IDE 与 Harness 的连接方式

### 进入条件

读者已有 S3 的任务、候选、批准、验证和事件语义，能用教学 Rust Harness 的 CLI 检查状态；不需要先完成计划模式、Skill、MCP 或委派。可运行起点是第 15 章教学后端和一个预览小站工作区。当前根 `runtime` 只有离线只读 `demo/show/resume/cancel`，不能直接作为具备 S3 写入能力的后端，也不提供可声称完成 R1c 的 Web Studio 客户端、真实模型或写入批准。21 的任务是设计薄适配层和能力表，再逐项补连接能力。

### 问题与失败现象

如果 UI 自己维护任务状态，页面重载、重复点击或断线就会重复派发；如果 UI 直接写文件，批准、基线和证据会被绕过。常见误判是把“按钮显示运行中”当成 runtime 正在执行，把 HTTP 预览当成已验证交付。需明确同一 request ID、调用者、工作区、任务、候选版本和事件游标，重连只续读，不重启任务。

### 核心概念

建立 Web Studio→Control API→第 15 章教学 Rust Harness→事件/产物的边界，并把根 `core/runtime` 作为产品合同参考。UI 状态包括选择的工作区、编辑器缓冲区、面板展开状态、最近游标和显示缓存；runtime 保存任务、运行历史引用、Attempt、Approval、Budget、Artifact、Verification 和 DeliveryManifest。保存会话至少持久化这些任务/历史引用，UI 另保存视图；客户端重连只用游标查询同一 Run；中断执行恢复须核对 lease、in-flight effect 和外部事实，未知结果不得盲重放。教学版只补最小事件游标和只读重连；服务重启无法续接时停止并核对，符合 B08，不给根 runtime 伪补崩溃续执行能力。

### 小节安排

1. **画出从提交到证据的控制边界**：把 UI 命令、runtime 状态、事件和产物逐项归属。
2. **设计最小 Control API 消费路径**：覆盖 `task.submit/run`、`run.get/cancel`、`approval.respond`、`events.subscribe`、`artifact.get`。
3. **区分保存、重连与执行恢复**：用关闭页面、网络断开、driver 重启三个时序说明不同结果。
4. **把版本与幂等键放进界面动作**：重复同内容返回同 Run，内容不同拒绝，版本冲突要求重新读取。

### 贯穿示例

用户在 IDE 选择“预览小站”，提交“检查 README 启动命令”，UI 发送调用者、工作区摘要、任务和 request ID；面板通过事件游标显示运行，收到候选后展示等待批准。用户刷新页面时只调用 `events.subscribe` 续读；用户关闭 runtime 后重启，若 effect 已 claimed 但无法确认，面板显示 `outcome_unknown` 并提供核对入口，不自动重发。上述动作是计划中的教学流程，现有外部 Web Studio UI 未检查。

### 实现增量

计划新增一个薄客户端适配层和 UI 状态模型，不新增第二套任务状态机或权威 DTO：`ViewState{workspace,document,selection,run_id,cursor}`、`ControlClient`、`EventProjector` 和错误到视图状态的映射从正式合同/教学权威生成。能力表应列出 S3 已有的候选、批准、验证和范围控制，21 补连接、游标、幂等和重连，其余真实 Web Studio/R1c 能力标为未实现。HTTP 预览 URL 必须绑定候选 digest/版本；diff 只能来自 runtime 的候选与基线。

### 验收设计

正常检查提交、进度、事件游标、候选、批准和 artifact 归属一致；相同 request 重放不多执行一次。失败检查不同内容同 ID、版本冲突、取消、授权撤销、断线、迟到事件和 runtime 重启；必须显示失败/未知并保持派发计数和文件事实。回归 S3 的批准绑定、预算和验证状态；INT-B03/B07/B08/B09/B10 是必要负例。当前只有规格和离线 runtime 证据，F21 尚未执行。

### 产物与练习

产物是连接时序图、状态归属表、Control API消费契约、F21计划快照和INT-S/B映射表。练习分别模拟刷新页面、客户端断开和driver重启，记录Run/Attempt/cursor是否变化；再重放相同与不同内容的request ID。完成标准是能从runtime查询和UI日志确认是否重复派发，而不依赖按钮文字。

### 交接

交给22连接契约、版本/幂等边界与断线语义。22加入编辑器缓冲区、磁盘基线和选择范围，缓冲区可作为明确标注的用户输入传递，但不能直接落到目标文件、绕过运行时写数据库，或把UI缓存当作磁盘事实。

### 复用与证据

复用 [REIN-INTEGRATION-SPEC.md](../../REIN-INTEGRATION-SPEC.md) 的产品分工、INT-S01–S08 和控制请求语义，[runtime/README.md](../../runtime/README.md) 的持久状态、独占 owner、显式恢复和 `OutcomeUnknown` 规则，[R1A 摘要](../../records/REIN-RUNTIME-R1A-20260921/task-summary.md) 的离线范围。它们是已有规格/实现/执行记录，但明确不含 Web Studio R1c；本章客户端和 UI 走查为计划新增、尚未核实。

## 22 把编辑器上下文交给 Agent

### 进入条件

读者已有 21 的 Control API 和状态归属，能区分 UI 缓冲区、磁盘文件和 runtime artifact。可运行起点是同一预览小站，包含 README、配置和一个待修复的页面；读者已掌握 S3 的允许路径、资料信任、基线摘要和批准前只读约束。尚未定义编辑器选择、未保存变更和上下文大小策略。

### 问题与失败现象

把编辑器中的旧缓冲区、磁盘中的新内容和 Agent 已读取的快照混在一起，导致候选基线错误；把整仓库直接塞入请求又泄露范围、超出预算。空白表单缺陷需要同时看到规格、目标页面和测试输入，但资料中的指令不能提升权限。编辑器显示“已保存”不等于 runtime 已拿到同一版本。

### 核心概念

上下文包必须写明来源、摘要、时间/版本和允许用途：任务说明、当前选中文本、磁盘基线、相关规格、只读工具结果分别标识。未保存缓冲区若要交给 Agent，应作为用户明确提供的输入并与磁盘基线分开；候选只能绑定 runtime 实际读取并哈希的目标基线。UI 负责选择和提示来源，runtime 负责重新读取、范围检查和证据绑定。

### 小节安排

1. **区分三种文本来源**：编辑器缓冲区、磁盘基线和 Agent 读取结果各自展示摘要。
2. **从选择区域生成最小上下文**：限制文件、行范围、规格和预算，说明截断行为。
3. **处理未保存内容与冲突**：保存、丢弃、以显式输入继续三种路径分别记录。
4. **为页面缺陷准备可复验输入**：空字符串、空格、有效值和预期副作用计数进入验证计划。

### 贯穿示例

用户在编辑器打开页面文件，缓冲区暂时包含本地未保存改动；面板明确显示“编辑器缓冲区摘要 A、磁盘摘要 B”。提交修复空白表单时，Agent 只能读取声明的页面、规格和验证器输入。若磁盘在任务中变化，runtime 重新检查基线并拒绝旧候选；若用户保存后重新提交，则产生新的输入摘要和批准绑定。示意流程不代表已有 Web Studio 已实现。

### 实现增量

计划新增 `EditorContext{path,selection,buffer_digest,persisted_digest,dirty}`、`ContextItem{source,uri,digest,role}` 和 `ContextManifest`，通过 Control API 传递声明而非直接让 UI 写 runtime 数据库。上下文截断、敏感路径拒绝、资料不可信标记和版本冲突均生成可观察事件。页面验证仍由独立 verifier 运行，不由前端判断通过。

### 验收设计

正常检查选中文本、规格、磁盘文件和工具结果在任务记录中有来源与摘要，候选只针对允许文件；B01 修改前基线应观察到空/空格输入检查失败，修改后同样输入被拒绝且副作用计数为 0，判定为修复通过；B02 有效值前后均只提交一次且值正确。失败检查 dirty buffer 与磁盘不一致、范围外选择、缺失规格、资料注入越权、上下文超限和基线变化；候选必须拒绝或重新读取。回归 S3 的批准必须绑定新候选和当前基线；本章未执行。

### 产物与练习

产物是上下文 manifest、来源展示设计、空白表单固定输入集、冲突回执格式和 F22 计划快照。练习先改编辑器未保存文本，再分别保存和取消，比较 runtime 看到的 digest；随后添加一段资料中的越权指令，观察其只作为不可信内容。完成标准是能追溯每一段 Agent 输入，不把 UI 选择证明成运行时读取。

### 交接

交给 23 的是有摘要和范围的上下文、dirty/baseline 冲突处理、B01/B02 输入和验证器调用约束。23 才执行一次真实产品纵切，必须把批准、diff、验证、失败与未知状态串起来；若 22 的上下文不满足，不得用预置答案绕过。

### 复用与证据

复用 [REIN-DESIGN.md](../../REIN-DESIGN.md) 的上下文、artifact、批准绑定和恢复语义，[contracts/maintenance-v1.md](../../contracts/maintenance-v1.md) 的单已有文件、SHA-256 基线、精确替换和禁止新增/删除/重命名边界，以及 [context-retrieval.md](../../docs/chapters/context-retrieval.md) 和 [context-state.md](../../docs/chapters/context-state.md) 的教材主题。现有 runtime 只证明离线只读上下文，Web Studio editor bridge 和真实写入仍计划新增。

## 23 完成一次真实开发任务

### 进入条件

读者已有 21 的连接、22 的上下文 manifest 和 S3 的候选/批准/验证；能用同一目标项目的固定 fixture 与输入。此处“真实”指真实产品交互和真实目标副本中的一次有界任务，不等同于真实模型已在线运行；没有可用真实模型时必须使用明确标注的离线响应并保留未验证状态。

### 问题与失败现象

单独展示 Agent 面板、diff 或测试绿色，都不能证明提交到交付的链路完整。常见失败包括批准旧候选、验证器失败仍显示完成、写入后断连误判未执行、目标副本基线冲突却覆盖文件。任务应覆盖从提交到证据的每个边界，并把 unknown 作为需要核对的状态。

### 核心概念

用最小纵切串起submit → observe → diff审查 → approval → apply → verify → evidence/delivery。批准绑定调用者、范围、候选digest、输入基线、策略版本和有效期；检查结果passed/failed/undetermined/not_run与有效性stale分开保存，UI无权改写。取消和迟到批准沿08的语义处理；已派发无回执的效果保留outcome_unknown，不盲重放。

### 小节安排

1. **冻结产品任务和实现前基准**：建立空白输入、有效输入、范围和预期副作用计数。
2. **在 IDE 中提交并观察运行**：展示任务状态、事件游标、工具结果和候选版本。
3. **审阅 diff 后回复一次授权**：检查当前基线和批准绑定，观察拒绝旧候选的负例。
4. **应用、验证并导出证据**：区分业务断言失败、验证器故障、未知写入和成功交付。

### 贯穿示例

从新目标副本启动预览小站，先用 C01 修正 README 命令，再提交空白表单缺陷：浏览器分别输入空字符串、空格和有效值。正常路线显示候选 diff，用户批准当前版本，页面预览和验证结果绑定同一 digest；B03 缺 Spec、B04 越界写、B05 验证器不可用、B09 写后断连、B10 取消分别停在对应状态。网页检查和原生界面走查分开保存；当前均是计划步骤。

### 实现增量

计划新增最小文本编辑/选择脚手架、客户端面板、diff/证据链接和目标副本适配；高阶编辑能力留后续，runtime 承担真实控制。需将 `ApprovalRespond`、`events.subscribe`、`artifact.get`、`evidence.list` 与 HTTP 预览候选摘要关联，保存每次文件操作和派发计数。教学裁剪不要求外部委派，但完整 R1c 的 R1b 外部委派仍是前置验收；本部分也不实现通用 DAG 或多客户端并发。

### 验收设计

正常检查按 `submit → observe → diff 审查 → approval.respond → apply → verify` 顺序完成 B01/B02、B07、B11、B12：批准只能消费审查过的当前候选。若编辑器有 dirty buffer，即使磁盘摘要未变，也必须先让用户保存、放弃或取消；禁止 Agent 静默覆盖未保存内容。失败检查旧候选批准、基线变化、范围外路径、验证断言失败、验证器故障、取消、断线和包摘要损坏；各自状态精确为拒绝/failed/undetermined/unknown，不显示成功 Acceptance。回归 S3 权限、预算、工具结果和 08 取消；本框架尚未执行真实 UI 或外部服务。

### 产物与练习

产物是一个固定任务的产品运行记录、候选 diff、批准与事件、浏览器/原生走查证据、验证报告、DeliveryManifest 和 F23 计划快照。工程线的有界例子固定为“只修改已有 IDE 错误提示映射，不修改测试”：由 S3 Agent 产生候选，人工批准，回归检查并做一次产品走查，独立记录结果。练习要求先完成正常路线，再改变磁盘基线重试批准、断开客户端并恢复查询、注入验证器故障，逐项写明实际文件与派发次数。完成标准是交付包能在新副本应用并读回，失败路线不被覆盖成成功。

### 交接

交给 24 的是可重复的产品任务、固定输入/输出、失败和成本记录、安装候选与证据清单。24 以这些真实产物制定评测、打包、干净安装和项目复盘；若 23 只有离线回放，24 必须把真实模型/原生 UI 仍列为未验证，而非补写结果。

### 复用与证据

复用 [REIN-INTEGRATION-SPEC.md](../../REIN-INTEGRATION-SPEC.md) 的 INT-B01–B12、R1c 产品纵切和交付边界，[contracts/maintenance-v1.md](../../contracts/maintenance-v1.md) 的候选/批准/验证约束，[runtime/README.md](../../runtime/README.md) 的显式恢复和不自动重放。R1A 的 MET-001–004 是已有离线执行证据，只覆盖根 runtime 只读闭环；本章的 Web Studio、真实写入批准和产品任务仍计划新增/尚未核实。

## 24 评测、打包与项目复盘

### 进入条件

读者已完成或明确记录 23 的固定任务、候选、失败、成本和证据，理解产品线与工程线分离。可运行起点是一个可导出的教学包和新目标副本；不要求第六部分进阶实验，也不能用文件数、代码行数或单次演示替代效果判断。

### 问题与失败现象

只展示一次成功截图会掩盖安装路径、版本不兼容、断线恢复、验证器故障和人工介入成本。发布一个能在开发机运行的目录也不等于干净安装可用；教学裁剪完成也不等于完整 R1c，更不等于 P0 或 R4。R1b 外部委派属于完整 R1c 的前置范围，不能在教学裁剪中被悄悄宣称完成。

### 核心概念

把产品交付拆成固定任务评测、失败与成本分析、包来源和兼容矩阵、干净安装回归、演示脚本、复盘与未决项。评测至少记录任务完成、历史回归、返工、人工批准次数、运行时间、模型/工具预算和未知结果；缺少计时器、计费或人工记录时成本保持 `null`，不得编造数字。产品线记录 IDE 操作预览小站；工程线记录“仅修改已有错误提示映射、不改测试”的 Agent 任务，两者分别得分。效果比较可设置基础 CLI 与集成 IDE 在同一固定任务上的基线，但不把一次演示当作统计结论。

### 小节安排

1. **冻结产品评测序列**：重复 C01、B01/B02 和失败场景，记录输入、版本、成本与证据。
2. **建立包和兼容矩阵**：说明 Rust runtime、UI 资产、schema、Veriflow 规则和运行依赖来源。
3. **做干净安装与回归演示**：在无开发缓存的新目录核验启动、连接、任务、预览和证据。
4. **写项目复盘与下一轮建议**：区分有效、条件性有效、无明显改善和尚无法判断，并列出 S6 输入。

### 贯穿示例

对同一预览小站重复三组序列：正常 C01/B01/B02、权限/基线/取消失败、B08/B09 断线恢复。再把打包产物安装到干净目录，核对 schema 和验证器版本，重放一个固定任务。工程线另用 S3 Agent 只修改已有 IDE 错误提示映射、不修改测试，记录规格、候选、批准、回归和一次产品走查；该结果不能替代产品线 B11。

### 实现增量

计划新增评测manifest、兼容矩阵、安装检查脚本、演示记录模板与复盘表，不扩张runtime状态机。包记录实际使用的教学Rust后端、IDE脚手架、schema、验证器、源码/构建摘要、依赖和平台；若接入Veriflow才随包固定其规则/脚本版本，未接入时沿用15的独立验证器并注明产品差距。安装后复核启动、连接、事件、预览和证据。完整三产品发行、签名、公证和渠道发布属于INT-S08/R4后续工作。

### 验收设计

正常检查固定任务在新副本完成、验证和交付，干净安装能启动并重放，工程线和产品线证据各自完整。失败检查缺依赖、schema 漂移、版本不兼容、验证器不可用、网络断开、unknown 结果和历史回归；记录失败或未确定并保留原始输出。回归 S3、INT-B01–B12 中受影响项和 23 的派发计数；框架阶段未执行安装、浏览器或原生 UI 验收。

### 产物与练习

产物是 S5 产品包、固定评测记录、成本/人工介入表、兼容矩阵、干净安装日志、演示脚本和 F24 计划快照。练习要求在新目录安装一次，故意移除一个依赖或改变 schema 摘要，观察失败分类；再完成一次产品线/工程线复盘，分别写出已证实和未知结论。完成标准是第三方可按来源和命令复现范围内结果。

### 交接

交给第六部分的是同一项目、已导出的候选/验证/交付产物、历史要求、失败记录和成本基线。25–29 可从 S5 研究架构理解与持续演进；若产品包没有真实产物，必须明确使用等价多文件基线，不得把本部分离线单文档记录写成真实 Agent 能力提升。

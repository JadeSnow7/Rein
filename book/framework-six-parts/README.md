## 定位与读者

本书面向会读写简单程序、希望亲手理解 Agent 工程机制的开发者与求职者。先用 Python 完成一个可解释的小工具，再把连续行动、权限、修改与验证放入 Rust Harness，最后通过 IDE 展示产品能力，并研究长期演进是否真的改善。读者不需要在开始时掌握 Rust、MCP 或多智能体。

主线必需的终端、JSON、错误处理和 Rust 知识在首次使用处解释；阅读材料只提供可选深化。每一章回答“现在失败在哪里、增加什么机制、如何观察变化”。框架是后续作者的写作合同，不是把所有设计名词强行实现成代码。

## 阅读路线与依赖

1. 入门路线：00–03，得到终端代码修改助手；04 从产品机制提炼核心能力，并冻结新的等价迁移样本，分别比较诊断、接受/应用与验证；05–08 再增加 Rust 内部协议与循环控制。
2. 单 Agent 工程路线：00–15，得到 S3；03 已演示单文件确认写入；14 才在通用 Harness 中接入持久批准和应用，13 只产生该阶段的候选补丁。09–12 的上下文、资料信任和权限为该写入建立条件。
3. 产品路线：S3 → 21–24，可独立交付 IDE。第四部分按需要插入能力：16 计划依赖 15；17 Skill 依赖 11、12、15；18 扩展/Hooks 依赖 05、08、12、15；19 MCP 依赖 18 的工具适配边界；20 委派依赖 07、12、15、16，不强制 Skill、MCP 或 Hooks。章号并不强制所有分支串联。
4. 进阶路线：S5 → 25–29，沿同一目标项目研究架构和长期维护。已有 S3 的读者可先阅读分析设计方法，但完整实验须准备第五部分的项目基线或明确声明等价的多文件项目基线；当前单文档 runner 只用于校准机制。

每章结束时交付能被下一章读取的输入、失败样本与检查结果，而非只交一段说明。尚不存在的前置产物均标为“计划新增”；不可用未来章的运行能力解释当前章已通过。

## 人机分工与读者参与（D18）

第一至五部分由人确定架构和设计，AI 编写代码；第六部分研究把设计也交给 Agent 的完全 vibe coding。书中的开发方式与 Rein 的工作方式同构：Rein 是“模型提议 → 人批准 → 程序验证”，本书是“AI 编码 → 人定设计并审查 → 程序验收”。

| 谁 | 负责 |
| --- | --- |
| 人 | 任务与验收条件、边界、接口与数据形状、状态设计、验收样本（含失败样本）、审查结论、是否合入 |
| AI 编程助手 | 按设计卡实现代码、补写测试代码、样板与参数解析 |
| 程序 | 执行验收，给出不依赖任何一方自述的结果 |

什么算通过由人决定；AI 可以补写测试代码，不能自行决定验收标准。读者参与按三段递进：

| 章节 | 读者对设计 | 读者对代码助手 |
| --- | --- | --- |
| 01–03 | 看：“本章设计”小框说明配套程序按什么约定写成，不要求细读契约 | 不使用；01 用自己运行的对话程序向模型要 C++ 源码 |
| 04–24 | 写：参与设计卡与验收样本 | 用 Claude Code、Codex 等实现，审查 diff 并运行验收 |
| 25–29 | 交出：研究把设计交给 Agent 的前提与效果 | 完全 vibe coding 实验，与前述分工对照 |

01–03 每章含“本章设计”小框和章末“本章边界卡”（模型能做什么、程序做什么、用户决定什么、还不能做什么）。04 起，正文按“问题 → 设计卡 → 验收样本 → 用代码助手实现 → 审查要点 → 运行验收 → 边界卡 → 提示词”组织，对应下列字段 6、7。04 只简短引导代码助手的使用，提示词工程、防御性编程和 AI 痛点在后续相应章节深入。

提示词从 04 起附在正式正文末尾，逐条标注来源：**作者实际使用**（链接开发记录）、**据设计反推**（说明依据，未经运行）、**已试用**（记录起始快照、工具与模型、实际 diff 和验收结果）。

## 统一写作字段与状态语言

各部分框架使用 `## NN 标题` 和十个三级字段，方便作者接力与结构检查；从 04 起，正式正文另在末尾附按来源标注的提示词（见上节）：

1. `进入条件`：知识、可运行起点和仍未具备的能力。
2. `问题与失败现象`：一个读者能观察到的问题。
3. `核心概念`：本章增量及与前文关系。
4. `小节安排`：至少四个按教学顺序命名的小节及内容提要；不得只列概念词。
5. `贯穿示例`：具体输入、动作、预期可观察结果，标注示意/离线/真实。
6. `实现增量`：数据结构、接口、状态或文件边界；提议名明确标为计划，概念章允许分析/设计产物。04 起写成读者可用的设计卡，并说明哪些由人确定、哪些交给代码助手实现。
7. `验收设计`：正常、失败、必要回归；给出输入与判断，框架阶段尚未执行。验收样本与判断由人确定，并列出审查代码助手产出时的要点。
8. `产物与练习`：产物、练习和可检查的完成标准。
9. `交接`：下一章或分支接收什么，章末快照计划。
10. `复用与证据`：具体已有路径、改写/新增内容和证据限制。

现状必须分别表达：**已有正文**是已读到的内容，可能仍为初稿；**已有实现**指检查到相应入口或逻辑；**已有执行证据**需引用原始记录并注明历史/离线/真实和绑定范围；**计划新增**指本框架设计；**尚未核实**指不足以判断。索引状态与正文不一致时如实列示并修正权威清单。

候选字段命名建议为 `path`、`start_line`、`end_line`、`original`、`suggested`、`reason`、`source_digest`，02–03 的原文行表由程序维护；13 才升级为含基线与补丁摘要的候选契约。字段名为本轮建议，不是现有 wire DTO。运行状态归 Harness，UI 保存视图和事件游标；批准绑定候选、目标基线、范围和当前版本。模型审查意见、程序检查、任务验收和系统评测分别记录。

示意输出不是运行记录；离线响应不是实时模型回复；历史执行回执不证明当前新章可跟做；人工教学验收须由学习者按冻结版本执行并留记录。未测数据保持未知，不能拿文件数、代码行数或测试总数代替学习效果或 Agent 能力提升。

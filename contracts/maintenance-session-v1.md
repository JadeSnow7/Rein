# 维护会话 v1：第 13–17 章的连接边界

状态：已实现离线集成入口；不表示逐章验收通过。继承 `maintenance-v1.md` 与 `extension-v0.2.md`，默认只读路线和 0.1 历史契约不变。

## 会话与授权

一次会话绑定一个已有 UTF-8 文档、一个受控规则和一个工作区。读取依据、候选生成、调用者审批、宿主应用与结果采纳分别执行。候选生成器只接收实际观察与失败反馈；评测文件的 `expected` 不进入生成器。调用者审批回调是本地受信接口，不能由模型输出替代。

Rust core 保留候选和批准表；批准必须匹配候选的相对路径、文件基线与替换内容。`apply_patch` 的工具参数携带候选数据用于宿主执行，参数自身不是授权。core 在派发前验证并消耗具体批准，宿主应用时复查基线。新的候选必须重新审批。结果未知时原批准不得再次派发。

## 维护 profile 与信封

默认 profile 只有 `read_file`、`search_files`。显式启用 maintenance profile 后，在同一 `rein-extension/0.2` 信封注册 `run_verification` 和 `apply_patch`。ready 的声明必须与实际处理器一致；core 的目标范围和批准检查独立于能力声明。

- `run_verification` 参数是 `{target, rule}`。规则只能来自已有受控验证器，不能传 shell。返回验证结果，区分任务不符合规则与工具无法完成检查。
- `apply_patch` 参数是 `{path, baselineSha256, replacement, digest}`。宿主仅替换已有普通文件，不能新增、删除、重命名或跟随符号链接。
- 每次调用仍使用独立 task/request/session/call 身份、单个在途宿主调用、严格终态和进程回收。

应用成功的证据包含实际修改后文件版本。验证证据绑定目标和验证依据，调用期间版本变化则不能采纳旧结论。验证不通过可以作为真实反馈，协议损坏或写入是否发生无法判定时停止并交人工。

## 有限修复

生成前通过宿主读取当前文档及规则所需依据，把实际文本传给生成器。生成器返回无须修改时仍须运行验证，不能将无候选直接解释为通过。

首次候选之外，默认最多两个修复候选。每次修复重新读取实际状态，获得新的候选与审批；保存此前失败，不能覆盖成最终一次成功。拒绝、取消、未知结果及预算耗尽都停止派发。

基础演示采用离线生成器与显式调用者审批，展示的是维护会话机制。它不宣称真实模型能力或完整单 Agent 项目验收。真实模型接入、逐章快照恢复及提示词试用单独留证。

## 本轮验证

要求真实 Rust → Node stdio → 临时文件变化 → 验证回执链路；同时检查无批准、候选篡改、过期基线、一次修复通过、持续失败达到上限、写入后断连不自动重放。各反例须观察实际 dispatch 次数、文件字节和停止原因；任意异常的 `toThrow` 不能代替指定边界的验证。

参考宿主会额外检查 core 为该次子进程注入的候选摘要环境值。它不进入模型参数，也不是可用于远程授权的独立令牌；决定是否允许派发的依据仍是 core 内部批准表和当前文件基线。
